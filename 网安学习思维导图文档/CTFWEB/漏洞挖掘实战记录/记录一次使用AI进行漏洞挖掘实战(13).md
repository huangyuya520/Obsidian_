
# one.xxx.edu.cn 存在数据中台视图预览接口越权导致全校师生身份证号等敏感信息泄露漏洞


## 漏洞描述

门户管理端（/platformManage/）的数据中台模块提供“视图管理”“数据集管理”，管理员在页面上写一段 SELECT 作为视图定义，点“预览数据”时前端调用 POST /api/blade-workbench/eduApiServeView/previewData，把 sql 字段原样交给后端，后端在数据源上执行该语句并把结果集（headData + data）回显给调用方。

这个接口的设计前提是“只有建视图/建数据集的平台管理员会用到它”，因此后端只校验了登录态，没有做功能级鉴权：任何持有门户令牌的账号，无论角色，都能调用。同时它对 SQL 只做了一层表白名单校验，判断语句最外层 FROM 后面的表名是否属于“数据中台可用表清单”，而这份清单里正好包含 edu\_student\_info、edu\_teacher\_info 等人员主表；子查询、函数、UNION 之外的表达式都不在白名单检查范围内。

攻击者用一个普通在校生账号即可依次完成：

- 读取数据中台可用表清单，拿到学生、教职工、班级、院系、专业、校区等 8 张基础表与 5 张业务表的真实表名；

- 向 previewData 提交自选的 SELECT，直接拿到结果集，身份证号、学号/工号、姓名、手机号、院系、班级、校区、宿舍全部明文；

- 用 count(\*) 精确统计规模：在校生 20144 条、教职工 1691 条；

- 把子查询放进投影列即可引用白名单之外的表，实测读到 blade\_user 有 77241 条账号记录、当前库名为 bladex，读取面实际是整库；

- 同一套权限缺失还让以下数据一并可读：9 个开放平台 appKey 及其授权 IP 段与联系人手机号/邮箱、49 个数据集与 82 个服务接口的协议定义、4 个视图的原始 SQL（含表名与业务口径）、edu\_student\_info 与 edu\_teacher\_info 的完整字段结构与中文注释。


结论：所有请求均在真实目标上返回 200 并带回真实数据；不带 Blade-Auth 头时返回 401「缺失令牌,鉴权失败」；查询白名单外的表时返回「仅可查询左侧列表中的表和视图」。这两条对照说明问题出在登录后的权限边界内，不是公开查询功能。

### Step 5：表名白名单只校验最外层 FROM

```

select (select count(*) from blade_user) as c from edu_student_info limit 1
```
