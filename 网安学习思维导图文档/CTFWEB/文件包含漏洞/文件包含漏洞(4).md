
# 文件包含漏洞常见文件包含利用手法

## 文件包含恶意文件进行漏洞利用
在文件包含漏洞（LFI/RFI）中，PHP 等服务端脚本的包含机制（如 `include`、`require`）会将==**任何被包含文件的内容当作后端代码解析**==，而不管文件的后缀名是 `.jpg`、`.txt` 还是 `.zip`。

当目标系统同时存在**文件包含点**和**限制严格的文件上传点**（如仅允许上传图片）时，攻击者通常会通过以下几种核心技巧组合利用以获取代码执行权限（RCE）

1. ==图片马与元数据注入（Image Webshell）==

这是最基础的组合手法。当上传接口对文件类型、MIME-Type 或文件头（Magic Number）进行校验时，将恶意脚本隐藏在合法图片中。

**请参考该笔记文章：**[文件上传漏洞(2)](文件上传漏洞(2).md#利用图片马隐藏恶意代码进行文件上传)


2. ==压缩包伪协议结合（`phar://` 与 `zip://`）==

当上传点允许上传压缩包，或者允许上传伪装成图片后缀的压缩包时，可利用 PHP 流包装器（Stream Wrappers）直接解析压缩包内的脚本。

| **协议**                  | **语法与格式要求**                | **说明**                                        |
| ----------------------- | -------------------------- | --------------------------------------------- |
| **`phar://`**           | `phar://[文件路径]/[压缩包内文件名]`  | 支持将 `.phar` 压缩包后缀改为 `.png`/`.jpg` 上传，包含时无需特权。 |
| **`zip://`**            | `zip://[绝对路径]%23[压缩包内文件名]` | 需要使用绝对路径，且 `#` 符号必须进行 URL 编码为 `%23`。          |
| **`compress.bzip2://`** | `compress.bzip2://[文件路径]`  | 直接对 bzip2 压缩的单一文件进行解压并执行。                     |

## 文件包含日志文件进行漏洞利用
在本地文件包含（LFI, Local File Inclusion）漏洞中，**日志包含利用（Log Poisoning / Log Inclusion）** 是一种非常经典且高频的代码执行（RCE）获取方式。

PHP 等后端语言在执行文件包含函数（如 `include`、`require`）时，**并不检查被包含文件的扩展名**，只要文件内容中存在有效的 PHP 代码标签（如 `<?php ... ?>`），解析器就会将其作为 PHP 代码执行。因此，==攻击者只要能将 PHP 恶意代码写入服务器可读的日志文件中，再通过 LFI 触发包含，即可实现任意代码执行==


- 包含日志文件完成文件包含漏洞利用的原理
	- 一般的WebServer（如Nginx，Apache）都会记录请求相关信息
	- 如，请求路径、返回状态码等
	- 因此，可以通过在这些记录点插入php代码，然后包含之完成利用


- 常用的日志
	- `Web Server`日志:`Apache`, `Nginx`
	- 其他可能产生日志的应用：`SSH`，`MySQL`
- 如何确定日志位置
	- 方式1:`phpinfo`
	- 方式2：根据常见的日志文件位置进行枚举
	- 方式3：读取产生日志的应用的配置文件进行获取
		- `e.g.,/etc/init.d/httpd`

4. ==注意点与排错技巧==

---

1. **日志文件读取权限不足**
    
    - **现象**：包含后页面无报错或提示 `Permission denied`。
    - **原因**：Web 运行用户（如 `www-data`、`nobody`）通常没有读取 `/var/log/auth.log`（权限通常为 `640` 且属组为 `adm`）或 root 所属的系统日志的权限。
    - **策略**：优先尝试 Web 服务自身的 `access.log` 与 `error.log`，通常属组与权限更容易匹配。

2. **语法污染（Log Poisoning Collapse）**
    
    - **现象**：日志被写入了不完整的 PHP 语句（如打错括号或漏写分号），导致整个日志文件在包含时直接触发 `Parse error: syntax error`，后续所有包含尝试均失败。
        
    - **策略**：
        
        - 投毒前在本地严格核对代码语法。
        - Payload 尽量短小精悍，优先使用动态传参形式，例如：

![](Pasted%20image%2020260830172540.png)
- 避免在 URL 中直接写包含大量特殊字符的复杂脚本。


3. **日志文件体积过大导致超时/内存溢出**

- **现象**：包含日志后页面响应极慢，最终返回 504 Gateway Timeout 或 500 内存耗尽错误。
    
- **原因**：大型站点的 `access.log` 往往有数百 MB，PHP `include()` 会将整个文件加载至内存并逐行扫描。
    
- **策略**：在目标服务轮转（Logrotate）后进行测试，或优先选择体积较小的日志文件（如 Error Log 或特定服务的独立 Log）

---


5. ==防御与加固方案==

- **输入限制与路径白名单**：严格对包含参数做白名单校验，杜绝接收用户输入的任意路径。
    
- **禁用危险配置**：配置 `php.ini` 中 `allow_url_include = Off`，限制远程包含。
    
- **限制目录访问范围**：使用 `open_basedir` 将 PHP 脚本的文件访问范围严格限制在 Web 根目录下，阻止跨目录读取 `/var/log/`。
    
- **最小化日志文件读取权限**：确保系统关键日志（如 `auth.log`、`access.log`）仅对管理员或特权进程开放读权限（权限设置为 `600` 或 `640`，去除 Web 进程的读取权限）





## 文件包含php session文件进行漏洞利用

### 补：session机制介绍
Session 机制是 ==Web 应用中用于在服务器端**跟踪用户状态**的一种解决方案==

因为 HTTP 协议本身是**无状态**的（服务器无法记住上一次请求是谁发出的），所以需要 Session 来记录用户的登录状态、购物车信息等连续互动数据


==工作原理==

- **首次访问**：用户打开网站，服务器收到请求后，会为该用户创建一个唯一的 **Session 对象**（保存在服务器内存、数据库或缓存中）。
- **生成 ID**：服务器同时生成一个随机且唯一的字符串，称为 **Session ID**。
- **下发凭证**：服务器通过响应头（Set-Cookie）把这个 Session ID 传给客户端的浏览器。
- **后续请求**：浏览器再次发送请求时，会自动在请求头中带上这个 Session ID。
- **识别身份**：服务器收到 Session ID 后，在内存中查找对应的 Session 对象，从而知道当前用户是谁

==Session 与 Cookie 的区别==

- **Cookie**：数据存储在**客户端**（用户浏览器），体积小，安全性相对较低。
- **Session**：数据存储在**服务器端**，安全性高，但如果用户量极大，会占用服务器较多的内存或存储空间

### 包含php session文件进行文件包含漏洞利用
利用 PHP Session 文件进行本地文件包含（LFI to RCE）是 Web 安全中的经典手法。PHP 在处理 Session 时，==默认会将 Session 数据以明文形式序列化存储在服务器本地磁盘上。攻击者只要能够向 Session 文件中注入 PHP 代码并获取其存储路径与文件名，即可通过文件包含漏洞执行任意代码==


- 利用条件
	- 1、能够得知PHPSession文件的位置
	- 2、PHP Session文件内容可控




1. ==PHP Session 文件存储机制==

当 PHP 启动 Session 时，会在服务器指定目录下创建一个以 `sess_` 为前缀、后接 `PHPSESSID` 的文件：

- **文件命名规则**：`sess_<PHPSESSID>`（如 `PHPSESSID=hacker123` 对应的文件为 `sess_hacker123`）
    
- **存储格式**：序列化字符串，例如 `username|s:6:"admin";is_admin|b:1;`
    
- **关键特性**：PHP 执行 `include()` 或 `require()` 时只识别代码标签 `<?php ... ?>`，不会受 Session 序列化格式的干扰

1. 当客户端发起一个 **Multipart/form-data** 格式的 POST 请求并包含文件上传时，如果 POST 数据中包含名为 `PHP_SESSION_UPLOAD_PROGRESS` 的字段，PHP 会自动触发 `session_start()`。

4. ==限制条件与排查要点==
---



1. **目录权限与属主问题**
    
    - 在 Ubuntu/Debian 默认 apt 安装的 PHP 环境中，`/var/lib/php/sessions/` 的权限通常为 `0733`（所有者 `root`，属组 `www-data`），Web 进程可写但**无权列目录与直接读取**，可能导致包含返回 `Permission denied`。
        
    - 自定义编译安装或 CentOS 默认使用 `/tmp/`，权限多为 `1777`，不受此限制。

2. **严格模式（`session.use_strict_mode`）**
    
    - 若配置 `session.use_strict_mode = On`，PHP 不会接受未初始化的自定义 `PHPSESSID`，必须由服务端随机生成合法 ID，增加了路径预测难度。

3. **Session 序列化引擎转义**
    
    - 部分序列化处理器（如 `php_serialize`）可能会转义双引号或特定特殊字符。尽量编写简短、不依赖复杂字符串拼接的 Payload，优先直接写文件释放持久化 WebShell


---


5. ==防护与修复建议==

- **配置基线加固**：
    
    - 若无上传进度监控需求，在 `php.ini` 中设置 `session.upload_progress.enabled = Off`。
        
    - 开启严格模式：`session.use_strict_mode = On`。
        
- **目录范围隔离**：启用 `open_basedir`，将 PHP 读写权限限制在 Web 目录之内，阻断对 `/tmp/` 或 `/var/lib/php/` 的跨目录访问。
    
- **代码层防御**：对包含参数实行严格的白名单校验，严禁直接拼接外部传入的路径
