### 使用空字符串截断绕过限制进行文件包含执行RCE==(php<5.3.4)==
在 PHP 文件包含漏洞（LFI / RFI）中，==**空字符截断**（又称 **%00 截断** 或 **Null Byte Injection**）是一种经典的绕过后缀限制的技术==

1. ==核心原理解析==

PHP 底层是用 **C 语言** 开发的。在 C 语言中，字符串使用 ASCII 码为 `0` 的字符（即 `\0` 或 `NULL`）作为**字符串的结束标记**（Terminator）

当后端代码为了防止任意文件包含，强制在用户输入的变量后拼接固定的后缀（如 `.php` 或 `.html`）时：

例：
![](Pasted%20image%2020260829164126.png)

如果在传入的参数中包含 `%00`（URL 编码对应的 NULL 字符）：

1. **PHP 层面接收**：`$file = "/etc/passwd\0"`，拼接后变为 `"/etc/passwd\0.php"`。
    
2. **底层系统调用**：PHP 将该路径传递给底层的 C 库函数（如 `open()`、`fopen()`）。
    
3. **C 语言截断**：底层函数读取到 `\0` 字符时，判定字符串已到达末尾，自动丢弃 `\0` 后面的所有内容（即 `.php`）。

4. **最终结果**：操作系统实际打开并解析的文件路径为 `/etc/passwd`，成功绕过了强制拼接的扩展名限制




2. ==漏洞利用场景==

- 场景 A：读取系统敏感文件 (LFI)
	- **后端代码**：`include("templates/" . $_GET['page'] . ".html");`
		
		例：
		![](Pasted%20image%2020260829165342.png)



- 场景 B：配合文件上传执行 Webshell
	当目标系统限制只能上传图片（如 `shell.jpg`），且文件包含函数强制带 `.php` 后缀时
	- **后端代码**：`include("uploads/" . $_GET['img'] . ".php");`
		
		例：
		![](Pasted%20image%2020260829165451.png)


3. ==利用的前提条件与限制==

%00 截断对运行环境有严格的要求，属于历史遗留问题：

| **条件项**    | **限制要求**                     | **说明**                                                          |
| ---------- | ---------------------------- | --------------------------------------------------------------- |
| **PHP 版本** | **< 5.3.4**                  | PHP 5.3.4 正式修复了文件系统函数中的空字符截断漏洞（CVE-2006-7243）。高版本会直接抛出警告并终止包含。  |
| **GPC 配置** | **`magic_quotes_gpc = Off`** | 如果开启了 `magic_quotes_gpc`，`%00` 会被自动转义为 `\0`（字面反斜杠加零），失去控制字符的作用。 |

### 使用多个`./`符号截断绕过限制进行进行文件包含执行RCE==(php<5.2.8)==
在 PHP 文件包含（LFI）漏洞利用中，当后端代码强制在用户可控参数后拼接固定后缀（如 `.php` 或 `.html`）且环境不支持 `%00` 截断时，**利用多个 `./` 进行路径长度截断（Path Length Truncation）** 是一种突破后缀限制并最终达成 RCE（远程代码执行）的经典技术

1. ==漏洞核心原理==

该绕过手法结合了**文件系统路径解析特性**与**操作系统的路径长度缓冲区限制**：

- **目录自引用特性（`./` 语义）**：
    
    在 POSIX（Linux）及 Windows 系统中，`.` 代表当前目录。因此，在文件或目录路径后追加任意数量的 `/./` 或 `./`，其逻辑指向都不会发生改变：
    
    $$\text{/var/www/uploads/shell.jpg} \equiv \text{/var/www/uploads/shell.jpg/./././.}$$

- **操作系统的最大路径长度限制**：
    
    底层文件系统在处理文件路径时，存在最大缓冲区长度限制：
    
    - **Linux / POSIX 系统**：`PATH_MAX` 通常为 **4096 字节**。
        
    - **Windows 系统**：`MAX_PATH` 通常为 **256 / 260 字节**。

- **截断机制**：
    
    当 PHP 拼接后的总路径长度超出底层缓冲区上限时，操作系统或 C 库函数会自动丢弃超出长度的多余字节。如果超出的部分恰好是后端拼接的 `.php` 等后缀，系统实际打开并包含的文件就是攻击者指定的文件本身


2. ==漏洞利用的前提条件==

| **条件项**    | **限制说明**                                                  |
| ---------- | --------------------------------------------------------- |
| **PHP 版本** | **PHP < 5.2.8**（PHP 5.2.8 修复了针对路径超长截断的漏洞 CVE-2008-5498）。  |
| **后端代码特征** | 存在文件包含点且强制拼接后缀，如 `include($path . ".php");`。              |
| **文件落地途径** | 目标服务器上存在可控内容的文件（如已上传的合法图片格式 Webshell、Session 文件、Web 日志等）。 |

## 有限制的远程文件包含(RFI)绕过

### 使用问号截断（Query String `?`）绕过限制进行RCE
**原理**：当 PHP 发送 HTTP/HTTPS 请求去获取远程文件时，==URL 中的 `?` 后面的内容会被远程 Web 服务器视作 **GET 请求参数**，而非请求的文件名本身。==

例：
![](Pasted%20image%2020260829181543.png)


1. ==问号截断的工作机制==

通过在传入的 URL 末尾附加 `?`，可以改变 URL 的解析结构：


例：
![](Pasted%20image%2020260829180434.png)


- **网络请求与解析：**
    
    - PHP 遇到 `http://` 协议流包装器时，会发起一个 HTTP GET 请求访问 `attacker.com`。
        
    - 根据 URI 标准（RFC 3986），`?` 后面的内容被识别为 **URL 查询参数**。
        
    - 攻击者的 Web 服务器接收到该请求后，实际读取并返回的文件路径为 `/shell.txt`，而 `?.php` 仅被视作无用的 GET 参数。

- **代码执行：**
    
    - 目标服务器获取到 `shell.txt` 的纯文本内容（如 `<?php phpinfo(); ?>`）。
        
    - `include` 函数将返回的内容直接作为 PHP 代码进行解析执行



### 使用`#或%23`符号绕过限制进行文件包含执行RCE
与问号截断（`?`）类似，该方法==利用了 **URI 标准规范（RFC 3986）对片段标识符（Fragment）的解析逻辑**==

1. ==核心原理解析==

在标准的 URI 结构中，==`#` 后面的内容被称为 **片段标识符（Fragment Identifier / Anchor）**==：

- 语法：
```
URI = scheme "://" host "/" path [ "?" query ] [ "#" fragment ]
```
- **客户端定位机制：** 片段标识符仅用于客户端（浏览器或协议客户端）==定位文档内的子资源或锚点位置。==

- **HTTP 请求行为：** 当网络客户端（包括 PHP 的 HTTP 流包装器）向==远程服务器发起 HTTP 请求时，**不会将 `#` 及其后的内容发送给远程 Web 服务器**，请求的物理路径仅为 `#` 之前的部分==

==(使用`%23`做URL编码转义)==

### 使用` `或`%20`符号空格绕过限制进行文件包含执行RCE
在 PHP 远程文件包含（RFI）中，==**空格截断（`%20` 绕过）** 是一种利用 **HTTP 协议请求行解析规则** 或 **操作系统文件名规范**，来绕过服务端代码对文件后缀强制拼接（如 `.php`、`.html`）的利用技巧==


1. ==核心原理：HTTP 请求行空格定界机制==

根据 HTTP 协议标准（RFC 2616 / RFC 7230），客户端与服务端交互的 **HTTP 请求行（Request-Line）** 格式规定使用 **空格（SP / ASCII 0x20）** 作为各字段的分隔符：

![](Pasted%20image%2020260829182217.png)


当 PHP 的 HTTP 流包装器（Stream Wrapper）发起远程请求时，如果 URL 中包含空格，且后端进行了字符串拼接，请求行会被重新切分：

![](Pasted%20image%2020260829182319.png)
很多 Web 服务器（或宽松模式下的 HTTP 服务）在解析请求行时，会将第一个空格后的内容识别为目标 URI（即 `/shell.txt`），而将第二个空格后的 `.php` 误识别为 HTTP 协议版本号或直接丢弃，从而依然向受害者返回 `/shell.txt` 的纯文本内容

3. ==补充场景：Windows 系统的尾随空格去除特性==

若漏洞场景涉及 **Windows 系统上的本地文件包含（LFI）** 或 **UNC/SMB 远程共享包含**：

- **Windows NTFS / Win32 API 规范：** ==Windows 文件系统会默认忽略并自动剥离文件名末尾的所有 **空格（ ）** 和 **点（`.`）**。==
    
- **利用方式：** 如果直接包含 `shell.php `（或 `shell.php...`），Windows 底层会自动将其规范化为 `shell.php` 进行读取
