
# PHP文件上传漏洞相关知识简介

## 补：文件上传的背后逻辑

### php文件上传基本流程
PHP文件上传的基本流程是==通过前端表单提交文件，由PHP后端接收并移动到服务器指定目录==

1. 前端表单设置

- 使用 `POST` 请求方法。
- 设置表单属性 `enctype="multipart/form-data"`，允许传输二进制文件。
- 添加 `<input type="file" name="file">` 选择文件。 [[1](https://www.php.net/manual/zh/features.file-upload.post-method.php), [2](https://developer.aliyun.com/article/726202)]

2. 后端接收与临时存储

- 文件发送到服务器后，会先保存在系统的临时目录中。
- PHP通过全局数组 `$_FILES['file']` 获取文件信息，如文件名、类型、大小和临时路径。
- 检查 `$_FILES['file']['error']` 确认文件是否正确上传。 [[1](https://www.runoob.com/php/php-file-upload.html), [2](https://www.cnblogs.com/Junglezt/p/16373815.html)]

3. 安全检查与验证

- **检查大小**：防止文件过大占用服务器空间。

- **检查类型**：验证文件扩展名或MIME类型，防止恶意脚本上传。 [[1](https://github.com/xidaner/Freed0m/blob/master/%E7%AC%94%E8%AE%B0/%E5%AE%89%E5%85%A8/Web%E6%B8%97%E9%80%8F/PHP%E6%96%87%E7%AB%A0/WEB-1-%E6%96%87%E4%BB%B6%E4%B8%8A%E4%BC%A0%E5%B0%8F%E8%8A%82/readme.md)]

4. 移动文件到目标目录

- 使用 `move_uploaded_file()` 函数将临时文件移动到服务器的永久存储位置。
- 建议对上传的文件进行**重命名**（如使用时间戳加随机数），避免文件名冲突或覆盖




- PHP文件上传的流程
	- `Step1`：前端选择文件并提交
	- `Step2`：文件被使用HTTP协议以`form-data`的格式发送
	- `Step3`：服务端将文件解析为`$_FILES`
	- `Step4`：业务逻辑对`$_FILES`进行处理

### 文件上传的form-data报文详解

- 文件上传的form-data报文详解
文件上传的 `multipart/form-data` 报文是==一种用于在 HTTP 请求中传输二进制文件和文本键值对的编码方式==

核心结构特点

- **请求头（Header）**：`Content-Type` 必须指定为 `multipart/form-data`，并包含一个随机生成的 `boundary`（边界字符串）用于分割不同的表单项。
- **多部分结构（Body）**：整个报文体被 `boundary` 分割成多个独立的部分（Part），每一部分包含自己的 `Content-Disposition`、可选的 `Content-Type` 和具体数据。
- **结尾标识**：报文体的最后以 `boundary` 加上 `--` 结束（即 `--boundary--`）

![](Pasted%20image%2020260827163412.png)

各字段详细说明

- **`boundary`**：分割线，用于区分不同的表单字段。它必须足够独特，确保不会在正文数据中意外重复。
- **`Content-Disposition`**：指定当前部分的元数据类型，固定为 `form-data`，并附带 `name`（表单字段名）。如果是文件，还会附带 `filename`（原始文件名）。
- **`Content-Type`**：声明具体部分的媒体类型（MIME Type）。普通文本通常省略，而文件部分通常会写明具体类型（如 `image/jpeg`、`application/pdf` 等），以便服务器正确识别。 [[1](https://juejin.cn/post/7293122700658049075)]


![](7a713a7081c2695ae6c4720ffe643b5f.jpeg)

`Content-Type`:必须为 `multipart/form-data`
`boundary`：用来分节文件内容
注意“`-`”的长度


### `$_FILES`数组介绍
`$_FILES` 是一个超全局变量，==专门用于处理通过 HTTP POST 方法上传的文件==

==当用户提交一个包含 `<form enctype="multipart/form-data">` 的表单时，PHP 会自动将上传的文件信息填充到 `$_FILES` 数组中==


1. 核心结构

假设表单中文件输入框的 `name` 属性为 `my_file`（即 `<input type="file" name="my_file">`），那么 `$_FILES['my_file']` 将是一个包含以下 5 个键值的关联数组：

- **`$_FILES['my_file']['name']`**：客户端文件的原始名称（例如：`photo.jpg`）。
- **`$_FILES['my_file']['type']`**：文件的 MIME 类型（例如：`image/jpeg`）。该值由浏览器提供，不够安全。
- **`$_FILES['my_file']['tmp_name']`**：文件上传后在服务器上存储的临时路径。
- **`$_FILES['my_file']['error']`**：文件上传过程中的错误代码（整型）。
- **`$_FILES['my_file']['size']`**：上传文件的大小，单位为字节（Bytes）

2. 错误代码说明（`['error']`）

通过检查 `$_FILES['my_file']['error']` 的值，可以判断文件是否上传成功：

- **`0` (UPLOAD_ERR_OK)**：上传成功。
- **`1` (UPLOAD_ERR_INI_SIZE)**：文件大小超过了 `php.ini` 中 `upload_max_filesize` 的限制。
- **`2` (UPLOAD_ERR_FORM_SIZE)**：文件大小超过了 HTML 表单中 `MAX_FILE_SIZE` 选项的限制。
- **`3` (UPLOAD_ERR_PARTIAL)**：文件只有部分被上传。
- **`4` (UPLOAD_ERR_NO_FILE)**：没有文件被上传。
- **`6` (UPLOAD_ERR_NO_TMP_DIR)**：找不到临时文件夹。
- **`7` (UPLOAD_ERR_CANT_WRITE)**：文件写入失败

==(注：遍历多文件时，需要通过下标（如 `$_FILES['photos']['name'][$i]`）来获取每个文件对应的信息)==

### Webshell简介
**Webshell** 是==一种以网页脚本文件（如 PHP、ASP、JSP 等）形式存在的代码执行环境和远程控制后门==

==基本概念==

- **Web**：指服务器需要开放 Web 服务（通过 80、443 等网页端口通信）。
- **Shell**：指取得对服务器某种程度的操作权限。
- **本质**：黑客利用网站漏洞（如 SQL 注入、文件上传等）将恶意脚本上传并混入正常的网站目录中，随后通过浏览器或专用客户端进行远程控制

==常见分类==

- **一句话木马**：代码极其短小但功能强大，隐蔽性极高。它只包含接收并执行参数的核心代码，常配合专用客户端（如中国菜刀、蚁剑）使用。
- **小马**：体积非常小。主要用于突破网站上传限制，作为跳板去下载或上传功能更全的“大马”。
- **大马**：体积较大、功能齐全。自带登录密码，通常包含文件管理、数据库管理、信息收集甚至系统提权等模块


==主要特点==

- **隐蔽性强**：文件名和代码常经过混淆或伪装，和正常网页混在一起，很难被轻易发现。
- **流量伪装**：通过标准的 Web 端口（如 80 端口）进出流量，容易绕过防火墙的常规拦截。
- **功能多样**：支持查看修改文件、操作数据库、执行系统命令等


==防御与检测==

- **严格鉴权**：限制后台文件上传功能，检查并修补系统漏洞。
- **安全扫描**：使用安全防护软件（如 [阿里云安全](https://help.aliyun.com/zh/document_detail/60859.html) 提供的防护建议、D盾或安全狗等工具）定期对 Web 目录进行特征码和行为扫描

## 文件上传漏洞介绍
**文件上传漏洞（File Upload Vulnerability）** 是指 Web 应用程序允许用户上传文件，但未对文件的后缀、类型、内容或存储与执行权限进行严格验证与过滤，==导致攻击者能够上传恶意脚本（如 PHP、JSP、ASP 等 Webshell）并获取服务器控制权的高危安全漏洞==

**核心危害**

- **远程代码执行（RCE）：** 攻击者直接执行系统命令，完全控制目标服务器。
- **数据泄露与篡改：** 读取数据库凭据、核心源码，或篡改网站页面。
- **内网渗透：** 以被攻陷的服务器为跳板，横向移动探测内网其他资产。
- **钓鱼与恶意软件分发：** 上传包含恶意病毒的伪装文件供他人下载

**常见成因与绕过手法**

- **前端 JavaScript 校验缺陷：** 仅在浏览器端拦截非法后缀。攻击者可直接禁用 JS 或使用抓包工具（如 Burp Suite）修改数据包绕过。

- **MIME-Type / Content-Type 伪造：** 后端仅校验请求头中的 `Content-Type`（如 `image/png`），攻击者可将恶意脚本的请求头直接伪造为合法类型。

- **黑名单过滤不严：**
    
    - **特殊后缀绕过：** 过滤了 `.php`，但未过滤 `.php5`、`.phtml`、`.jspx` 等。
    - **操作系统特性：** Windows 系统下利用末尾空格、点（`.`）或 `::$DATA` 绕过校验并被系统自动还原。
    - **大小写混淆：** 如 `.pHP`、`.AsP`。
        
- **文件头伪造与图片马：** 后端仅校验文件头字节（Magic Number）。攻击者在图片末尾拼接 Webshell 代码（制作“图片马”），或在脚本头部添加 `GIF89a` 伪造文件头。

- **Web 容器解析漏洞与配置文件覆盖：**
    
    - 上传自定义 `.htaccess` 或 `.user.ini` 改变目录解析规则。
    - Nginx / IIS / Apache 历史解析漏洞（如 `test.jpg/test.php` 或 `test.asp;.jpg`）。

- **条件竞争（Race Condition）：** 后端采用“先保存到临时目录，再进行安全校验与删除”的逻辑，攻击者通过多线程高频请求在文件被删除前触发执行


**防御与加固方案**

- **严格白名单限制：** 仅允许特定业务所需的扩展名（如 `.jpg`, `.png`, `.pdf`），坚决不使用黑名单。

- **重命名与路径隐藏：** 服务端强制对上传文件进行随机重命名（如 UUID 或时间戳哈希），并打乱存储路径，防止直接猜测 URL。

- **关闭执行权限：** 将上传目录设置为只读/不可执行（如 Nginx 配置禁止执行特定脚本，或挂载为 `noexec` 分区）。

- **存储分离与对象存储：** 将用户上传的文件托管至独立的文件服务器、CDN 或云端对象存储（如 AWS S3、阿里云 OSS），隔离 Web 核心服务。

- **内容深度二次渲染：** 对图片文件使用图像库（如 GD、ImageMagick）进行二次重绘压缩，彻底清除嵌入的恶意代码。

- **综合内容与后缀检测：** 结合后缀白名单、MIME-Type 校验和文件头 Magic Number 检测，避免单一维度的验证缺失

# 文件上传漏洞防御


## 核心防御方式：限制文件类型

### 利用前端JS限制文件后缀防御文件上传漏洞
**前端 JavaScript 限制文件后缀**主要用于提升用户体验，在客户端提前拦截不符合要求的格式以减少无效网络请求。==但必须明确：**前端校验运行在用户本地，无法作为独立的网络安全防线，攻击者可轻易绕过**==

==**前端 JS 常见实现方式**：==

**HTML 原生 `accept` 属性限制：** 在文件上传控件中指定允许的文件后缀或 MIME 类型，浏览器在弹出文件选择窗口时会自动过滤文件类型

**监听 `change` 事件提取后缀比对：** 用户选择文件后，通过 JS 解析文件名、提取后缀并与预设白名单比对

**表单 `submit` 提交前拦截：** 在表单提交事件中进行统一拦截校验，防止通过拖拽或非标准方式灌入文件

==**前端校验的典型绕过手法**==

因为前端代码对客户端完全透明且可控，攻击者通常采用以下手段完全无视前端限制：

- **抓包修改扩展名（Burp Suite / Fiddler）：** 攻击者先选择合法的 `.jpg` 文件通过前端校验，在请求发往服务端的中途截获数据包，将文件名修改为 `shell.php` 或恶意脚本名称后放行。

- **浏览器 DevTools 动态篡改：** 直接打开开发者工具（F12），在 Console 中修改/覆盖验证函数（如 `checkFile = () => true`），或在 Elements 面板中删除 `<input>` 上的 `accept` 属性及 `onchange` 事件。

- **禁用浏览器 JavaScript：** 在浏览器设置中直接关闭 JavaScript 执行，前端所有脚本校验立即失效。

- **直接构造原始 HTTP 请求：** 绕过浏览器界面，使用 `curl`、Postman 或 Python 脚本直接向后端上传接口发送带有恶意脚本的 `multipart/form-data` 请求

==**安全定位与最佳实践**==

前端验证的价值仅在于**交互优化与降低服务器非恶意负载**。针对文件上传漏洞的实质防护，必须严格落地在**服务端（Backend）**：

- **前端职责：** 提供即时错误提示（如大小限制、格式提醒），提升合法用户操作流畅度。
    
- **后端绝对防御：**
    
    - 强制采用服务端**后缀白名单**。
        
    - 服务端对文件进行**随机重命名（如 UUID）**，消除任何特殊后缀、空字节或大小写绕过空间。
        
    - 存储在**无执行权限**的目录或独立的云存储（如 OSS/S3）中

### 利用服务端MIME类型检测防御文件上传漏洞
**服务端 MIME 类型（Multipurpose Internet Mail Extensions）检测**是通过==识别文件的媒体类型元数据或真实底层二进制特征，限制仅允许合法格式（如 `image/png`、`application/pdf`）上传的安全机制==

==**核心误区：HTTP 标头伪造**==

许多开发者误将客户端上传请求头中的 ==`Content-Type` 当作 MIME 检测依据==（如 PHP 中的 `$_FILES['file']['type']`）。该字段完全由客户端控制，攻击者可使用抓包工具（如 Burp Suite）将恶意文件的类型任意修改为合法值


==**真实 MIME 检测方案（基于文件内容与魔数）**==

可靠的服务端 MIME 检测必须**基于文件内容的真实二进制特征（Magic Bytes / File Signatures）**，由服务器主动读取并分析，而非信任请求报文中的声明


==**局限性与常见绕过手法**==

单纯依赖 MIME 检测仍存在安全盲区：

- **图片马（Polyglot 文件）：** 攻击者在脚本头部手动添加合法文件魔数（例如在 PHP 文件开头添加 `GIF89a`），或使用 `copy /b 1.jpg + shell.php 2.jpg` 将恶意代码拼接在合法图片后。MIME 检测工具可能会将其识别为合法图片。

- **解析配置缺陷：** 当上传伪装成图片的恶意文件（如 `shell.php.gif` 或图片马）后，如果服务器存在解析漏洞（如 Apache 多后缀解析、Nginx CGI 路径解析漏洞）或本地文件包含（LFI），恶意代码依然会被解释执行。
    

==**纵深防御最佳实践**==

MIME 检测应作为安全防线的一环，与以下措施协同使用：

- **后缀与 MIME 双白名单：** 同时严格校验文件名后缀（强制小写匹配）与底层内容 MIME 类型，两者必须一致且均在白名单内。

- **服务端强制重命名：** 上传后生成随机文件名（如 UUID），丢弃原始扩展名，避免利用解析特性绕过。

- **图像二次渲染：** 使用图像处理库（如 GD、Pillow、ImageMagick）对图片进行重绘压缩，抹除隐藏在 EXIF 元数据或文件尾部的 Webshell 代码。

- **隔离存储与禁止执行：** 将文件存储至无脚本执行权限的目录，或直接托管至独立的云对象存储（OSS/S3）

### 利用服务端限制后缀名防御文件上传漏洞
**服务端限制文件后缀名**是通过后端代码==对上传文件的扩展名进行提取、清洗与比对，阻止未经允许的脚本或可执行文件落盘的核心防御机制==。在实际落地中，==防御效果完全取决于采用的是**黑名单**还是**严格白名单**策略==

==**黑名单机制的缺陷与常见绕过**==

==黑名单是指明确禁止某些高危扩展名（如 `.php`, `.asp`, `.jsp`, `.exe`）==，放行其余所有后缀。这种策略极易因覆盖不全或环境解析差异而被绕过：

- **替代/特殊后缀绕过：**
    
    - **PHP 环境：** 开发者封禁了 `.php`，但未封禁 `.php3`、`.php5`、`.phtml`、`.pht`、`.phps` 等。
        
    - **ASP/ASP.NET 环境：** 绕过 `.asp` 使用 `.asa`、`.cer`、`.cdx`、`.ashx`、`.asmx`、`.soap`。
        
    - **JSP 环境：** 绕过 `.jsp` 使用 `.jspx`、`.jspa`、`.jsw`、`.jsf`。

- **大小写混淆：** 在 Windows 服务器或不区分大小写的 Web 容器中，上传 `.pHp`、`.AsP` 或 `.Jsp`。若后端未对提取的后缀进行统一下转小写（`toLowerCase()`），黑名单将被直接击穿。

- **操作系统特性（Windows）：**
    
    - **末尾点和空格：** 上传 `shell.php.` 或 `shell.php` ，后端未正确去除末尾符号导致绕过黑名单，而 Windows 文件系统在保存时会自动截断末尾的点与空格，最终还原为 `shell.php`。
        
    - **NTFS 文件流特性：** 上传 `shell.php::$DATA`，黑名单识别为非常规后缀而放行，Windows 在存储时会将其视为默认数据流，实际在磁盘生成 `shell.php`。

- **Web 配置文件覆盖：** 若黑名单未限制 `.htaccess`（Apache）或 `.user.ini`（Nginx/PHP-FPM），攻击者可上传自定义配置文件，将原本无害的图片后缀（如 `.png`）重写解析为 PHP 脚本执行。

#### 文件后缀双写绕过
**后缀双写绕过**（Double-writing Bypass）是文件上传漏洞中针对**黑名单过滤机制**的一种利用手段。当服务端试图通过“将恶意后缀替换为空”的方式来过滤危险文件，但替换逻辑仅执行了一次（非递归替换）时，就会产生此类绕过

==漏洞成因与核心原理==

该漏洞的根本原因在于服务端的字符串替换逻辑存在缺陷：

1. **黑名单过滤与清空逻辑**：后端维护了一个危险扩展名黑名单（如 `.php`、`.asp`、`.jsp` 等）。
    
2. **单次非递归替换**：当代码检测到文件名中包含黑名单字符时，直接调用字符串替换函数（如 PHP 中的 `str_ireplace` 或 `str_replace`）将其**替换为空字符 `""`**。
    
3. **闭合拼接**：如果将一个危险关键词拆分，并将其嵌套在另一个相同的关键词中间（例如 `pphphp`），过滤函数在移除了中间匹配到的子字符串后，两端的残余字符会自动向内靠拢，重新拼凑成一个完整的危险扩展名
- **多后缀与 Web 容器解析漏洞：** 上传 `shell.php.jpg`，部分旧版 Apache 存在从右向左解析未知后缀的特性，若服务器未识别 `.jpg` 会继续向前解析为 PHP 执行。










==**白名单机制的标准实现**==

白名单是**唯一推荐**的安全设计原则：明确定义业务必须允许的极少数安全格式（如 `.png`, `.jpg`, `.pdf`），拒绝其余一切输入。

- **安全提取与匹配核心逻辑：**
    
    1. 准确提取文件名中**最后一个 `.` 之后**的字符。
        
    2. 去除前后空格、控制字符及特殊符号。
        
    3. 统一转换为纯小写格式。
        
    4. 使用**严格全等比对（In-Array / Set Lookup）**，禁止使用模糊正则或子字符串包含判断


==**后缀校验的常见逻辑陷阱**==

- **直接使用字符串截取首个 `.`：** 例如对 `shell.php.jpg` 使用 `split('.')[1]`，提取到的扩展名为 `php` 而非 `jpg`，导致逻辑错乱或被攻击者利用多后缀绕过。

- **使用字符串包含判断代替全匹配：** 如使用 `filename.contains(".png")`，攻击者构造 `shell.png.php` 即可直接绕过。

- **空字节截断（00 截断）：** 历史漏洞形态（如 PHP 5.3.4 之前或 C 语言编写的文件处理模块）。攻击者提交 `shell.php\x00.jpg`，应用层判断后缀为 `.jpg`，底层文件 API 遇到 `0x00` 终止读取，最终生成 `shell.php`

==**纵深防御加固建议**==

单靠后缀名校验无法防御“图片马结合文件包含漏洞”或解析漏洞，需配合以下关键措施：

- **服务端强制随机重命名：** 绝对不要直接使用客户端提供的原始文件名保存。生成随机 UUID/Hash 并拼接通过白名单校验的后缀，彻底消解所有特殊字符、路径穿越（`../`）及多后缀风险。

- **多维度交叉验证：** 将后缀名白名单与真实内容 MIME/Magic Number 校验相结合。

- **存储与权限隔离：** 存储目录彻底关闭脚本执行权限，或直接将静态资源分发到无后端解析环境的独立对象存储（如 OSS / S3）

## 内容检测

### 利用脚本特征检测防御文件上传漏洞
内容检测（脚本特征/关键字检测）是指==后端在接收到上传文件后，读取文件的原始字节流或文本内容，通过正则匹配、特征签名或关键字黑名单，检查其中是否包含恶意的脚本起始标签、危险系统函数或可执行代码片段==

==**常见的检测目标特征**==

后端内容检测通常通过扫描以下特征来判断是否为恶意脚本：

- **脚本起始与声明标签：**
    
    - **PHP：** `<?php`, `<?=`, `<?`, `<script language="php">`
        
    - **JSP：** `<%`, `<%=`, `<%@ page`, `<jsp:scriptlet>`
        
    - **ASP/ASP.NET：** `<%`, `<script runat="server">`
        
    - **HTML/XSS：** `<script>`, `<iframe>`, `onload=`, `javascript:`

- **高危命令执行与代码执行函数：**
    
    - **PHP：** `eval()`, `assert()`, `system()`, `exec()`, `shell_exec()`, `passthru()`, `popen()`, `proc_open()`, `preg_replace('/.*/e', ...)`
        
    - **Java：** `Runtime.getRuntime().exec()`, `ProcessBuilder`, `Unsafe`, 反射调用（`Method.invoke`）
        
    - **ASP/.NET：** `eval()`, `Execute()`, `ExecuteGlobal()`, `Process.Start`

- **常见混淆与载荷传递特征：**
    
    - `base64_decode`, `gzinflate`, `str_rot13`, `create_function`
        
    - 全局输入变量接收：`$_POST`, `$_GET`, `$_REQUEST`, `$_COOKIE`


==**常见的绕过与混淆手法**==

脚本特征检测本质上是**基于黑名单的文本匹配**，攻击者可以通过语法多样性与代码混淆轻松绕过：

- **替代标签与大小写混淆：**
    
    - 使用短标签 `<?=` 代替 `<?php`（在开启 `short_open_tag` 时直接执行）。
        
    - 大小写交替：`sYsTeM()`, `<sCrIpt language="pHp">`。

- **字符串拼接与动态函数调用：**
    
    - 绕过关键字匹配，利用变量动态构造函数名
    - 利用数组或字符 ASCII 偏移构造
    - **反引号执行命令：**
		- 在 PHP 中直接使用反引号代替 `system()`
	- **无字母数字 Webshell（Non-Alpha Webshell）：**
	    - 仅利用异或（`^`）、取反（`~`）或自增（`++`）等符号在内存中运算出目标函数名与参数，文件中完全不出现任何英文字母或关键词。
	- **编码与压缩封装：**
	    - 将恶意代码进行 Base64 编码或 Gzip 压缩后嵌入图片特定数据段（如 EXIF 元数据或 PNG IDAT 块），文件表面不含任何明文敏感特征


==**内容特征检测的固有缺陷**==

- **误报率高（False Positives）：** 正常的二进制文件（如 JPEG 压缩表、编译后的 PDF、字体文件）中，随机字节序列经常会巧合出现类似于 `eval`、`system` 或 `<?` 的 ASCII 字符，导致合法业务文件被误拦截。
    
- **维护成本极高：** 编程语言语法特性灵活多变，静态关键字黑名单无法穷举所有混淆与构造变体


==**最佳防护与替代方案**==

内容检测不应作为核心防线，在实际工程中应配合更底层的结构性治理：

- **图像文件二次渲染（最有效的内容清理）：** 对用户上传的图片调用图像处理库（如 GD、ImageMagick、Pillow）进行重采样与重建输出。二次渲染会重构图片像素数据并丢弃非法数据块，彻底破坏隐藏在图片中的 Webshell 代码。

- **集成专业杀毒引擎与 YARA 规则：** 如需对文档（PDF、Office）或压缩包做深度检测，应调用专业的反病毒引擎（如 ClamAV）或编写多维度的 YARA 规则，而非简单的正则字符串匹配。

- **抽象语法树（AST）静态分析：** 针对需要允许上传代码/脚本的特定场景，利用 AST 语法解析器分析调用链行为，而非依赖文本子串比对。

- **存储隔离与禁执行兜底：** 强制将上传文件存入独立对象存储（如 OSS/S3），并在 Web 容器层彻底关闭上传目录的脚本解析与执行权限（`noexec`）

### 利用文件头检测防御文件上传漏洞
文件头检测（Magic Number / File Signature 检测）是指服务端在接收上传文件时，==通过读取文件最开始的若干字节（即“文件魔数”）==，比对其底层二进制签名是否符合合法文件类型的特征，从而判断文件真实格式的防御手段

与容易被客户端伪造的 `Content-Type` 和文件名后缀相比，文件头直接从服务端读取的文件流中获取，提供了更底层的校验依据

**常见文件类型的文件头魔数对照**

| **文件格式**                 | **十六进制特征码 (Magic Bytes)**                 | **ASCII / 文本特征** |
| ------------------------ | ----------------------------------------- | ---------------- |
| **JPEG / JPG**           | `FF D8 FF`                                | ÿØÿ              |
| **PNG**                  | `89 50 4E 47 0D 0A 1A 0A`                 | .PNG....         |
| **GIF89a / GIF87a**      | `47 49 46 38 39 61` / `47 49 46 38 37 61` | GIF89a / GIF87a  |
| **PDF**                  | `25 50 44 46`                             | %PDF             |
| **ZIP / DOCX / XLSX**    | `50 4B 03 04`                             | PK..             |
| **Windows PE (EXE/DLL)** | `4D 5A`                                   | MZ               |
……


==**文件头检测的常见绕过手法**==

文件头检测仅检查文件最前部的 2～8 个字节，并不对后续的文件体进行安全分析，因此极易被以下手法绕过：

- **直接伪造头部字符串：** 在恶意 PHP 脚本最开头直接插入合法的头部字符（如 `GIF89a`），欺骗 `exif_imagetype` 或简单字节比对

- **制作图片马（Polyglot 文件）：** 将合法的图片与恶意脚本进行二进制拼接，保留完整合法的图片文件头与像素结构

- **元数据 / EXIF 属性注入：** 利用图片编辑工具或 EXIF 库，将 Webshell 写入图片的元数据字段（如 `Artist`、`Copyright` 或 `UserComment`）。文件头部与整体结构完全合法，但内部包含恶意载荷。

- **配合解析漏洞与文件包含（LFI）：** 即便生成的文件拥有合法的图片头和图片后缀，若服务器存在**本地文件包含漏洞**（`include('uploaded/webshell.jpg')`）或 Web 容器解析漏洞（如 Nginx CGI 配置漏洞 `webshell.jpg/.php`），恶意代码依然会被强制解释执行


==**纵深防御最佳实践**==

文件头检测只能用于**格式合法性初筛**，必须配合以下综合防御方案：

- **强制二次渲染（破坏图片马）：** 使用图像处理库（如 Python Pillow、PHP GD / ImageMagick）对上传的图片进行重绘与压缩保存。二次渲染会重新编码像素点并丢弃所有非标准数据块与注释，彻底清除嵌入的恶意脚本。

- **扩展名白名单 + 强制随机重命名：** 丢弃原始文件名，统一使用 `UUID` + 白名单后缀保存，阻止多后缀解析与文件名注入。

- **上传目录隔离与禁执行：** 将上传文件存储到独立的静态资源服务器或云对象存储（如 AWS S3、阿里云 OSS），并在 Web 容器配置中彻底关闭该目录的脚本解析权限（如禁止解析 `.php`, `.jsp`, `.asp`）
