# 文件上传漏洞防御绕过技巧

## 前端绕过JS检测
**前端 JavaScript 检测**（Client-Side Validation）是指浏览器在将文件发送至服务器之前，利用运行在本地的 JS 脚本对上传文件的后缀名、大小或 MIME 类型进行校验。

由于**客户端的所有环境与代码均处于用户（攻击者）的完全控制之下**，任何仅依赖前端的防护机制都无法真正阻断恶意请求

==前端 JS 校验的几种常见绕过技巧==

1. ==抓包改包法（最常用、最稳定）==

前端校验只发生在浏览器发送请求之前。只要让合规文件通过前端检测，在数据离开浏览器之后拦截并修改其内容与文件名即可。

- **步骤**：
    
    1. 将木马/测试脚本（如 `shell.php`）先重命名为白名单后缀（如 `shell.jpg`）。
    2. 开启代理工具（如 Burp Suite）并开启拦截（Intercept on）。
    3. 在浏览器中选择 `shell.jpg` 点击上传，此时前端 JS 校验通过。
    4. 在 Burp Suite 拦截到的 HTTP 请求体中，将 `filename="shell.jpg"` 修改回 `filename="shell.php"`。
    5. 放行（Forward）请求包至后端服务器

2. ==禁用浏览器 JavaScript==

前端检测脚本依赖浏览器的 JS 引擎执行，直接在浏览器中禁用 JS 即可跳过所有前端逻辑。

- **Chrome / Edge 操作**：
    
    1. 按 `F12` 打开开发者工具，按 `F1` 或点击右上角齿轮进入 **Settings**。
    2. 找到 **Debugger** 模块，勾选 **Disable JavaScript**。
    3. 直接在网页上选择 `.php` 或恶意文件点击上传。

- **快捷插件**：使用如 `Quick JavaScript Switcher` 等浏览器插件一键开关 JS

## 服务端绕过MIME类型检测

### 补：MIME类型简介
MIME 类型（多用途互联网邮件扩展，Multipurpose Internet Mail Extensions）是==一种标准，用来表示文档、文件或字节流的性质和格式==

==基本介绍==

- **作用**：它像数据的“身份证”，告诉浏览器或邮件客户端如何打开和处理该文件。
- **发展**：它最初用来扩展电子邮件，让邮件支持非 ASCII 字符、图像和音频；现在它也被广泛用于 HTTP 协议 中，用来定义服务器传送的网页内容类型

==结构格式==

MIME 类型由**类型**和**子类型**组成，中间用斜杠 `/` 分隔：

> `type/subtype`

- **不区分大小写**，但通常写成小写。
- 后面可以附加参数（例如 `charset=utf-8` 表示字符编码）

==常见类型==

- **`text/plain`**：纯文本文件。
- **`text/html`**：HTML 网页文件。
- **`image/jpeg`**：JPEG 格式的图片。
- **`application/json`**：JSON 格式的数据。
- **`application/octet-stream`**：未知的二进制文件，通常会让浏览器触发下载

### 改尾缀名和改文件内容绕过服务端MIME类型检测

1. ==抓包修改 Content-Type（最直接手段）==

如果服务端只校验 `$_FILES['file']['type']`，而没有校验文件扩展名或重命名文件，只需在请求发送过程中将 MIME 类型改为允许的白名单类型即可。

- **操作步骤**：
    
    1. 准备恶意脚本（例如 `webshell.php`）。

    5. 将 `Content-Type: application/octet-stream` 或 `application/x-php` 替换为合法类型，例如 `image/jpeg` 或 `image/png`。
        
    6. 放行（Forward）数据包

## 服务端绕过后缀名检测
攻击者绕过后缀名检测的核心原理在于：==**利用服务端验证逻辑的缺陷、操作系统的底层文件系统特性，或是 Web 容器（如 Apache、Nginx、IIS）对文件解析规则的认知差异**==

### 补：.htaccess文件简介
`.htaccess` ==是 Apache 网页服务器中的一个**分布式配置文件**，它用来决定服务器该如何向访问者提供特定目录下的文件==

==核心作用==

- **URL 重写**：隐藏后缀或实现伪静态（如把 `index.php?id=1` 变成 `article/1`）。
- **网页重定向**：设置 301 永久重定向或 302 临时重定向。
- **自定义错误页面**：为 404、500 等错误状态码指定专用的提示页面。
- **访问权限控制**：通过 IP 地址或密码来限制某些目录的访问。
- **防盗链与 MIME 类型配置**：防止其他网站直接引用你的图片资源

==工作特点==

- **目录级别生效**：把它放在哪个文件夹里，它就只对这个文件夹以及底下的所有子文件夹起作用。
- **即时生效**：修改后保存就能直接用，不需要重启 Apache 服务器。
- **纯文本格式**：可以用任何文本编辑器（如 Notepad++、VS Code）直接打开和修改




- htaccess文件讲解
	- htaccess文件（或者”分布式配置文件”）提供了针对目录改变配置的方法
		- 该目录是否允许被用户访问
		- 允许当做PHP代码执行的文件尾缀
	- 作用于此目录及其所有子目录

### 黑名单检测绕过（Blacklist Bypass）
黑名单机制是指服务端列举出禁止上传的后缀名（如 `.php`, `.asp`, `.jsp`, `.exe` 等），==只要后缀在列表中即拦截。由于很难穷举所有可执行扩展名和环境特性，黑名单在实战中最易被攻破==

1. ==特殊可执行后缀（别名扩展名）==

许多 Web 容器默认支持多种扩展名来触发脚本解释器：

| **语言环境**          | **常见被封禁后缀**    | **可尝试的替代执行后缀**                                          |
| ----------------- | -------------- | ------------------------------------------------------- |
| **PHP**           | `.php`         | `.php3`、`.php4`、`.php5`、`.phtml`、`.pht`、`.phps`、`.php7` |
| **ASP / ASP.NET** | `.asp`、`.aspx` | `.cer`、`.asa`、`.cdx`、`.ashx`、`.asmx`、`.asax`、`.soap`    |
| **JSP**           | `.jsp`         | `.jspx`、`.jspf`、`.jsps`、`.jsw`                          |
……

> [!NOTE]
> ==**生效前提**：目标中间件（如 Apache `httpd.conf` 或 IIS `mime.types`）配置了将这些后缀映射至对应的脚本解析器。==


2. ==大小写混淆（Case Insensitivity）==

如果服务端代码在校验黑名单时**未将后缀名统一转为小写**（如未调用 `strtolower()`），但在 Windows 或部分未对大小写敏感配置的 Linux 容器中执行，可通过混合大小写绕过

3. ==Windows 文件系统末尾特殊字符特性==

Windows 文件系统（NTFS / FAT）==在保存文件时，会自动剥离文件名末尾的**空格**和**句号（点）**，且支持数据流特性。若服务端在校验后缀时未做严格去除，利用此特性可使黑名单匹配失败，但最终仍以目标脚本落地==。

- **末尾加点（`.`）**：`shell.php.`（黑名单判断后缀为 `php.`，校验通过；Windows 落地保存为 `shell.php`）

- **末尾加空格（ ）**：`shell.php ` （黑名单判断后缀为 `php` ；Windows 自动去除末尾空格保存为 `shell.php`）

- **点+空格+点混合**：`shell.php. .`（针对仅执行了一次去除末尾点或空格的防御逻辑）

- **NTFS 备用数据流（`::$DATA`）**：
    
    - 在 Windows 下，`shell.php::$DATA` 会被系统识别为向 `shell.php` 文件的默认数据流写入内容。
        
    - 后端提取的后缀为 `php::$DATA` 从而绕过黑名单，但系统最终在磁盘上生成的正是 `shell.php`



4. ==双写 / 过滤不彻底绕过==

## 利用php设计缺陷绕过

### 补：php `move_upload_file`函数介绍
PHP 的 `move_uploaded_file` 函数==用于将通过 HTTP POST 上传的临时文件移动到服务器上的指定永久位置==

- 语法：
```
move_uploaded_file ( <$from> , <$to> )
```
- **`$from`**：上传文件的原始临时文件名（通常是 `$_FILES['<file>']['<tmp_name>']`）。
- **`$to`**：文件移动后的目标新位置路径。
- **返回值**：成功时返回 `true`，失败时返回 `false`

==注意事项==

- **目录必须存在**：目标目录必须提前存在，`move_uploaded_file` 不会自动帮你创建缺失的文件夹。
- **权限问题**：运行 PHP 的Web服务器用户（如 `www-data`）必须对目标文件夹具有写入权限。
- **覆盖机制**：如果 `$to` 目标路径下已经存在同名文件，原文件将会被直接覆盖



### 利用`move_upload_file`函数空字符截断缺陷进行文件上传==(php<5.3.4)(CVE-201502348)==
在 PHP 开发与安全测试中，`move_uploaded_file` 函数的**空字符截断漏洞**（通常称为 `%00` 截断或 Null Byte Injection）是一种经典的文件上传绕过手段


1. ==核心漏洞原理==

PHP 底层是由 C 语言实现的。在 C 语言中，字符串以 ASCII 码为 `0x00`（即 `\0`，空字符 / NUL）作为字符串的结束标志。

当 PHP 将包含 `\0` 的路径字符串传递给底层的系统调用（如 C 语言的 `fopen`、`rename` 等）时，系统读取到 `\0` 便认为字符串已经结束，从而**忽略 `\0` 之后的所有字符**。

若目标代码中文件的保存路径（目标路径参数 `$destination`）由用户可控变量与白名单后缀拼接而成，攻击者可以在路径中插入空字符，使底层文件系统在保存时提前截断，从而生成攻击者指定后缀的脚本文件（如 `.php`）


2. ==触发前提条件==

该漏洞通常需要同时满足以下条件：

1. **PHP 版本限制**：==PHP 版本低于 **5.3.4**==（从 PHP 5.3.4 开始，官方在底层对文件系统函数的路径参数增加了空字符检查，遇到 `\0` 直接返回失败）。

2. **魔术引号配置**：`magic_quotes_gpc = Off`（若开启，用户输入的 `\0` 或 `%00` 会被自动转义为 `\0` 字符串字面量，导致截断失效）。

3. **路径可控拼接**：后端的存储路径（`$save_path` 或 `$destination`）允许外部参数注入并参与最终路径的拼接

### 利用`move_upload_file`函数忽略结尾`/.`缺陷进行文件上传
在 PHP 文件上传漏洞中，利用 `move_uploaded_file` 函数**忽略末尾 `/.`**（以及 `/.` 路径规范化特性）进行绕过，是一种利用**业务层文件名校验逻辑与底层文件保存函数解析差异**的高级绕过技巧

1. ==核心漏洞原理==

该漏洞的本质是 **“检查层与执行层的解析分歧”**：

1. **业务逻辑层检测偏差**： 开发者在对上传文件的后缀进行黑白名单校验时，通常会使用 `pathinfo()`、字符串截取、或者将文件名通过 `explode('.', $filename)` 拆分为数组来获取后缀。当文件名末尾为 `/.` 时，业务层的后缀提取逻辑会被干扰（例如获取到的后缀为空、或者为 `.`，从而成功绕过 `.php` 等黑名单）。
    
2. **底层 `move_uploaded_file` 的路径规整化**： 在 Linux / Windows 系统及 PHP 底层文件系统调用中，路径末尾的 `/.`（代表“当前目录”）在执行文件写入时会被底层的虚拟文件系统（TSRM/VCWD）及系统调用进行路径规范化（Path Normalization）处理。系统会自动剥离末尾无意义的 `/` 与 `.`，最终将文件直接保存为前面的文件名（即 `shell.php`）

![](Pasted%20image%2020260829211843.png)



2. ==典型脆弱场景与代码分析==
许多框架或 CMS 在处理前端传递的 `save_name` 参数时，==允许传入数组或将其进行字符串切割重组==：

例：
![](Pasted%20image%2020260829212212.png)

- 脆弱点剖析：

1. `$_POST['save_name']` 可以被攻击者直接以数组形式提交。
2. 攻击者构造非连续索引数组：
    
    - `save_name[0] = "shell.php/"`
        
    - `save_name[2] = "jpg"`

3. **计算逻辑穿透**：

- 此时数组中有 2 个元素（Key 为 `0` 和 `2`），`count($file_name)` 等于 `2`。
- 后缀检测取 `$file_name[2 - 1]` 即 `$file_name[1]`，由于 Key `1` 不存在，其值为 `null`，不在黑名单中，成功绕过校验。
- 拼接最终保存路径 `$img_path`： `reset($file_name)`（即 `shell.php/`） + `.` + `$file_name[1]`（`null`） = **`"uploads/shell.php/."`**。
- `move_uploaded_file` 接收到 `uploads/shell.php/.`，自动截除 `/.`，成功生成 **`uploads/shell.php`**

## JAVA中的通过空字符截断缺陷绕过限制进行文件上传==(JDK<7)==
在 Java Web 应用开发与安全测试中，**空字符截断（Null Byte Injection / `0x00` 截断）** 曾是一种利用 Java 虚拟机（JVM）与底层操作系统 C 语言库交互差异，绕过后缀名白名单检测并上传恶意脚本（如 `.jsp`、`.jspx`）的经典手法


1. ==核心漏洞原理==

Java 中的空字符截断本质上是 **Java 字符串对象与底层操作系统 C 库字符串表现形式不一致** 导致的逻辑脱节：

1. **Java 层面的字符串表示**： Java 中的 `java.lang.String` 是基于字符数组（`char[]`）和明确的 `length` 字段维护的。在 Java 层面，字符 `\u0000`（ASCII `0x00`）被视为普通合法字符，字符串的长度计算、子串截取（`substring`）、后缀判断（`endsWith`）均把 `\u0000` 当作普通内容处理。
    
2. **JNI 与操作系统底层 C 库**： 当 Java 通过 `java.io.File`、`FileOutputStream` 等类对文件系统进行实际读写时，会通过 JNI（Java Native Interface）调用操作系统底层的 C 语言系统函数（如 `open()`、`stat()`、`creat()` 等）。
    
3. **截断发生**： C 语言标准规定字符串必须以 `\0`（`0x00`）作为终止符。因此，当含有 `\u0000` 的文件名被传递到底层 C 函数时，操作系统直接将 `\0` 识别为文件名终点，**丢弃 `\0` 后续的所有字符**

![](Pasted%20image%2020260829204919.png)



2. ==影响环境与版本限制==

- **受影响版本**：**JDK 7u40 之前**（包括 JDK 6 各版本及早期的 JDK 7 构建版本）。
    
- **修复机制**： 从 **JDK 7u40**（2013 年 9 月发布）开始，Oracle 官方在 `java.io.File` 和 `java.io.FileInputStream` / `FileOutputStream` 等底层类中加入了严格的空字符检查。若路径中包含 `\u0000`，会直接抛出 `java.lang.IllegalArgumentException: Invalid file path` 或 `InvalidPathException`，导致空字符截断在现代 Java 环境下直接失效

## 基于图片马的绕过

### 补：图片马简介
图片马（图片木马）是==一种表面上看起来是正常图片，但内部隐藏了恶意代码（通常是一句话木马）的文件==。它常用于网络安全攻防测试中的文件上传漏洞绕过

==工作原理==

- **外观伪装**：文件拥有合法的图片扩展名（如 `.jpg`、`.png`、`.gif`）和正常的图片头信息，能够正常显示或通过基础的文件格式校验。 [[1](https://didiplus.kwpmp.cn/archives/mFFCM4sY), [2](https://blog.csdn.net/kubernetes8ctl/article/details/154761560)]

- **代码隐藏**：攻击者将脚本代码（如 PHP、ASP 代码）追加到图片的末尾，或者通过编辑工具（如十六进制编辑器、Photoshop）将代码嵌入图片数据中。 [[1](https://cloud.tencent.com/developer/article/2245839), [2](https://blog.csdn.net/qq_48368964/article/details/140756993)]

- **触发执行**：单纯的图片马无法直接运行代码。它需要配合服务器的配置缺陷（如解析漏洞）或网站的**文件包含漏洞**，诱导服务器将该图片文件当作脚本代码解析，从而激活隐藏的恶意代码并获得 WebShell 控制权


==常见制作方式==

- **命令行合成**：在 Windows 的 `cmd` 中使用二进制复制命令（如 `copy /b`）将图片文件与代码文件合并为一个新文件。
- **十六进制编辑**：使用十六进制编辑器（如 WinHex、010 Editor）打开图片，在文件末尾直接粘贴并保存恶意代码。
- **图像处理软件**：利用 Photoshop 等工具打开图片，将代码写入图片的注释或 EXIF 信息中再进行保存


==防范与应对==

- **严格校验**：对上传的文件进行内容检查和重新渲染（如重构图片、去除冗余数据），而不仅仅依赖后缀名或 MIME 类型。
- **权限控制**：禁止上传目录拥有执行脚本的权限，防止图片被当作代码解析。
- **安全配置**：及时修复服务器及中间件（如 IIS、Nginx、Apache）的解析漏洞

### 利用图片马隐藏恶意代码进行文件上传
**图片马（Image WebShell / Polyglot Image）** ==是指将恶意脚本代码（如 PHP、ASP、JSP 等 WebShell）与合法的图片二进制数据拼接或融合后生成的文件==。

在文件上传安全检测中，服务端往往会==通过**文件头（Magic Bytes）**、**MIME 类型**或图形处理库（如 `getimagesize()`、`exif_imagetype()`）对上传内容进行合法性检查。图片马的主要作用正是**伪装成合法图片绕过内容检测**==


1. ==图片马的触发与执行条件==
**重要前提**：图片马本身仍保留了图片后缀（如 `.jpg`、`.png`），在标准 Web 服务器配置下，**直接访问图片文件只会作为静态资源下载或展示，无法直接执行其中的脚本代码**。

图片马要成功作为 WebShell 执行，必须依赖以下几种漏洞或配置缺陷配合：

| **触发方式**                         | **原理说明**                                                        | **典型场景**                                                                                                            |
| -------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **本地文件包含 (LFI)**                 | 服务端使用 `include()`、`require()` 等函数载入文件，PHP 会将目标文件内容均视为 PHP 脚本解析。 | `index.php?file=uploads/shell.jpg`                                                                                  |
| **Web 服务器解析漏洞**                  | 服务器配置不当，错误地将非脚本后缀文件传递给后端解析器处理。                                  | **Nginx** `cgi.fix_pathinfo=1` (`shell.jpg/xxx.php`)；<br><br>  <br><br>**Apache 1.x/2.x** 多后缀解析 (`shell.php.jpg`)   |
| **配置覆盖 (.htaccess / .user.ini)** | 先上传配置文件修改当前目录的解析规则，再载入图片马。                                      | `.htaccess` 中写入 `SetHandler application/x-httpd-php`；<br><br>  <br><br>`.user.ini` 写入 `auto_prepend_file=shell.jpg` |








## 基于二次渲染的绕过进行文件上传

### 补：二次渲染简介
二次渲染是指==服务器在接收到用户上传的文件（特别是图片）后，自动对文件进行解码、压缩、裁剪或重新生成等再次处理的操作==



- 什么是二次渲染？
	- 所谓的二次渲染，指的是在文件上传后开发者会对图片的内容进行修改
		- 如颜色、大小等
	- 对图片马会有什么影响？
		- 对内容的修改有可能导致我们的图片马失效
			- 相关资料： https://wwe.lanzoui.com/iFSwwn53jaf



==核心目的==

- **规范显示**：统一图片的尺寸、格式和像素。
- **优化性能**：减少文件体积，节省服务器存储空间并加快加载速度。
- **安全防护**：破坏并清除文件中夹杂的恶意代码（如隐藏在图片像素中的 WebShell 脚本），防止文件上传漏洞


==工作原理==

- **用户上传**：用户上传一张包含特定内容或附加代码的文件。
- **服务器处理**：服务器调用图形处理函数（如 PHP 的 `imagecreatefromjpeg` 或 `imagecopyresampled`）重新解析并生成一张新图片。
- **内容重写**：新图片只保留图像的像素数据，原本附加在文件空白区或数据流中的非图像代码（恶意代码）会被擦除或覆盖

### 构造文件数据结构对服务端二次渲染机制绕过进行文件上传
**基于二次渲染（Secondary Rendering）的文件上传绕过**，是指当服务端使用图形库（如 PHP GD 库、ImageMagick 等）对用户上传的图片进行重绘、压缩并重新生成新图像时，==通过巧妙构造图片内部数据结构，使得恶意代码在经历解码、重绘与重新编码后，依然完整保留在最终生成的文件中==

1. ==为什么常规图片马在此失效？==

- **文件尾追加法（`copy /b a.jpg + b.php`）**：渲染器只读取有效图像数据，文件尾部未被图像规范引用的附加字节会被直接丢弃。
- **EXIF 元数据注入法（`exiftool -Comment=...`）**：`imagecreatefrom*` 在提取像素阵列构建内存画布时，通常不解析或主动剥离 EXIF、ICC 配置文件、注释等非像素元数据块


2. ==主流图片格式的二次渲染绕过技巧==

绕过二次渲染的核心思想是：**找到在渲染与重新编码过程中“不会发生改变”或“能被逆向预计算”的数据区间，将 WebShell 嵌入其中**。

- ==GIF 格式绕过（难度：低）==

GIF 图像采用基于调色板的 LZW 无损压缩机制，其结构相对直观，重绘后保留不变的数据段最多。

**绕过原理：** GIF 文件由文件头（Header）、逻辑屏幕描述符、全局调色板（Global Color Table）、图像控制块与图像数据块（Image Data）等构成。GD 库在重新渲染 GIF 时，通常保留原始的调色板索引以及部分未变动的图像描述数据。

**利用流程：**

1. **上传采样**：准备一张小尺寸的正常 GIF 图片（如 10×10 像素），上传至目标系统触发二次渲染，并下载服务端生成的最终渲染图。
2. **十六进制对比**：使用 010 Editor、Beyond Compare 或 Hex 比较工具，比对原图与渲染后图的二进制差异。
3. **定位未变动区**：找到两张图片中完全一致且长度足够容纳 Payload（如 20~40 字节）的连续数据段（通常位于全局颜色表与第一帧图像描述符之间）。
4. **注入 Payload**：在原图的该固定偏移位置填入紧凑型 WebShell（如 `<?=$_GET[0]($_POST[1]);?>`），再次上传。渲染后该部分数据将原样保留



- ==PNG 格式绕过（难度：中/高）==

PNG 属于无损压缩格式，其核心像素数据存放在 `IDAT`（Image Data）数据块中，采用 Deflate（结合 LZ77 算法与 Huffman 编码）进行压缩。


**绕过原理：** GD 库渲染 PNG 时，会解压 IDAT 块、应用 PNG 滤波器（Filter Type 0~4），然后重新进行 Deflate 压缩。 攻击者通过**逆向 Deflate 压缩算法**，预先反推并构造特定的原始像素点矩阵（Raw Pixels）。当 GD 库对这些特定像素应用过滤并执行 Deflate 压缩时，压缩输出的二进制字节流恰好能拼出预设的 ASCII 代码字符串

例：
![](Pasted%20image%2020260829230628.png)




- ==JPEG/JPG 格式绕过（难度：高）==

JPEG 属于有损压缩格式，依赖离散余弦变换（DCT）与量化表（DQT），重新渲染时大部分高频像素数据会被舍入平滑，难度最高。

**绕过原理：**

1. **量化表与 Huffman 表利用**：部分版本的 GD 库在处理 JPEG 时，会复用部分量化表（DQT 标记 `0xFFDB`）或保留特定的预设数据段。
    
2. **寻找 DCT 稳态样本**：通过脚本对大量 JPEG 样本进行反复迭代测试，找到某些在特定量化参数下“即使多次压缩其 DCT 系数也不会再发生改变”的图片区域，将代码写入这些稳态块中。
    

**实战利用：** 通常借助针对特定 PHP/GD 版本的自动化脚本（如 `jpg_payload.php`）：

1. 传入一张基础的 JPEG 图片。
    
2. 脚本在内部模拟多次 `imagecreatefromjpeg` 与 `imagejpeg` 运算，直至找到能稳定保留 Payload 的偏移点并输出最终图片。






3. ==渲染马的触发与执行条件==

即便图片马成功穿透二次渲染并留存于服务器上，它在磁盘中仍然是以 `.gif`、`.png` 或 `.jpg` 后缀存储。要将其转化为有效的代码执行，==必须结合以下利用场景==：

| **触发组合**         | **核心机制**                                          | **示例**                                                     |
| ---------------- | ------------------------------------------------- | ---------------------------------------------------------- |
| **本地文件包含 (LFI)** | PHP 的 `include` / `require` 会将任何后缀的文件当作 PHP 脚本解析。 | `include($_GET['page']);` 包含 `uploads/avatar_rendered.gif` |
| **配置文件解析覆盖**     | 利用 `.user.ini` 或 `.htaccess` 强制指定图片马作为前置包含文件。     | `auto_prepend_file=avatar_rendered.png`                    |
| **Web 容器解析缺陷**   | 旧版 Nginx/IIS 的畸形解析特性。                             | 访问 `avatar_rendered.jpg/x.php` 触发 FastCGI 解析               |
