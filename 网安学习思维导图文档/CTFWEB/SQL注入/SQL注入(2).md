### 补：回显注入与盲注

#### 回显注入
**数据通过同一条通道返回给攻击者**，能在页面上直接看到想要的数据。

- 常见两种形式：
	- 联合查询注入
	- 报错注入

**特点**：
- 必须有**数据回显位置**或**详细的错误回显**。
- 一次请求就可能拿到整片数据，速度快。
- 危害明显，但也容易被日志或WAF检测。

#### 盲注
**页面不直接返回数据库内容，也不返回详细的报错信息**。只能根据页面行为上的细微差异，像“猜谜”一样逐位推断数据。

- 常见两种形式：
	- 布尔注入
	- 时间盲注

**特点**：
- 不需要数据回显，也不需要详细报错，**适用性最广**。
- 每个字符需要多次判断（如二分法），极为耗时，请求量巨大。
- 常需要用脚本或工具（如 SQLMap）自动化。

### 布尔注入

#### 布尔注入原理
==在不可有具体数据回显的情况下，以后台SQL语句执行正确与否所返回的回显并不太哦那个为根据完成的SQL注入攻击；==
通过构造逻辑判断式（真/假），观察页面是否呈现出**两种不同的状态**（如是否多显示一段文字、HTTP状态码不同、布局微调）

![](21b553a7765960b3cb4d23a06dde6138_720.jpg)

#### 布尔注入思路
通过构造布尔注入payload，来判断相应界面中的反馈有无不同，如有，则可能存在注入。
1. 验证注入点与确定回显差异
	首先测试逻辑表达式对页面响应的影响，确认布尔盲注可行性
2. 探测目标数据的长度
	在猜解具体字符前，必须先确定目标字符串（如数据库名、表名、字段值）的长度，防止无休止地猜解下去
3. 逐字符拆解与猜解（ASCII 转换）
4. 按数据库层级推导数据
	通过构造对 `information_schema` 元数据表的查询，按照固定的层级提取完整数据


### 时间盲注
当应用程序存在 SQL 注入点，但==**页面既不回显查询结果，也不返回明显的真/假差异**==（普通布尔盲注无法直接判断）时，攻击者通过向数据库注入带有**条件判断 + 时间延迟函数**的语句，根据服务器响应时间的长短，间接推断出数据内容。
在无法根据后台SQL语句执行的正确与否所返回的回显不同来完成的SQL注入攻击前提下，使用正确与否的时延长短不同来替代回显不同的布尔盲注。

#### 补：rpad()函数介绍
`RPAD` 函数（Right Pad）是一个常见的字符串处理函数，==用于在字符串的**右侧**填充指定的字符，使其达到设定的总长度==。如果原字符串本身长度已经大于或等于设定长度，则会将原字符串进行截断

- 语法：

#### 补：repeat()函数介绍

- 语法：
	`repeat(<字符串>,<重复次数>)`



#### 基于rlike操作符的时间盲注
利用==正则表达式匹配复杂字符串时触发指数级回溯==，从而阻塞查询执行

#### get_lock函数介绍
`GET_LOCK(str, timeout)` 是 MySQL 提供的一个用户级命名锁（或称应用锁）函数。它尝试获取一个名称为 `str`、最大等待时间为 `timeout` 秒的专属锁，常用于控制并发、防止重复提交或实现分布式简易锁。成功获取锁返回1，等待超时则返回0，发生错误则返回NULL

- 语法：
	`GET_LOCK(<锁的名称>(str), <等待时间>)`

### 补充：(SQL自动化注入的脚本编写知识)基于二分法算法的自动化布尔盲注原理

基于二分法算法的自动化布尔盲注，本质上是**将数据库未知的敏感数据映射到有序集合中，利用数据库作为布尔判定机（Oracle），通过 $O(\log N)$ 复杂度的区间二分折半缩小目标范围，从而以极低的网络请求开销解码数据**

在布尔盲注中，后端服务器对注入语句仅返回两种状态：`True`（如页面正常展示、HTTP 200）或 `False`（如内容缺失、错误提示）。

- 每次 HTTP 请求仅能获取 **1 bit** 的信息量（即 $0$ 或 $1$）。
- 目标字符取值范围通常为 ASCII 可打印字符集 $[32, 126]$（共 $95$ 个字符）

将字符的 ASCII 码视为一个单调递增的有序数组 $A = [32, 33, \dots, 126]$，真实字符对应的 ASCII 码为目标值 $X$。

- **初始区间**：$[low, high] = [32, 126]$
- **中点取值**：$mid = \lfloor \frac{low + high}{2} \rfloor$
- **判定谓词**：构造 SQL 逻辑条件 $P(mid): X > mid$
    - **若响应为 True**：说明 $X \in [mid + 1, high]$，区间更新为 $low = mid + 1$
    - **若响应为 False**：说明 $X \in [low, mid]$，区间更新为 $high = mid - 1$
- **终止条件**：当 $low > high$ 时搜索结束，最终的 $low$ 即为唯一确定的 ASCII 码值

关键工程问题与边界处理

1. **多字节编码字符（如中文数据）**
    - 标准 ASCII 范围无法覆盖 UTF-8 中文字符（Unicode 编码通常 $\ge 128$）。
    - **解决方案**：使用 `ORD()` / `CONVERT()` 函数，或将目标数据通过 `HEX()` 转为十六进制字符串（字符集固定收缩至 `0-9`, `A-F`，仅 16 种可能，二分每次只需 4 次请求）。

2. **网络抖动与误判容错（Flickering）**
    - 网络丢包、WAF 临时拦截会导致单次布尔状态误判，由于二分法具有依赖性，单次误判会导致后续区间整体偏移。
    - **解决方案**：引入判定置信度机制（如重试确认），或在得出最终字符后做一次等值验证：`ASCII(...) = final_value`。

3. **大小比较符号受限时的等价变换**
    - 若 WAF 拦截了 `>` 或 `<` 符号：
        - 可使用 `BETWEEN ... AND ...` 替代区间判断。
        - 可使用 `GREATEST()` / `LEAST()` 函数实现大小比较。
        - 切换为**位运算盲注（Bitwise Blind）**





**使用二分法在请求量与稳定性之间取得了最佳平衡**


### 补充：(SQL自动化注入的脚本编写知识)基于二分法算法的自动化时间盲注原理
==(二分法的时间盲注基本原理类似二分法的布尔盲注，同上)==
其本质是**利用时间延迟作为单向“隐蔽侧信道”（Side-Channel），将对数据库敏感数据的提取转化为基于时间阈值的二值判定（Timing Oracle），并利用二分折半查找将网络等待开销降至最低**

通过构造条件延时语句（如 `IF(condition, SLEEP(2), 0)`），将 SQL 逻辑计算转化为耗时差异：
$$\text{Response Time} = \begin{cases} \ge T_{\text{threshold}} & \implies \text{True (逻辑成立)} \\ < T_{\text{threshold}} & \implies \text{False (逻辑不成立)} \end{cases}$$

时间盲注的工程优化策略

1. **反向休眠优化（Sleep on False）**：
    - 在二分区间中，往往命中次数较少。如果设计为“条件不成立时休眠”，或者根据当前区间概率设计休眠触发条件，可以减少服务器整体执行 `SLEEP` 的总次数，进一步压缩脚本等待耗时。

2. **假阳性纠偏（False Positive Handling）**：
    - **问题**：网络拥堵会导致普通请求响应时间也超过 $T_{\text{threshold}}$，导致二分法将假信号误判为真，引起不可逆的区间偏移。
    - **策略**：当检测到响应超时（判定为 True）时，**立即发起一次二次确认请求**；若二次确认仍超时，才确认收敛区间。

3. **并发位置爆破（Position-level Concurrency）**：
    - 虽然单字符内部的二分状态是串行依赖的，但**不同位置的字符（第 1 位与第 2 位）之间完全独立**。
    - 利用 Python `asyncio` / `aiohttp` 或多线程，同时开启多个并发任务分别二分爆破不同下标位置，可将 10 个字符的总提取时间压缩至接近单字符提取时间
