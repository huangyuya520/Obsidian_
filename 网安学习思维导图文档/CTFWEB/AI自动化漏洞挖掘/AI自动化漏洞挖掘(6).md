2. Swagger 文档泄露
==Swagger（现遵循 OpenAPI 规范）是一种用于生成、描述和调用 RESTful API 的开发工具框架==。在微服务开发（尤其是金融行业广泛使用的 Spring Boot / Spring Cloud 体系）中，开发人员常集成 Swagger 或其衍生 UI（如国内金融项目极常用的 Knife4j / Swagger-Bootstrap-UI）以提升联调效率。

**Swagger 文档泄露**指系统上线生产环境时，未将开发/测试环境的 Swagger 依赖或映射关闭，导致外部未授权用户可以直接访问到完整的 API 接口列表、请求方式（GET/POST/PUT/DELETE）、参数字段格式、响应结构以及内网调用逻辑


==金融业务场景下的高风险诱因==

金融系统对接口文档的敏感度显著高于一般内容型网站，主要体现在以下几个业务特性：

1. **庞大的微服务矩阵与接口暴露面** 大型银行、证券、消金平台通常拆分为数百个微服务（用户中心、账户核心、风控引擎、征信查询、结算清算、支付网关等）。一旦网关路由规则配置不当，某个边缘服务的 Swagger 暴露，便会连带暴露出大量内部通信与调试接口。

2. **敏感字段明文规范化暴露** 金融接口对数据结构的定义极为严格。Swagger 文档会详细罗列字段命名，例如：
    
    - 身份认证：`idCardNo`（身份证）、`realName`（真实姓名）、`cvv2`、`cardExpire`（卡有效期）。
        
    - 资金操作：`amount`（金额）、`transType`（交易类型）、`channelId`（商户渠道编号）。
        
    - 内部系统：`isInternal`、`debugFlag`、`auditStatus`（审核状态）。

3. **隐蔽的调试与废弃接口** 开发团队在快速迭代（如贷款催收、风控放款策略变更）时，常遗留未在前端页面绑定的“影子接口”（Shadow APIs）或用于本地 Mock 数据的内部接口。这类接口往往缺乏鉴权校验。

==纵深挖掘：从文档泄露到金融高危漏洞==

在金融 SRC 的规则下，单纯提交一个无未授权操作的 Swagger 页面，奖励分值较低（通常在低危区间）。要挖掘出核心漏洞，需要借助泄露的文档展开以下纵深测试：


1. 垂直/水平越权（BOLA / BFLA）

金融业务对权限隔离要求极高。文档中经常暴露出具有高权限的接口，例如：

- **账户查询接口**：观察是否仅通过 `userId`、`accountId` 或 `mobile` 查询流水。如果服务端未对当前 Token 与目标 ID 做强绑定校验，便存在水平越权泄露 KYC（个人敏感金融数据）的风险。
    
- **审批/管理接口**：如 `/api/loan/approve`、`/api/risk/whitelist/add`。测试普通用户携带自身 Token 或无 Token 访问这些管理接口是否触发拦截。



2. 参数篡改与业务逻辑绕过

通过 Swagger 文档查看请求参数中是否存在敏感校验标志，例如：

- **金额与优惠**：`deductRate`（费率）、`discountAmount`（减免金额）、`interestRate`（利息）。测试是否可由前端或请求体直接传入并被后端入库。
    
- **状态覆盖（Mass Assignment / 对象注入）**：例如用户信息更新接口 `POST /api/user/updateProfile`，文档暴露了实体中包含 `role`、`kycStatus`、`creditLimit`（授信额度）等属性。测试通过在请求中夹带这些属性是否会直接修改核心字段




3. 未授权回调与接口伪造

- 金融收单、聚合支付模块常包含第三方支付（如银联、微信、支付宝）的异步通知接口（如 `/pay/notify/callback`）。
    
- 文档会披露回调接口所接收的数据格式、签名算法字段。检查回调逻辑是否未校验商户真实签名、直接接收模拟报文即改变订单状态（造成“虚假充值”或“零元购”）




4. 敏感凭据与内网地址泄露

- 检查文档中的参数描述、接口说明（`summary`/`description`）或示例值（`example`）。部分开发者会直接将测试环境的账号密码、第三方金融网关的 `AppSecret`、`MerchantId` 或内网数据库/MQ 连接地址硬编码在注释中




==防护与修复方案==

金融行业对于接口文档泄露有严格的内控与合规要求（如关基保护、等保 2.0、金融数据安全标准）：

1. **环境隔离与条件加载**： 在 Spring Boot 体系中，利用 Profile 机制确保 Swagger 配置仅在 `dev` 或 `test` 生效，生产环境严格关闭


2. **API 网关策略拦截**： 在微服务网关（如 Spring Cloud Gateway、Kong、Nginx）上配置严格的黑名单或路由重写规则，禁止任何外部流量请求带有 `*swagger*`、`*api-docs*`、`/doc.html` 的 URI。


3. **强制零信任鉴权**： 确立“即使文档泄露，接口仍然安全”的防御纵深。所有接口必须在网关层或业务层通过统一鉴权中间件校验 JWT / OAuth2 令牌，坚决废除“仅靠隐藏接口 URL 保证安全”（Security through Obscurity）的做法

7. SPF 邮件伪造
在金融行业安全应急响应中心（SRC）中，**SPF（Sender Policy Framework）配置缺陷导致的邮件伪造**是一类出现频率极高、但在定级上常常存在争议的漏洞。

在普通互联网厂商眼中，SPF 缺失有时会被视为“无危害配置问题”或定为低危/忽略；但在**银行、证券、保险、持牌消金**等强信誉属性的金融机构中，一旦核心域名被成功伪造，极易被黑产用于针对高净值客户或内部员工的鱼叉式钓鱼、虚假对账单诈骗及 CEO 欺诈（BEC 攻击），因此金融 SRC 通常对此类漏洞的危害敏感度更高。


==一、 SPF 基础与验证原理==

SPF 是一种基于 DNS 的电子邮件认证机制（RFC 7208），域名所有者在 DNS 中发布 TXT 记录，声明哪些服务器（IP 或域名）被允许代表该域名发送邮件。

一个标准的 SPF 记录示例如下：

例：
```
v=spf1 ip4:101.200.1.0/24 include:mail.partner.com -all
```



1. 核心前缀机制（Qualifiers）

接收方邮件服务器解析 SPF 时，通过后缀指示符判定动作：

|**机制前缀**|**状态判定**|**邮件服务商默认处理动作**|
|---|---|---|
|**`-all`**|**HardFail**（强制拒绝）|邮件服务器通常直接退信或丢弃。|
|**`~all`**|**SoftFail**（软失败）|接受邮件，但可能打上“垃圾邮件”标记或提高垃圾邮件评分。|
|**`?all`**|**Neutral**（中立）|不作任何判定，与无 SPF 记录效果接近。|
|**`+all`**|**Pass**（完全允许）|极其危险，允许全球任意 IP 代表该域名发信。|



==二、 金融机构常见的 SPF 漏洞成因==

金融机构业务庞杂，涉及三方营销平台、短信/邮件网关、内部呼叫中心及各级支行子域，极易产生以下配置疏漏：


1. “信封地址”与“显示地址”分离（缺乏 DMARC 对齐）

这是邮件伪造最本质的技术成因。邮件协议中存在两个发件人概念：

- **`Mail From`（RFC 5321 协议地址 / Return-Path）**：邮件传输信封上的发件人，退信通知发送至该地址，**SPF 仅对该字段进行校验**。
    
- **`From`（RFC 5322 标头发件人 / Display From）**：邮件客户端界面（Outlook、Foxmail 等）展示给用户的发件人。
    

> **漏洞成因**：如果目标金融域名仅配置了 SPF，但**未配置严格的 DMARC 记录（或 `p=none`）**，攻击者可以使用自己可控的外部域名作为 `Mail From` 绕过 SPF 校验，而在邮件标头的 `From` 字段任意伪造成 `service@bank.com`。客户端因无 DMARC 强制对齐策略，会直接向用户展示受信任的银行官方发件人


2. 软失败策略滥用（`~all`）

很多金融运维人员因担心影响三方业务（如外包呼叫中心、征信报告代发平台）的正常送达率，长期使用 `~all` 甚至 `?all`。在缺少 DMARC 兜底的情况下，大部分主流邮件服务商（腾讯企业邮、网易企业邮、Exchange）仍会将此类邮件直接投递到收件箱中



3. 子域名与非生产域名遗漏

金融企业往往对主域名（如 `bank.com`）做了严格配置，但忽略了以下资产：

- **子域名**：如 `oa.bank.com`、`notice.bank.com`、`dev.bank.com`。SPF 默认不具备子域名继承性，未显式声明的子域名完全没有 SPF 保护。
    
- **空停用域名 / 品牌防御性注册域名**：用于防抢注但未启用的域名未设置 `v=spf1 -all` 保护，导致攻击者利用其伪造发信




4. DNS 查询超限导致 Permanent Error（PermError）

RFC 7208 规定：解析 SPF 记录时，触发的 DNS 查询次数（包含 `include`、`a`、`mx`、`ptr` 等）**不得超过 10 次**。 金融机构随着业务线合并，SPF 中频繁追加三方服务的 `include:`，导致递归查询次数超过 10 次，接收方解析触发 `PermError`。部分容错配置较低的邮件服务器会将此错误降级处理，导致防御失效。




5. 网段授权过宽（CIDR 泄露）

部分金融机构直接在 SPF 记录中加入了托管服务商庞大的公网 IP 段（如公有云的 `/16` 甚至 `/8` 大网段）。攻击者只需在相同的公有云节点申请一台机器，即可直接以合法的 IP 范围通过 SPF 验证。



==三、 金融 SRC 挖掘与验证实战==

在授权测试范围内，测试 SPF 伪造一般经历以下排查流程：

1. DNS 记录快速筛查

使用基础网络命令检测域名的 SPF 与 DMARC 状态：

例：
```
# 查询主域及子域的 SPF 记录
dig +short TXT target-bank.com | grep "v=spf1"

# 查询 DMARC 策略
dig +short TXT _dmarc.target-bank.com
```

- **高风险特征**：未查到任何 SPF 记录，或查到 `v=dmarc1; p=none;`（仅监控，不拦截伪造）。




2. 发信验证与伪造测试（使用 Swaks）

`swaks`（Swiss Army Knife for SMTP）是验证邮件伪造的主流测试工具。测试前需准备一台具备公网独立 IP 且未被主流反垃圾黑名单收录的服务器。

- 场景 A：直接伪造发件人测试（测试 SPF 本身容错）

例：
```
swaks --to target-user@company.com \
      --from official-alert@target-bank.com \
      --server your-smtp-server.com \
      --header "Subject: 【紧急风险提示】关于账户安全认证升级的通知" \
      --body "请点击链接完成身份核验。"
```



- 场景 B：利用 DMARC 缺失进行 Header From 欺骗
例：
```
swaks --to target-user@company.com \
      --mail-from attacker@controlled-domain.com \
      --h-From: "中国XX银行信用卡中心 <creditcard@target-bank.com>" \
      --server your-smtp-server.com \
      --header "Subject: 【账单通知】您本月有未结算账单" \
      --body "点击附件下载对账单查看明细。"
```


**观察点**：

1. 邮件是否被收件方直接拒绝（Reject）。
    
2. 邮件进入了收件箱（Inbox）还是垃圾箱（Junk/Spam）。
    
3. 客户端界面展示的发件人名字与邮箱地址是否为伪造的银行地址。




==四、 金融 SRC 提报要点与定级影响==

在金融 SRC 提报 SPF 伪造时，**单纯丢出一张 DNS TXT 查询截图通常只会被评为“低危”甚至直接忽略**。若想获取中危或更高评级，必须提供充分的业务影响证明：

1. **核心域 vs 边缘域**：
    
    - 伪造核心事务域名（如涉及短信提醒、对账单发送、登录凭证校验的主域），危害远大于某个闲置的三级域名。

2. **实际投递成果证据（PoC 质量）**：
    
    - 必须包含测试邮件成功投递到**企业内部办公邮箱（如其自身的 Exchange/企业微信邮箱）**或**主流公网邮箱（QQ、网易 163、Gmail、Outlook）收件箱**的完整截图。
        
    - 截图需展示邮件原文（Email Headers），证明 `Authentication-Results` 中 SPF/DMARC 绕过或校验失效的细节。

3. **结合钓鱼场景的危害说明**：
    
    - 结合金融场景定制钓鱼载荷（如伪造放款审批通知、薪酬调整通知、网银证书过期更新），说明该漏洞如何使攻击者以权威信任背书发起精准欺诈。




==五、 防御与修复方案==

防御 SPF 伪造必须采用组合拳，单一机制无法防御现代邮件欺诈：

1. **严格收敛 SPF 策略**：
    
    - 必须使用硬拒绝策略 `-all`，杜绝 `~all` 与 `?all`。
        
    - 精简解析记录，合并 CIDR，确保 DNS 查询总数小于 10。

2. **强制实施 DMARC 拦截策略**：
    
    - 在 DNS 添加 `_dmarc` 记录，并将策略配置为 `p=reject`（直接拒绝）或至少过渡到 `p=quarantine`（隔离至垃圾箱）

3. **部署 DKIM 签名**：
    
    - 结合 `DKIM（DomainKeys Identified Mail）`，由邮件发送服务器利用私钥对邮件进行数字签名，接收方通过 DNS 中的公钥校验完整性，防止传输链路被篡改。

4. **防御性空白域名保护**：
    
    - 对企业名下所有不用于发信的辅助域名及子域名，统一添加“空 SPF”与拒收策略
