
# 补：SRC漏洞挖掘入门介绍
==**SRC（Security Response Center，安全应急响应中心）** 是各大企业建立的面向外部安全研究人员（白帽子）收集自身产品与系统安全隐患的平台。SRC 漏洞挖掘本质上是在**明确授权和规则边界**的前提下，对企业公开在互联网上的真实业务系统进行安全性测试，挖掘安全隐患并获取安全积分与奖金（Bounty）==




==一、 SRC 的基本运作机制==

企业自建或入驻第三方的 SRC，主要分为两类：

- **企业自建 SRC：** 如腾讯 TSRC、阿里 ASRC、字节跳动安全应急响应中心等，直接由企业内部安全团队审核与发放奖励。
    
- **第三方漏洞众测平台：** 如补天、漏洞盒子、HackerOne、Bugcrowd 等，平台作为中间人组织企业进行公开或定向的漏洞众测活动


SRC 漏洞评分通常基于 **CVSS / 自身评分准则**，从严重程度划分为：

- **低危（Low）：** 反射型 XSS、非敏感信息泄露、缺少安全配置标头等。
    
- **中危（Medium）：** 存储型 XSS、普通用户水平越权、敏感配置泄露、弱密码。
    
- **高危（High）：** 关键业务垂直越权、SSRF（打入内网）、SQL 注入、敏感数据批量泄露。
    
- **严重（Critical）：** 任意命令执行（RCE）、任意文件上传 GetShell、核心业务任意密码重置/资金篡改



==二、 SRC 漏洞挖掘全流程==

```
[研读规则/范围] ➔ [资产信息收集] ➔ [目标筛选分层] ➔ [漏洞挖掘测试] ➔ [验证/PoC编写] ➔ [合规提交与修复跟踪]
```


1. 规则确认（测试的前提红线）

在动手测试前，必须仔细阅读对应 SRC 的 **《漏洞收集范围与规则》**：

- **确定测试资产范围（In-Scope）：** 哪些域名、IP 段、小程序在奖励范围内，哪些被明确排除（Out-of-Scope）。
    
- **禁止的行为：** 严禁 DoS/DDoS、社工员工、内网横向扩散、批量脱库（通常提取一两行证明即可）、物理渗透等。



2. 资产收集与测绘（核心决胜点）

业内常说“**信息收集决定了渗透测试的上限**”。在成熟企业中，主站防护通常极为严密（WAF + 强风控），新上线的业务、子公司边缘资产往往是漏洞高发区。

- **子域名挖掘：** 结合证书透明度日志（crt.sh）、DNS 字典爆破（ksubdomain）、被动资产收集（Subfinder、Amass）。
    
- **IP 资产与端口识别：** 通过资产测绘引擎（FOFA、Hunter、Shodan）排查暴露在外的非标端口与旁路系统。
    
- **JS 文件分析：** 爬取前端 JS 文件，提取隐蔽 API 接口、开发环境调试路径、硬编码的测试账号或 AccessKey/Token。
    
- **目录与敏感路径扫描：** 探测 `.git` 泄露、备份文件（`.bak`、`.zip`）、Swagger/Actuator 接口等。



3. 漏洞挖掘与验证

根据不同系统特点展开测试：

- **边缘小系统/子公司资产：** 易存在旧版本框架漏洞（如 Shiro 反序列化、ThinkPHP RCE、Fastjson 反序列化、未打补丁的 Spring CVE）。
    
- **主站核心业务系统：** 注重**业务逻辑漏洞**与**API 接口安全**



4. 报告撰写与提交

一份规范的漏洞报告能大幅减少与审核人员的沟通成本：

- **漏洞简述：** 准确归类（如“某商城订单接口存在水平越权修改配送地址”）。
    
- **影响范围：** 明确受影响 URL、参数、接口。
    
- **复现步骤：** 清晰分步描述，附上请求包与响应包截图，说明需要替换的参数。
    
- **危害证明（PoC）：** 仅证明存在危害，不要扩大破坏范围。
    
- **修复建议：** 给出简要防护方案（如鉴权检查、参数白名单校验）



==三、 SRC 中最易出高危的方向==

|**漏洞大类**|**核心测试点**|**实战特点**|
|---|---|---|
|**越权漏洞（IDOR）**|平行越权（修改 `user_id` 查看他人数据）、垂直越权（普通用户调用管理员 API）|自动化扫描器极难发现，主要依赖人工抓包比对双账号权限。高危率极高。|
|**身份与认证绕过**|验证码爆破/复用/回显在响应中、任意密码重置（验证凭证参数可控或逻辑跳步）|常见于注册、找回密码、绑定换绑手机号等业务流。|
|**API 接口未授权**|Swagger-UI / OpenAPI 文档暴露、GraphQL 查询未鉴权、后端未校验 Token|前后端分离架构普及后最常见的缺口，常常能直接批量提取数据。|
|**移动端与小程序**|微信/支付宝小程序抓包、App 反编译与动态调试|移动端接口常因为独立维护，缺少 Web 主站级别的 WAF 和限流策略。|
|**SSRF / 外部请求调用**|URL 预览、转存图片、Webhook 配置、文件解析转码|如果能利用协议（`gopher://`、`dict://`）探测内网未授权 Redis、FastCGI，危害可直接上升至严重。|


==四、 常用挖掘工具链==

- **流量代理与分析：** `Burp Suite`（核心基石）、`Yakit`。
    
- **资产收集与测绘：** `Subfinder`、`ksubdomain`、`httpx`、`katana`（爬虫）。
    
- **主动辅助扫描：** `Nuclei`（通过自编写或社区 YAML 模板快速排查已知指纹与漏洞）、`Xray`（配合 Burp 被动代理挖掘常见 Web 漏洞）。
    
- **前端与小程序分析：** `WechatOpenDevTools`（微信开发者工具逆向调试）、`Packer-Fuzzer`（Webpack 前端打包提取 API 漏洞）




五、 白帽子的核心职业素养与红线

1. **测试停止线：**
    
    - 发现 SQL 注入时，仅需获取数据库版本号（如 `user()` 或 `@@version`）证明即可，**切勿导出全库或爬取个人隐私数据**。
        
    - 发现任意文件上传/RCE 时，执行 `whoami` 或弹出计算器写静态 PoC 文件即可，**不要深挖内网或种植持久化后门**。

2. **严防对业务产生破坏：** 测试支付或并发下单漏洞时，使用小额真实测试后及时退款，不得造成企业账目混乱或瘫痪系统。
    
3. **严格保密：** 在厂商未修复并公开之前，严禁将漏洞细节与 PoC 发布在社交平台或技术博客中



## 现代AI在SRC漏洞挖掘中扮演怎样的角色？
现代 AI 在 SRC（安全应急响应中心）漏洞挖掘中，==早已超越了简单的“提问答疑”工具，而是演进为白帽子的“全流程智能副驾（Copilot）”乃至具备执行能力的“垂直测试智能体（Agent）”==。

由于现代成熟企业的边界防护（WAF、风控、自动化巡检）日益完善，传统的“无脑扫描器+通用字典爆破”在 SRC 中收效甚微。AI 的介入，本质上是**帮助白帽子大幅压缩低维繁琐的分析时间，让攻防博弈集中到高阶的业务逻辑与上下文漏洞上**



==一、 现代 AI 在各挖掘阶段的实际角色==

1. 攻击面收敛与“噪音提炼器”（Recon & Surface Mapping）

信息收集往往会产生海量数据（数以千计的子域名、数百个 JS 依赖包、海量 API 接口），AI 在这里充当高效的“情报分析员”：

- **前端代码与 JS 分析：** 现代 Web 应用高度依赖 Webpack/Vite 前端打包。AI 可以快速解析脱敏、反混淆压缩代码，从中自动提取隐蔽未公开的 API 路由、测试环境接口以及硬编码的敏感凭证（如内部 Token、AccessKey）。
    
- **文档与接口语义识别：** 面对泄露的 Swagger/OpenAPI 或 GraphQL Schema 文档，AI 能根据接口语义（如 `admin_update`、`internal_query`）评估敏感度，圈定可能缺少鉴权校验的高价值测试点



2. 业务逻辑漏洞推演（Logic Flaws & IDOR）

传统 DAST 扫描器（如 Awvs、Xray）长于基于规则的语法类注入（SQLi、XSS），但在处理**越权、多步状态机、支付篡改**等逻辑漏洞时几乎无能为力。这恰恰是具备上下文理解能力的 LLM 的强项：

- **权限状态差分对比（Delta Analysis）：** 抓取普通用户和特权用户（或 Tenant A 与 Tenant B）针对同一资源的请求/响应包，让 AI 快速标记出角色鉴权参数的细微差异，推演未授权访问或越权操作的切入点。
    
- **多步状态机跳步假设：** 在测试重置密码、优惠券兑换或多步骤订单时，AI 能够理解业务状态转移链路，提出具有启发性的假说（如：“如果在步骤 2 校验通过后直接伪造步骤 4 的参数，是否能绕过中间的身份重验？”）。




3. 上下文感知的 Payload 变异（Custom Fuzzing & WAF 绕过）

传统 Fuzzing 依赖死板的字典，易被 WAF 精准拦截。现代 AI 能够针对具体技术栈定制 Payload：

- **针对性变异：** 如果识别到目标后端是基于特定版本的框架（如 Spring Boot、ThinkPHP、Node.js），AI 能根据上下文生成利用语法差异、编码组合（Unicode 变异、畸形 JSON、分块传输）构造的定制化探测向量。
    
- **错误信息反向诊断：** 当目标接口返回异常堆栈或特定拦截代号时，AI 能够快速解释报错底层逻辑，推断后端的过滤机制，并给出针对性的绕过思路



4. 武器化 PoC 编写与自动化验证

- **一键脚本化：** 从 Burp Suite 导出原始 HTTP 请求包后，AI 可以在秒级生成并发条件竞争（Race Condition）测试脚本、带动态 Token 刷新的自动化复现 Python 脚本。
    
- **规范化报告输出：** 漏洞复现成功后，AI 能将凌乱的测试日志和数据包快速整理成满足 SRC 审核标准的漏洞报告，清晰结构化受影响接口、步骤重现、危害证明（PoC）以及精准的安全加固建议。




==二、 AI 在漏洞挖掘中的“双重身份”：工具与新靶标==

除了作为挖掘工具外，AI 自身在企业系统中的广泛集成，直接催生了 SRC 的全新攻击面：

- **企业级 AI 应用渗透：** 越来越多的 SRC 将企业内部集成的 AI 助手、智能客服、Agent 纳入测试范围。
    
- **新型漏洞类型：**
    
    - **间接提示词注入（Indirect Prompt Injection）：** 通过污染网页内容或文档，诱导 AI Agent 执行未授权的越权操作（如读取邮件、发起内部 API 请求）。
        
    - **Agent / MCP 越权调用：** AI 智能体调用的内部工具链（MCP Server、内部微服务接口）未严格做权限边界隔离，导致高危横向越权


==三、 现代 AI 在 SRC 中的局限与避坑要点==

1. **“一本正经胡说八道”的幻觉（Hallucination）：**
    
    - AI 极易根据前端参数表面推测存在高危漏洞（如看见未脱敏的数据结构就笃定存在未授权），但在真实动态环境中后端可能有硬编码过滤或二次鉴权。
        
    - **准则：一切必须以动态抓包的真实响应为准，绝不能轻信静态推论。**

2. **SRC 平台的治理与合规红线：**
    
    - 各大 SRC（如 HackerOne、国内各大安全响应中心）严令禁止未经人工复现、批量用 AI 生成的“垃圾报告”。未经实操验证便提交 AI 虚构的漏洞报告，会被直接判为无效甚至扣除信誉分。
        
    - **数据安全合规：** 进行 SRC 测试时，切勿将涉及客户真实敏感数据、企业未公开的核心业务数据上传到不受信任的公有云 AI 模型中，避免造成数据合规违规。

3. **缺乏主动的动态探测能力：**
    
    - 单纯的大语言模型只有“大脑”，没有“眼睛和手”。目前实战中最高效的模式是 **“AI + Burp Suite/Yakit/Nuclei 插件”** 组成的工作流，通过 API 实时将流量灌给模型进行边抓包边分析。




==白帽子与 AI 协同的正确心智==

==在当前阶段，**AI 不会直接自动化替你打穿整个系统，但熟练掌握 AI 工作流的白帽子，正在快速淘汰依赖纯手动重复劳动的挖掘者。**==

对于正在学习漏洞挖掘的新人，最优的利用方式是：**让 AI 充当随时答疑的资深导师与脏活累活的执行助手**——让它替你读长篇 JS、让它帮你写测试脚本、让它帮你分析冷门协议；而你的核心精力，应始终放在**理解业务系统架构、识别业务逻辑缺陷以及把控合规边界**上

## SRC漏洞报告撰写
==一份高质量的 SRC（安全响应中心）漏洞报告，核心目标是**让审核人员在 3 分钟内无歧义地复现漏洞、看清其实际业务危害，并据此给出公正的评级与赏金**==

报告结构通常遵循“定位快、复现稳、定级准、建议实”的原则


==一、 标准报告结构与要素拆解==

1. 报告标题（Title）

标题需在列表页直接体现关键信息，建议采用**标准化公式**：

> **[所属子域名/系统名称] + [漏洞位置/接口] + [漏洞类型] + [直接危害]**

- **反面教材**：`发现一个严重越权漏洞`、`某接口存在SQL注入`
    
- **正面教材**：`[mall.example.com] 订单查询接口存在水平越权，可遍历全平台用户地址与手机号`



2. 漏洞基本属性（Metadata）

以结构化键值对形式呈现，便于审核员入库录入：

|**属性字段**|**示例与说明**|
|---|---|
|**所属厂商/资产**|Example 集团 - 核心商城系统|
|**漏洞类型**|业务逻辑漏洞 - 水平越权（IDOR） / 注入 - 报错型 SQL 注入|
|**自评等级**|高危（High） / 严重（Critical） / 中危（Medium）|
|**测试 URL / 接口**|`POST [https://api.example.com/v1/user/order/detail](https://api.example.com/v1/user/order/detail)`|
|**受影响参数**|`order_id` / `user_token`|
|**测试账号**|测试账号 A: `test_user_01`, 测试账号 B: `test_user_02`|


3. 漏洞简述与成因分析（Vulnerability Summary）

用 2~3 句话说明漏洞触发逻辑与背后的安全缺陷：

- **业务逻辑**：该接口用于普通用户查询个人订单详情。
    
- **缺陷原因**：服务端未校验当前 Session 对应的 `uid` 与入参中的 `order_id` 归属关系，仅依据前端传递的 `order_id` 直接从数据库检索并返回结果，导致水平越权。




4. 详细复现步骤（Reproduction Steps - 核心部分）

复现步骤必须做到**无前置知识即可一步步复现**，切忌“一句话代过”。

1. **环境准备与账号状态**：注明需要的角色、权限、两套测试凭据。
    
2. **抓包与修改参数细节**：
    
    - 给出完整的 HTTP Raw Request / Response（脱敏关键 Token，保留必要字段）。
        
    - 明确指出将哪一个参数改为了什么值。
        
3. **关键证据截图**：
    
    - 截图需截全，包含接口地址、参数变更前后对比、返回结果。
        
    - 圈出关键数据（如泄露的手机号、身份证、密码哈希等）


---


5. 危害与利用场景分析（Impact Analysis）

不要只写理论危害，要结合**业务场景**说明实际危害：

- **数据机密性影响**：`order_id` 采用 10 位纯数字递增生成，攻击者编写脚本即可在无认证/普通权限下按步长遍历，导致全量订单数据泄露（包含收件人真实姓名、手机号、收货地址）。
    
- **业务连带风险**：数据可被黑产用于杀猪盘、冒充客服诈骗等下游攻击，影响品牌声誉及法律合规（如个人信息保护法）

==二、 提升通过率与评级的高级技巧==

1. **严格遵守“点到为止”测试红线**
    
    - **SQL 注入**：读出 `user()`、`version()` 或确认延时即可，**切勿 dump 大量业务数据**。
        
    - **RCE / 命令执行**：执行 `whoami`、`id` 或 `hostname` 即可，**不要弹公网 Shell、不建后门、不提权**。
        
    - **逻辑漏洞（如越权改密）**：必须使用自己注册的两个测试账号验证，**严禁修改管理员或他人账号**。

2. **突出“攻击路径”，而非孤立参数**
    
    - 很多审核员不认可“弱口令”，但如果是“某个废弃子域名的 Jenkins 弱口令 -> 包含私有 GitLab AccessToken -> 形成内网代码泄露”，提交完整的利用链（Exploit Chain）将直接从中低危跃升为高危/严重。

3. **善用请求报文差异化高亮**
    
    - 使用 Markdown 代码块并注释出关键修改点（如 `// 此处篡改 uid`），减少审核员寻找 Payload 的时间成本。

4. **理性自评，避免“无脑严重”**
    
    - 熟悉各家 SRC 的评分准则（CVSS 标准）。将一个无实际危害的 Self-XSS 或未绑定的 DNS 解析强行标为“严重”，容易降低审核员对报告者的专业度信任。

## SRC漏洞挖掘之“漏洞”简介
在网络安全与 SRC（Security Response Center，企业安全应急响应中心）挖掘中，漏洞（Vulnerability）**与常规的**程序错误（Bug）**有着本质区别：==漏洞特指系统、协议、架构或业务逻辑中存在的缺陷与配置不当，攻击者能够借此绕过预设的安全策略，对系统的**机密性（Confidentiality）、完整性（Integrity）或可用性（Availability）造成破坏。==

但在 SRC 实际运作中，判定标准更加偏向**商业风险与实际危害**。并非所有技术扫描器报出的异常都能算作有效漏洞





==什么是漏洞：从通用概念到安全视角==

在广义软件工程中，任何不符合预期的代码行为都叫 Bug；而在安全攻防中，只有满足以下条件的代码或逻辑问题才构成**安全漏洞**：

1. **==存在攻击面与触发路径**：==存在能够接收外部不可信输入或非预期交互的入口。
    
2. ==**打破信任边界或权限隔离**：==导致未授权访问、权限提升、越权操作或数据泄露。
    
3. ==**违反安全三要素（CIA）**：==
    
    - **机密性受损**：未经授权读取敏感信息（如源码泄露、未授权查询用户隐私、SQL 盲注提取数据）。
        
    - **完整性受损**：未经授权篡改、创建或删除系统数据（如越权修改他人密码、存储型 XSS 篡改页面行为、任意文件上传覆盖系统配置）。
        
    - **可用性受损**：导致合法服务无法访问（如拒绝服务、关键业务资源锁死）



==怎样才算一个合格的“SRC 漏洞”？==

SRC 是企业面向外部白帽子的漏洞收集平台，其核心职责是**为企业业务风险买单**。一个问题要被 SRC 审核人员定级并给予赏金/积分，必须同时满足以下四个核心维度：

1. 资产合规（In-Scope）

- **在范围之内**：必须属于该 SRC 发布的众测资产规则列表（主域名、明确收购的子公司、指定 App 或 API 网关）。
    
- **非排除资产**：第三方 SaaS 供应商（如未魔改的外部问卷系统）、即将下线的废弃测试站若已在规则中声明“不计分”，则通常直接忽略（NA）。



2. 存在可证明的实际业务危害（Real Business Impact）

SRC 最忌讳“纯理论风险”。审核人员首要评估的是：**这个漏洞如果被黑客利用，公司会损失什么？**

- **技术 Bug $\neq$ SRC 漏洞**：
    
    - _非漏洞示例_：未配置 `X-Content-Type-Options`、服务器报错输出了 PHP/Java 堆栈但没有敏感密钥、仅反射自身输入的 Self-XSS（无 CSRF 结合）。这些通常被归类为“最佳实践建议”或“无实际危害”，直接忽略。
        
    - _合格漏洞示例_：报错堆栈中直接泄漏了数据库明文账号密码；反射型 XSS 结合业务场景能成功盗取含 HttpOnly 外的敏感凭证并触发危险操作。
        
- **越权必须越过“数据或权限”**：单纯请求返回一个空数组或公开信息的平行越权，算不上有效漏洞；若能替换参数直接遍历下载全平台用户的身份证号、合同或充值记录，才算高危漏洞。





3. 完整的攻击链路与可复现性（PoC & Reproducibility）

- **确定性复现**：审核员按照你的报告步骤能够 100% 重现该攻击行为。
    
- **具备概念验证（PoC）**：必须展示攻击成立的最后一步。
    
    - 证明存在 SSRF：不能只说向自己的 DNSLog 发出了一个请求，需证明能够探测内网敏感端口或读取云厂商元数据（Metadata 接口）。
        
    - 证明存在 SQL 注入：不仅是报错，至少需要通过延时（Sleep）、布尔条件或报错回显提取出数据库版本号或当前数据库用户名。





4. 测试边界合法性（Testing Boundary Compliance）

SRC 是授权测试，严禁任何破坏性行为：

- **验证即止（Proof of Concept, not Exploitation）**：证明可以越权下载敏感文件，下载 1-2 条自身测试账号的数据作为证据即可；若直接脱库或批量下载成千上万条真实用户信息，不仅会导致漏洞被拒，还可能触犯法律风险。
    
- **严禁影响业务可用性**：不能对线上生产环境打 DoS/DDoS 攻击；不能向真实用户群发垃圾短信/钓鱼邮件。




==常见对比：容易被驳回的提交 vs 合格的 SRC 漏洞==

|**常见被拒提交（通常定为 忽略 / 无危害）**|**合格的 SRC 漏洞（正常定级发放奖励）**|
|---|---|
|**仅发现开放端口**：Nmap 扫出 8080、6379 开放，无任何未授权交互验证。|**未授权访问**：6379 Redis 无密码且可交互读取敏感键值，或存在未授权访问的 Actuator 端点泄漏环境变量配置。|
|**Self-XSS**：在个人简介栏输入弹窗代码，只有自己登录能看到，无法转嫁给其他用户。|**存储型 XSS**：在企业反馈中心留言植入恶意代码，客服/管理员在后台审查时自动触发并回传管理后台 Token。|
|**CORS 配置松散**：响应头返回 `Access-Control-Allow-Origin: *`，但该接口本身就是公开数据，无鉴权 Cookie。|**敏感 API 的 CORS 劫持**：带有用户身份凭据（Credentials: true）的敏感个人资产查询接口允许任意源请求，可跨域盗取用户数据。|
|**未启用安全 Header**：缺少 HSTS、X-Frame-Options 等基础响应头。|**有效点击劫持（Clickjacking）**：将缺少防护的关键转账、修改绑定手机号页面嵌入透明 iframe，且成功完成交互劫持 PoC。|


==SRC 核心评级梯队参考==

- **严重（Critical）**：直接获取核心系统权限（RCE、反序列化、任意文件上传执行代码）、核心内网漫游、绕过风控导致海量资金直接损失、核心业务全量数据拖库。
    
- **高危（High）**：越权直接修改/获取他人敏感核心数据（银行卡、身份信息、密码重置逻辑缺陷）、SQL 注入、高利用价值的 SSRF（可打内网核心服务）。
    
- **中危（Medium）**：影响普通业务的存储型 XSS、普通逻辑缺陷、不含高敏感信息的垂直越权、限制条件较多的任意文件读取。
    
- **低危（Low）**：有一定利用门槛的反射型 XSS、URL 任意跳转、非敏感信息泄露（接口返回内部 IP、员工测试账号工号）。


在 SRC 挖掘中，不要只关注技术表现形式（“这里有个弹窗”、“这里有个报错”），而要始终追问下一步：**“我作为攻击者，利用这个点能拿到什么权限？造成什么业务危害？”** 能够闭环回答这个问题的提交，才是一个真正的 SRC 漏洞。

1) 直接批量获取业务系统批量高价值信息泄露的漏洞。包括但不限于源代码压缩包泄漏、越权或者直接获取公司员工（姓名、电话、地址、证件、部门岗位等）批量（数据三元素组合一万条以上，数据二元素十万条以上）明文泄露和用户数据（姓名、电话、地址、证件等）的批量（数据三元素组合十万条以上，数据二元素组合百万条以上）明文泄露的漏洞。 
2) 业务系统管理后台弱口令、未授权访问管理平台并使用管理员功能等核心交互的漏洞。包括但不限于绕过认证直接获取管理后台权限、任意账号登录和密码修改。

5) 访问任意系统文件的漏洞。包括但不限于任意文件读取/下载/删除。
6) 子域名劫持、网页篡改，触发会跳转到非法网站的漏洞或情报。
7) 可完全回显、直接获取内网敏感信息的 SSRF 漏洞，须验证该漏洞能够访问内部网络，但禁止利用该漏洞对内网服务进行扫描。

【中危】 
1) 普通信息泄露的漏洞。包括但不限于未涉及敏感数据的SQL 注入、影响数据量有限或者敏感程度有限的越权、源代码等信息泄露。
2) 需要用户交互或其他前置条件才能获取用户身份信息的漏洞。包括但不限于包含用户、网站敏感数据的 JSON Hijacking、重要业务敏感操作（如支付类操作、修改个人账号敏感信息类操作）的 CSRF、一般业务存储型XSS。
3) 普通的逻辑缺陷和越权漏洞。包括但不限于越权增删改查用户/业务数据，非核心交互功能但会影响到用户/业务正常使用的越权。
4) 可攻击管理后台的 XSS 类攻击（需提供前台攻击位置，定位风险）漏洞。
5) 在业务预期外，单用户可批量获取大额现金优惠券（6 折及以下），获取数量大于 20 张。 
6) 仅图片回显、部分回显的 SSRF 漏洞。 
7) 非核心业务收费功能绕过付费，业务上第三方应用多次免费使用、绕过付费、绕过限制使用高级版功能等。如：非核心业务的延长产品试用期漏洞、基础版用户越权使用高级版用户功能等。 
8) 需点击链接进行交互的 OAuth 登录或绑定劫持。
9) 顺丰相关小程序密钥泄露，若未能证明该密钥可利用较大危害的API，最高评级【中危】 
10) 可实时批量爬取大量在途的顺丰运单号、时间以及未具体到详细地址但返回收寄件人地区的。如绕过滑块验证码、或存在接口可批量进行运单路由信息。

【低危】 
1) 轻微信息泄漏漏洞，包括但不仅限于路径信息泄漏、SVN 信息泄漏、phpinfo、URL 任意跳转等。 
2) 账号体系（包括但不仅限于顺丰会员账号体系）的撞库，爆破等问题。
3) 存在安全隐患，但利用难度较大的漏洞。 
4) 可访问内网，但无回显、无法获取信息或服务权限的SSRF 漏洞。
5) 可造成的实际危害较小的越权或流程缺陷。 
6) 只有在特定条件下才可以触发的漏洞。如只有在特定非常用浏览器下才可以触发的存储型 XSS。 
7) 仅影响同组织内用户非重要功能的漏洞。如：同组织内越权漏洞、存储型XSS等 8）无任何限制短信轰炸漏洞。针对单用户短信超 20 条每分钟。

【忽略】 
1) 实际业务安全性无影响的 Bug，包括但不仅限于业务系统功能缺陷、网页乱码、样式混乱、静态文件目录遍历、应用兼容性等问题。 
2) 无法利用/无实际危害的漏洞。包括但不限于无实际危害的越权、不可利用的Self XSS（无法分享给其他账号访问未收到后台记录）、pdf 格式的XSS 静态文件目录遍历、401 认证钓鱼、内网 IP/ 域名泄露、无敏感信息（如用户昵称、用户个人公开的信息、已脱敏的敏感信息等）的 JSON Hijacking 、横向短信轰炸、用户名枚举、swagger 类接口文档泄露和 Spring Actutor 健康检查模块信息泄露但不可进一步利用的漏洞等。 
3) 非顺丰业务的安全漏洞，如：仿冒顺丰域名业务的网站（如发现确认仿冒后给予感谢分）。 
4) 无法重现的漏洞，包括但不仅限于经审核人员多次确认无法重现的漏洞、无实际危害证明的扫描器结果等。 
5) 内部已知、正在处理的漏洞，包括但不限于：在其他平台公开的第三方软件漏洞，其他白帽子或内部已发现的漏洞。 
6) 测试环境(域名包含 sit、test、uat、stg 等)安全问题，专项活动除外。
7) 可批量获取优惠额度较小的优惠券（6 折以上），且优惠券不可转让或变现。
8) 部分风险过低或难以利用的漏洞。包括但不限于 PDF XSS、并发请求不重要的功能（如阅读量、点赞量、无法获利的积分等）、无法进一步利用的API Key 泄露、本地拒绝服务漏洞、基于理论未提供实际危害证明的漏洞。
9) 蜜罐系统漏洞不计分。 
10) 根据邮政行标 YZ/T 0131-2013《快件跟踪查询信息服务规范》，一线快件处理人员的姓名、电话、处理场所（指快件所在的快件处理场所的名称）为规定需公开的投递信息，不属于敏感数据。

## 业务系统场景中的SRC漏洞挖掘思路
在业务系统场景中进行SRC（Security Response Center）漏洞挖掘，核心在于“跳出单纯的代码审计，站在业务逻辑与产品架构的高度去审视系统”。大型厂商的主站和核心业务（如支付、用户中心）通常防护森严，==而边缘业务、子公司系统、内部OA、测试环境以及复杂的业务逻辑交互点往往是漏洞的高发区。==

以下是针对业务系统场景系统化的SRC漏洞挖掘思路与实战方法论：

==一、 资产收集与边界突破（寻找“灯下黑”）==

大厂的核心资产（如主站、主要APP）往往经过多轮渗透，常规漏洞较少。因此，扩大攻击面、寻找“灯下黑”是突破的关键。

1. **多维度资产映射**
    
    - **子域名字段与旁站**：利用 Layer、OneForAll、Amass 等工具，结合各大搜索引擎（FOFA、Shodan、Hunter、Quake）进行全网资产扫描，挖掘常被忽略的子域名。
        
    - **子公司与收购资产**：通过企查查、天眼查梳理企业的关联公司、全资子公司、控股公司。很多子公司或新收购的业务系统安全建设滞后，往往存在严重漏洞。
        
    - **IP段与C段探测**：针对目标企业的备案IP、云服务厂商（AWS、阿里云、腾讯云等）段进行存活扫描和端口探测。

2. **非标准环境与遗留系统**
    
    - **测试/预发布环境**：寻找形如 `test.`、`staging.`、`beta.`、`dev.`、`demo.` 的域名。这类环境往往关闭了WAF、开启了详细的 Debug 报错、甚至使用弱密码。
        
    - **老旧系统与历史版本**：企业常年迭代会留下旧版系统（如 `v1.`、`old.`），往往存在未修复的组件漏洞或低级逻辑缺陷。
        
    - **第三方合作与供应链系统**：如企业内部使用的供应商管理系统、客服系统、第三方外包运维平台等。

3. **敏感信息收集**
    
    - **GitHub/Gitee 泄露**：监控企业员工提交的代码，搜索敏感关键词（如 `internal_api`、`password`、`token`、`jdbc:mysql`、`oss_access_key`）。
        
    - **JS文件分析**：利用 JSFinder 或浏览器开发者工具，深入分析前端 JavaScript 文件，往往能挖出未授权的后台 API 接口、内部域名及敏感路径。




==二、 业务逻辑漏洞挖掘（核心战场）==

业务逻辑漏洞是SRC中评级较高（中危/高危）且不容易被自动化扫描器发现的类型，需要将自己代入为“产品经理”或“恶意用户”来思考。

1. **越权漏洞（IDOR / Access Control）**
    
    - **水平越权**：通过修改请求参数中的 `user_id`、`order_id`、`account` 等，查看或操作其他用户的数据。
        
        - _挖掘技巧_：多账号交叉测试（注册A、B两个账号），使用 Burp Suite 的 Autorize 插件进行自动化对比。
            
    - **垂直越权**：低权限用户（如普通注册用户）直接访问高权限接口（如管理员后台 API、删除/审核接口）。
        
        - _挖掘技巧_：收集管理员界面的所有 API 路径，将普通用户的 Cookie 替换进去尝试访问。
            
    - **未授权访问**：敏感接口未做任何身份校验。常见于 Swagger 文档、Actuator 监控端点、数据导出接口等。

2. **业务流程缺陷与状态机绕过**
    
    - **越过关键步骤**：例如在电商或充值流程中，直接跳过支付步骤（Step 2），通过修改参数直接请求成功回调接口（Step 4）。
        
    - **密码找回/修改逻辑缺陷**：
        
        - 验证码返回前端或在 Response 中可直接看到。
            
        - 验证码可爆破（未限制频率或位数过少）。
            
        - 越权修改（通过修改找回密码时的 `user_id` 或手机号，将新密码重置到自己控制的账号上）。
            
    - **交易与支付逻辑漏洞**：
        
        - 篡改金额、数量（如将商品价格改为负数、0.01元，或购买数量输入超大正/负数导致溢出）。
            
        - 相同订单号重复提交（利用优惠券、积分或余额）。

3. **条件竞争（Race Condition / 并发漏洞）**
    
    - 常见于涉及“加减分”、“优惠券领取”、“秒杀”、“提现”的场景。
        
    - _挖掘思路_：使用 Burp Suite 的 Turbo Intruder 插件，发送高并发请求，测试是否能在同一时间点绕过库存扣减、积分扣除或余额限制（例如用1份积分兑换多份商品）



==三、 经典Web与API漏洞的业务场景变体==

在业务系统中，常规漏洞往往需要结合特定的业务场景才能发挥最大危害：

1. **SQL 注入（SQLi）**
    
    - **高发场景**：复杂的后台管理系统查询、多条件组合筛选、数据导出（Excel/CSV 导出功能由于涉及复杂拼接，极易产生注入）。
        
    - **注意点**：现代系统多使用 ORM 框架（如 MyBatis），常规参数化查询较安全，重点关注使用 `$` 符拼接、order by 动态排序、in 查询等场景。

2. **服务器端请求伪造（SSRF）**
    
    - **高发场景**：支持通过 URL 导入数据的系统（如从外部链接导入头像、从指定 URL 抓取网页内容、Webhook 配置、云存储同步）。
        
    - **危害**：结合内部端口扫描、读取云主机元数据（Metadata）获取 AccessKey，甚至内网横向移动。

3. **不安全的文件上传与处理**
    
    - **高发场景**：头像上传、证件上传、附件导入。
        
    - **挖掘思路**：绕过前端校验、双文件头、畸形后缀、文件名控制导致的文件覆盖、配合解析漏洞，甚至利用 Office/PDF 解析组件触发反序列化或命令执行。

4. **敏感信息泄露与 API 滥用**
    
    - **接口未授权/未限流**：短信/邮件轰炸、撞库、利用撞库社工库批量收集用户信息。
        
    - **越权敏感信息泄露**：在某些查看详情或用户列表的接口中，返回了身份证号、手机号、完整地址等过多的敏感字段（未做脱敏）




==四、 高效挖掘的心法与提交流程==

1. **理解业务闭环**：挖洞前先完整体验一遍该业务系统的前后端交互流程，画出核心数据流向图。思考：“这个业务最核心的资产是什么？如果我是恶意攻击者，我最想破坏哪里？”
    
2. **善用工具链组合**：
    
    - 收集：FOFA / OneForAll / JSFinder
        
    - 代理与抓包：Burp Suite (配合各种优秀插件如 Autorize、Turbo Intruder、API Kit)
        
    - 扫描：Nuclei（编写或使用针对特定业务框架的 POC）、Sqlmap

3. **注重漏洞 PoC 的编写与报告质量**：
    
    - 提交 SRC 时，复现步骤要清晰、截图要完整、危害评估要客观。
        
    - 证明漏洞的同时注意合规与边界，切勿进行破坏性操作（如删除核心生产数据、拖库等），遵守授权范围

#### 常见渗透场景——渗透探讨
最容易找出漏洞的四大类型：


**==信息泄露、XSS、业务逻辑、越权==**


### SRC漏洞挖掘中的常见漏洞类型的测试思路及易出货的场景：
现代 SRC（安全应急响应中心）所面对的目标系统多采用前后端分离、微服务架构与成熟框架（如 Spring Boot、Django、Go），传统的直接注入类漏洞逐渐向微服务边缘下沉，==而**越权、业务逻辑、接口暴露与微服务交互缺陷**占据了高危漏洞的核心。==


==越权访问漏洞（IDOR / BOLA）==

产生场景

- **参数与身份解耦：** 后端服务在接收到请求后，直接取参数中的实体标识（如 `user_id`、`order_sn`、`account_id`）拼接 SQL 或检索 Redis，未比对当前登录态（Session / JWT claims）与该标识的归属关系。
    
- **微服务链路鉴权缺失：** API 网关验证了请求的登录凭证后，将请求透传至下游服务；下游服务默认网关已做全量鉴权，不再对具体对象资源进行细粒度校验


测试思路

- **双账号对照测试：** 准备权限对等的 A、B 账号（测试平行越权），以及低权账号和匿名态（测试垂直越权）。抓取 A 账号所有敏感操作（查看账单、修改收货地址、导出报表），将请求中的主体标识替换为 B 账号的标识。
    
- **参数结构嗅探：**
    
    - 转换传递方式：若 `GET /api/user/info?id=1001` 无效，测试 `POST /api/user/info` 并在 JSON Body 中携带 `{"id": 1002}`。
        
    - 参数污染（HPP）：测试 `?id=1001&id=1002`，某些解析器取后者可能覆盖鉴权参数。

- **数值规律分析：** 优先关注自增 ID、时间戳生成的弱伪随机 ID、Base64 编码的明文组合。对于 UUID，可通过前端其他功能（如个人主页、公开评论列表）收集目标用户的公有 UUID 进行跨接口注入





==业务逻辑与认证缺陷==


产生场景

- **状态机设计断层：** 业务流程依赖前端状态驱动，服务端接口缺乏前置步骤的校验闭环（例如：找回密码流程包含“验证验证码 -> 输入新密码 -> 提交保存”，保存接口未校验前置 Token）。
    
- **并发控制缺失：** 涉及资金、代金券、库存、签到奖励等关键变动时，底层数据库事务未加排他锁（`SELECT ... FOR UPDATE`）或分布式锁（Redis Redlock），导致在高并发下出现数据不一致。


测试思路

- **验证码与鉴权绕过：**
    
    - **回显截获：** 观察发送验证码的响应包（Response），排查验证码是否直接泄漏在 JSON 字段中。
        
    - **爆破与时效：** 抓包测试 4 位/6 位验证码接口是否存在频次限制（Rate Limit），尝试利用 X-Forwarded-For 伪造、多线程并发发包进行区间爆破。
        
    - **流程跳步与状态伪造：** 在验证码输入阶段故意输入错误，抓包将返回的 `{"code": 400, "msg": "fail"}` 篡改为 `{"code": 200, "msg": "success"}`，观察前端是否放行至改密页面，并测试最终提交接口能否成功执行。

- **条件竞争（Race Condition）：**
    
    - 使用 Burp Suite 的 Turbo Intruder 扩展或 HTTP/2 协议的多路复用（Single-packet attack），在毫秒级窗口内并发发送数十个相同的兑换、退款、点赞或提现请求




==服务端请求伪造（SSRF）==

产生场景

- **外部资源调用业务：** 系统提供“抓取远程图片/头像”、“Webhook 回调配置”、“URL 分享卡片预览”、“在线文档/PDF 转换渲染”等功能。
    
- **校验逻辑不完备：** 后端仅通过正则匹配字符串、黑名单校验 IP，或在校验 URL 后与发起实际请求间存在时间差，导致内网请求穿透。


测试思路

- **协议与伪协议嗅探：** 除了标准的 `http://`、`https://`，测试 `gopher://`（利用其攻击内网 Redis/FastCGI）、`file://`（读取本地配置文件）、`dict://`。
    
- **内网过滤绕过：**
    
    - **进制转换：** 将 `127.0.0.1` 替换为十进制整数 `2130706433`、十六进制 `0x7f000001` 或八进制 `017700000001`。
        
    - **特殊地址映射：** 利用 `0.0.0.0`、`127.1`、`localhost`，或指向内网的公开域名（如 `customer.127.0.0.1.nip.io`）。
        
    - **重定向穿透：** 搭建外部可控服务器，先返回 200 通过服务端白名单校验，随后通过 302/307 响应重定向到 `[http://192.168.](http://192.168.)x.x` 或云平台元数据接口。
        
    - **DNS 重绑定（DNS Rebinding）：** 利用 TTL=0 的双解析域名，第一次解析为合法公网 IP 绕过检查，第二次发起实际 HTTP 请求时解析为内部私有 IP。
        
- **云上元数据凭证利用：** 若目标部署在公有云环境（阿里云、腾讯云、AWS），重点尝试获取实例元数据（如 `[http://100.100.100.200/latest/meta-data/](http://100.100.100.200/latest/meta-data/)` 或 `[http://169.254.169.254/latest/meta-data/iam/security-credentials/](http://169.254.169.254/latest/meta-data/iam/security-credentials/)`）以截获临时 AccessKey/STS Token




==接口暴露与权限绕过==


产生场景

- **文档与脚手架未下线：** 生产环境未关闭 Swagger、Knife4j、Druid 监控台、Actuator 等调试框架。
    
- **路径解析不一致（Parser Differentials）：** Nginx、Apache、API 网关与后端容器（Tomcat、Spring、Node.js）对 URL 路径的解析规范存在差异，导致访问控制规则被绕过。


测试思路

- **前端静态资源逆向：**
    
    - 深度检索打包后的 JS 文件（`app.*.js`、`chunk-vendors.*.js`），使用正则提取接口路径、硬编码的 API Key、测试环境域名与开发注释。
        
    - 检索未在前端 UI 呈现的隐藏管理接口（如 `/api/admin/system/export`）。

- **框架调试端点扫描：**
    
    - Spring Boot：测试 `/actuator/env`（环境变量/密码泄露）、`/actuator/heapdump`（内存转储取证）、`/actuator/gateway/routes`（路由泄露）。
        
    - 数据库与API文档：测试 `/druid/index.html`、`/swagger-ui.html`、`/v2/api-docs`。

- **路径规范混淆绕过：**
    
    - 利用分号截断（Spring 特性）：`GET /api/v1/auth;admin/delete`
        
    - 规范化目录穿越：`/api/v1/user/..;/admin/dashboard`
        
    - 双重 URL 编码：`%252e%252e%252f`




==任意文件上传与解析缺陷==


产生场景

- **校验规则可被规避：** 后端仅通过客户端 `Content-Type`、文件头魔法字节（Magic Bytes）或简单的后缀黑名单过滤，未重命名文件或存储在直接具备执行权限的 Web 目录下。
    
- **复杂格式解析风险：** 引入第三方库处理 SVG、PDF、Office 文档，未关闭外部实体解析（XXE）或未做图片渲染沙箱隔离。


测试思路

- **后缀多重变异：**
    
    - 大小写与黑名单替代：`.pHp`、`.phtml`、`.jspx`、`.cer`、`.ashx`。
        
    - Windows 路径特性与空格截断：`shell.php.`、`shell.php::$DATA`、`shell.php` 。
        
    - 配合解析特性的多后缀：`shell.php.jpg`（排查 Apache / Nginx 早期特定配置下的多后缀解析风险）。

- **格式注入拓展：**
    
    - **SVG 注入：** 上传 XML 格式的 `.svg` 图像，在其中嵌入 `<script>` 标签构造存储型 XSS。
        
    - **XXE 盲注：** 上传包含外部实体引用的 DOCX、XLSX 或 SVG，观察是否向外部 DNS/HTTP 监听平台发起带外请求（OOB）。











**==弱口令==**

**==注入与表达式执行（SQLi / SSTI）==**

产生场景

- **非标场景动态拼接：** 尽管广泛使用了 Mybatis、Hibernate、ORM 等预编译方案，但在表名（`FROM ${tableName}`）、排序字段（`ORDER BY ${sortField}`）、批量操作（`IN (${ids})`）等无法使用占位符的地方依然使用了字符串拼接。
    
- **模板引擎动态渲染：** 邮件发送系统、自定义页面生成功能中，直接拼接用户输入内容送入模板引擎（FreeMarker、Velocity、Thymeleaf）计算


测试思路

- **二次与隐蔽注入点识别：**
    
    - 规避主查询参数，优先测试分页大小（`pageSize`）、排序方向（`sortOrder=desc`）、导出接口的自定义字段。
        
    - JSON 字段内注：针对支持 JSON 数据类型的数据库，测试 JSON Key 或抽取函数内的拼接点。

- **盲注探测：**
    
    - 时间盲注：针对过滤报错信息的接口，使用 `SLEEP(5)` 或利用正则耗时函数观察网络延迟。
        
    - 报错注出：利用 `extractvalue()`、`updatexml()`、`convert()` 触发类型转换错误回显敏感数据。

- **表达式与模板注入（SSTI）：**
    
    - 输入 `${7*7}`、`{{7*7}}`、`#{7*7}` 观察返回结果是否被计算为 `49`，根据报错信息识别具体引擎，随后利用反射或内置上下文对象实现环境逃逸




**==SQL 注入==**
漏洞原理：用户输入未被正确过滤，导致恶意代码被解析执行

测试思路： 输入验证测试：在输入框（如搜索栏、登录表单）中插入特殊字符（单引号'、分号;、括号()），观察系统响应是否异常（如 SQL 报错、命令执行结果）。 
工具辅助测试：使用 Burp Suite 的 Intruder 模块批量发送注入 Payload，或用sqlmap 自动化检测 SQL 注入。 
盲注场景测试：通过条件语句（如 IF(1=1, SLEEP(5), 1)）判断系统是否存在无回显的注入漏洞




易出货的场景： 
1. 使用工具捡洞，有师傅有介绍到，或使用盲注 
2. 排序注入出货率较高，各种表单排序 
3. 数据包返回报错”SQL 注入语句”













**==存储型跨站脚本攻击==**
漏洞原理：存储型 XSS 的特点是攻击 Payload 被永久存储在服务器端（如数据库、文件系统），当用户访问包含恶意代码的页面时，浏览器会自动执行 Payload。与反射型XSS 相比，其危害更持久，影响范围更广（如针对所有访问该页面的用户）。

**==敏感信息泄露==**
挖掘敏感信息泄露的诀窍：细致+细致+细致(Hae) 

任何存在用户数据交互的都不能放过


1. 第一个问题：哪些地方会存在敏感信息 

第一个问题：哪些是敏感信息（一般的想法：手机号码、身份证号码、住址信息）

个人身份信息：包括姓名、身份证号码等。 

账号与凭证信息：例如用户名、密码（/get/1）、安全问题答案、身份验证信息等。 

财务信息：包括银行账号、信用卡号码、支付宝账号等金融相关信息。（比较牵强） 医疗保健信息：涉及健康状况、病历记录、医生诊断等医疗信息。

个人通讯信息：包括电话号码、电子邮箱地址、通讯录等。

商业机密信息：如公司的商业计划、营销策略、客户数据等。

法律文件与合同：包括法律文件、合同协议、诉讼文件等。

比较常见挖掘到的敏感信息： 手机号码、账户、密码、身份证号码、银行的财务信息、内部报告、商业机密、客户资料等



2. 第二个问题，哪些地方会存在敏感信息（存在数据交互的地方）
用户输入界面：例如登录、注册、表单提交等，存在未加密的传输、缺乏输入验证等问题。(敏感信息未脱敏 1872921011 187xxxxxxx 敏感信息get 型传输) 

数据库操作：包括对数据库的读取、写入、更新、删除等操作，未经适当的权限控制和加密存储。（增删改查-用户交互（数据库的交互））

文件存储与传输：未加密的文件存储、文件传输过程中的中间人攻击风险等。（下载文件、发送文件，1.pdf） 

日志记录：系统日志中可能会记录用户的操作行为，如果未经适当处理，可能导致敏感信息泄露。（accesstoken、user、password、数据包、文件）

第三方集成：与外部系统、服务或 API 的集成，未对数据传输和存储进行充分的安全控制。（未授权，A 系统给 B 系统）地图 api 付费的接口

通讯与消息传递：包括电子邮件、即时消息等通讯方式，未加密的传输可能导致信息泄露。（聊天，与客服聊天获得他人的聊天记录 高危3k）


打印与备份：未经加密的打印、备份数据，存储介质的丢失或被盗等情况。（SSRF）

系统管理员权限：拥有系统管理员权限的人员可能能够访问到系统中的敏感信息。（拥有高权限的系统 能直接访问到敏感信息 911xxxx111）（在工作中需要对其进行严格管理）
