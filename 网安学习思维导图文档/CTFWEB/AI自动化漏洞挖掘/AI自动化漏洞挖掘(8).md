
# 集群化多Agent渗透测试平台开发
开发集群化多 Agent 渗透测试平台的核心在于**解耦高层次决策与高频网络 I/O**，通过**层次化调度架构（Hierarchical Architecture）** 结合**黑板模型（Blackboard Pattern）**管理动态资产状态，并建立严格的**确定性执行沙箱与范围红线（Scope Guardrails）**。




==一、 系统拓扑与核心分层架构==

平台整体推荐采用控制面与执行面分离的三层架构：

例：
![](Pasted%20image%2020261006164024.png)



1. **控制面（Control Plane / Master）：** 负责目标范围校验、攻击树（Attack Tree）分解、任务分发与全局仲裁。不直接执行网络发包操作。
    
2. **状态与知识总线（Blackboard / Message Bus）：** 维护资产拓扑与漏洞状态，所有 Agent 共享当前已发现的事实（Facts），避免重复探测。
    
3. **执行集群（Worker Cluster）：** 基于容器化运行的垂直领域 Agent 实例，按需从队列拉取子任务，调用安全工具链并回传结构化观察数据（Observations）。





==二、 Agent 职能专业化拆分与协作范式==

通用大模型直接执行全流程渗透极易出现上下文爆炸与目标漂移，必须按专业领域拆分为细粒度 Agent：


|**Agent 角色**|**核心职责**|**输入上下文**|**工具集成方式**|
|---|---|---|---|
|**Planner / Orchestrator**|任务解构、优先级排序、全局状态评估与重规划|授权范围、当前资产图谱、发现清单|不直接外联工具，只操作任务队列与图谱数据库|
|**Recon Agent**|外部资产发现、端口指纹识别、目录爆破、子域名挖掘|目标域名/IP 段、探测深度阈值|封装 Nmap、Subfinder、Httpx，通过标准化 JSON 解析器回传|
|**Audit Agent**|代码/接口逻辑分析、参数敏感度判断、指纹已知漏洞匹配|目标端点结构、请求/响应样本、技术栈指纹|集成 Nuclei 模板库、自定义扫描规则引擎、语义推断|
|**Verify Agent**|确定性验证（PoC 验证），严禁破坏性行为|漏洞候选特征、PoC 逻辑、目标环境参数|沙箱内执行无害验证脚本（如基于 OOB/DNSLog 回显确认）|
|**Report Agent**|聚合完整攻击链路、提取利用证据、输出修复方案|验证成功的利用链拓扑、关键请求响应包|模板引擎生成标准安全评估报告|



协同机制：事件驱动流水线 + 局部辩论

- **事件驱动触发：** Recon Agent 发现新端口（如 `8080/http`）并在黑板写入事实后，自动触发 Audit Agent 对该服务的技术栈指纹与端点进行探索，无需 Master 逐一轮询。
    
- **低置信度双 Agent 辩论：** 当 Audit Agent 给出置信度低于 0.7 的漏洞假说时，调度 Verification Agent 与 Reviewer Agent 进行上下文交叉比对，排除伪阳性后再申请执行验证。





==三、 共享状态与资产攻击图设计（Asset Graph）==

大模型上下文窗口有限，**严禁将工具的原始扫描输出全量塞入 Prompt**。必须在存储层维护图结构数据库（如 Neo4j）：

例：
![](Pasted%20image%2020261006164222.png)

- **Observation Condensation（观察提炼）：** 工具输出必须经过确定性代码清洗。例如 Nmap XML 输出清洗为精简 JSON 字典；HTTP 响应提炼为状态码、指纹头字段与响应体特征摘录。
    
- **增量拓扑注入：** Agent 每次行动前，根据当前关注的节点，从 Neo4j 查询该节点及其 2 度关系子图，将结构化拓扑动态渲染进 Prompt 上下文中。




==四、 集群调度与高并发资源隔离==

1. **执行沙箱隔离（Containerized Sandbox）：**
    
    - 每个执行工具的 Worker 运行于轻量级无状态 Pod（如 Kubernetes Job 或 Docker 容器）。
        
    - 采用 gVisor / Kata Containers 实现系统调用隔离，防止 Agent 生成的脚本或调用的第三方工具在本地产生非预期副作用。

2. **流量网关与代理池集成：**
    
    - 所有 Worker 的外部网络流量统一路由至集中式代理网关。
        
    - 网关实现**分布式令牌桶算法（Token Bucket）**，针对单个目标 IP 严格限制并发请求数（如每秒请求上限 QPS=5），规避拒绝服务风险与目标防爆破封禁。

3. **异步任务流编排：**
    
    - 采用 Celery / Temporal / Ray 管理长耗时任务。将"端口全扫描"与"敏感接口研判"拆分为不同 QoS（服务质量）等级的任务队列，防止阻塞核心规划线程。





==五、 确定性红线防护体系（Scope Guardrails）==

在自动化多 Agent 场景中，防止失控（Out-of-Scope）是系统的第一生命线。红线拦截应设于**代码硬逻辑层**，严禁仅依靠 Prompt 软性提示：

例：
![](Pasted%20image%2020261006164420.png)

1. **Pre-flight 范围网关：** 针对 Agent 决定的每个 URL、IP、域名实施静态网络校验。若目标不属于授权范围清单（Target Whitelist），直接由拦截网关抛出 `403 Target Out of Bounds` 异常并中止当前子任务。

2. **动作分级与高危熔断：**
    
    - **Level 1（被动/只读分析）：** HTTP GET 请求、指纹比对、版本匹配 -> 允许全自主执行。
        
    - **Level 2（非破坏性验证）：** 触发带有随机 Canary 值的无害回显验证（如 DNSLog 探测） -> 自动执行但需记录全量审计日志。
        
    - **Level 3（破坏性/状态改变操作）：** 任何涉及数据写入、配置覆写、提权尝试的操作 -> 强制进入 **Human-in-the-Loop（人工确认门禁）**，生成可解释的行动计划等待工程师手动授权。




==六、 工程落地推进路线==

1. **阶段一：协议与工具标准化（MCP / Schema 规范）**
    
    - 为常用扫描工具（Nmap, Httpx, Nuclei）编写符合 MCP（Model Context Protocol）或 JSON Schema 的标准接口，确保输入/输出 100% 具备确定性数据结构。

2. **阶段二：黑板状态机搭建**
    
    - 使用 Redis 维护全局任务状态队列，PostgreSQL/Neo4j 存储标准化后的资产拓扑树，编写基于规则的状态迁移逻辑（如 `Discovered -> Fingerprinted -> Audited -> Verified`）。

3. **阶段三：双 Agent 验证闭环测试**
    
    - 部署单一 Planner Agent 与两个 Worker（Recon + Verification）。在本地搭建的靶场（如 Vulhub 容器）内进行封闭测试，验证从资产录入到输出验证报告的单闭环逻辑。

4. **阶段四：集群化扩展与安全熔断器集成**
    
    - 将 Worker 容器封装为 Kubernetes Deployment，集成前置代理网关、CIDR 范围校验钩子与分布式限流，形成具备弹性扩容与红线约束的完整集群。











集群化的目的：方便管理、统一控制、主机集群化、agent集群化。

有条件可将agent放置在Docker容器中进行作业==(保障其安全性)==



渗透测试Agent开发测试思路：
1. 了解什么是提示词、什么是Skill；
2. 写skill、改Skill（让Agent在信息搜集的时候不仅仅使用单一工具进行测试）；
3. 了解什么是工作流(workflow)、什么是多Agent，进行提效；
4. 集群化Agent测试，使用简单skill完成大量确定性任务；



解决渗透测试中AI安全边界的方法：
1. 使用ai管理agent的测试行为；
2. 通过提示词或者Skill规定安全边界==(无法完全拦截危险操作，尤其是多Agent执行时，子Agent基本上不会管安全边界)==

边界限制：
1. 只对Web站点进行测试；

3. 不破坏业务以及业务数据；

2. 只要有实际价值的低危、中危、高危、严重漏洞，不要没有实际意义的漏洞
3. 优先挖掘“未授权访问”类型的漏洞
