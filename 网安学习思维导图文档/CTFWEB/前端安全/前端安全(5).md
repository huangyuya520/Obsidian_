
# CSRF攻击介绍


![](e92c4666577023ab4451061a60929b4b_720.jpg)

**CSRF（Cross-Site Request Forgery，跨站请求伪造）** 是一种针对 Web 应用程序的受迫性攻击手段。攻击者诱导受害者在其已经登录的目标网站上，在不知情的情况下以受害者的身份执行非预期的敏感操作（如转账、修改密码、发帖等）。

其核心本质在于：**目标网站过度信任来自用户浏览器的身份凭证（主要是 Session Cookie），而浏览器在发送跨站请求时会自动携带该目标站点的 Cookie**





==攻击成立的前提与完整流程==

CSRF 攻击并不窃取用户的账号或密码本身，而是“借刀杀人”，必须同时满足两个核心条件：

1. **已认证会话**：受害者在目标站点 A 成功登录，并在浏览器中保留了有效的认证凭据（Cookie/Session）。
    
2. **跨域触发诱导**：受害者在未退出站点 A 的情况下，通过同一浏览器访问了攻击者预设的恶意站点 B




==攻击链路四步走==

1. **登录受信站点**：用户访问并登录银行站点 `bank.com`，服务器颁发认证 Cookie 存储于用户浏览器中。
    
2. **诱导访问恶意网页**：攻击者通过钓鱼邮件、论坛发帖诱导用户点击并访问恶意站点 `evil.com`。
    
3. **静默触发跨站请求**：`evil.com` 页面内的代码自动向 `bank.com` 发送一个转账请求（如向攻击者账户转账 1000 元）。
    
4. **凭据自动携带与执行**：用户的浏览器根据 HTTP 机制，向 `bank.com` 发送请求时会自动附带其保存在本地的 `bank.com` 认证 Cookie。`bank.com` 服务端验证 Cookie 有效，误以为是用户本人的意图，从而执行转账

2. 依赖“浏览器自动携带Cookie”。
3. ==多用于转账、改密、发帖等敏感操作。==







==常见攻击代码形式==


1. ==GET 型 CSRF==

如果服务端的关键操作接口允许通过 GET 请求触发，攻击者只需在恶意页面中嵌入标准的 HTML 标签（如 `<img>`、`<script>`、`<iframe>`）：

例：
```
<!-- 用户加载此网页时，浏览器会自动尝试加载图片，从而静默发出 GET 转账请求 -->
<img src="https://bank.com/transfer?toAccount=hacker&amount=1000" style="display:none;" />
```





2. ==POST 型 CSRF==

若服务端接口要求 POST 请求，攻击者可在恶意页面中构造一个隐藏的 `<form>` 表单，并用 JavaScript 在页面加载完毕时自动提交：

==CSRF 与 XSS 的对比==

|**比较维度**|**CSRF（跨站请求伪造）**|**XSS（跨站脚本攻击）**|
|---|---|---|
|**信任关系**|网站**信任用户的浏览器**（盲信其自动携带的凭据）|用户**信任网站的代码**（相信网页上运行的脚本是安全的）|
|**攻击手段**|冒充用户身份发送请求，**借权限执行操作**|在目标网页注入并运行恶意 JavaScript|
|**数据读取能力**|**无法读取**目标站点的响应数据（受 SOP 隔离）|**可直接读取**页面 DOM、Cookie、LocalStorage 等敏感数据|
|**主要防御方案**|CSRF Token、Cookie `SameSite`、Origin 校验|输入过滤转义、HTML 内容编码、CSP（内容安全策略）|

# CSRF攻击应用场景

## 在”转账“业务中的CSRF攻击
在资金转账业务中，CSRF 攻击之所以极具破坏力，==是因为转账是**直接产生财务资产转移的高危写操作**==。==当银行或支付系统的接口缺乏交易意图确认机制，且过度依赖浏览器自动携带的会话凭证（Cookie）时，攻击者即可在受害者毫无感知的情况下完成越权转账==



1. ==脆弱转账接口的设计缺陷根源==

一个能够被 CSRF 成功利用的转账接口通常具有以下特征：

1. **凭证的隐式携带（Ambient Authority）**：转账请求合法性的判定依据完全依赖浏览器在请求中自动注入的会话 Cookie（如 `JSESSIONID`、`token_cookie`）。
    
2. **请求参数确定且易于预测**：转账所需的参数仅包含收款账号（`toAccount`）、金额（`amount`）等公开或攻击者已知的字段。
    
3. **缺乏不可伪造的上下文校验**：未对请求来源（Origin/Referer）做白名单匹配，且未要求请求携带与用户当前页面绑定的动态校验物（如 Anti-CSRF Token、支付密码、短信验证码）

4. ==转账业务场景下的深度防御架构==

金融级转账场景不可采用单一策略，必须采用**纵深防御体系（Defense-in-Depth）**：

|**防御层级**|**实施手段**|**机制与防护效果**|
|---|---|---|
|**业务鉴权层（最彻底）**|**关键操作二次确认（Step-Up Auth）**|在最终扣款接口强制要求提供仅当前用户知晓的凭据：<br><br>  <br><br>• 独立支付密码（区别于登录密码）<br><br>  <br><br>• 动态短信/邮件验证码（OTP）<br><br>  <br><br>• 基于 FIDO2 / WebAuthn 的生物识别或 UKey 签名<br><br>  <br><br>即使黑客成功触发跨站请求，因缺失二次校验码，请求必然失败。|
|**会话与 Token 层**|**交易绑定型 Anti-CSRF Token**|不仅要求携带随机 Token，而且将 Token 与**本次交易的关键上下文**绑定：<br><br>  <br><br>`Token = HMAC(SessionID + toAccount + amount + Timestamp)`<br><br>  <br><br>黑客即便跨站伪造请求，也无法预测该加密 Token。|
|**浏览器策略层**|**严格隔离 Cookie（SameSite 强化）**|登录状态的 Cookie 必须打上安全标记：<br><br>  <br><br>`Set-Cookie: SESSION=...; Secure; HttpOnly; SameSite=Strict`<br><br>  <br><br>`SameSite=Strict` 会在所有跨站跳转和跨站嵌入场景中完全拦截 Cookie 发送。|
|**网络网关层**|**Origin / Referer 严控拦截**|网关（如 API Gateway、Nginx）统一拦截：<br><br>  <br><br>1. 必须存在 `Origin` 头（非跨域情况若缺失则校验 `Referer`）；<br><br>  <br><br>2. `Origin` 必须匹配本行白名单域，严禁宽松正则或子域名泛解析。|


5. ==金融系统安全设计准则：意图确认机制（Intent Confirmation）==

转账功能防护的核心原则是“意图不可代理”。

在架构设计中，一次完整的转账必须被拆分为两阶段状态机：

1. **预检与意图创建阶段（Pre-check / Intent Creation）**：
    
    - 用户输入收款人及金额，调用接口生成一个临时的 `TransactionID`，并在服务端生成一个与该交易及用户状态强绑定的短期挑战（Challenge）。
        
2. **确认与结算阶段（Commit / Execution）**：
    
    - 必须由用户显式触发确认，将 `TransactionID` 连同二次身份验证因子（动态口令、硬件签名）一次性提交给执行接口。
        

只要严格剥离了单纯依赖浏览器 Cookie 自动放行的逻辑，CSRF 攻击在转账场景中就失去了所有利用空间

## 在”密码修改“业务中的CSRF攻击
在 Web 安全中，“修改密码”业务是 CSRF 攻击最具杀伤力的目标之一。==与单纯的转账或发帖不同，密码修改接口一旦被 CSRF 攻破，其直接后果是**账户完全接管（Account Takeover, ATO）**——攻击者将受害者的凭据篡改为已知密码，并在会话重置后永久锁死原用户==



1. ==脆弱密码修改接口的设计缺陷==

能够被 CSRF 攻击成功的密码修改接口，通常存在以下架构缺陷中的至少一项：

1. **未校验原密码（Old Password）**：接口仅接收 `new_password` 和 `confirm_password`，完全依赖当前请求中的 Session Cookie 来确认身份。
    
2. **缺乏状态绑定校验（No CSRF Token）**：请求体中未包含不可预测的抗重放/抗跨站凭证。
    
3. **接口支持松散的请求方式或编码**：允许使用 GET 方法修改密码，或后端框架宽容接收来自 `<form>` 的 `application/x-www-form-urlencoded` 数据。
    
4. **Cookie 未配置严格的跨站隔离**：Session Cookie 未设置 `SameSite=Strict` 或 `SameSite=Lax`

# CSRF防御介绍

## 在客户端浏览器设置`SameSite Cookie`机制防御CSRF攻击
`SameSite` 是 HTTP 响应头 `Set-Cookie` 中的一个安全属性，==它通过**限制跨站请求（Cross-Site Request）时浏览器的 Cookie 发送行为**，从源头上切断跨站请求伪造（CSRF）赖以生存的“凭证自动附带”机制==





1. ==CSRF 攻击本质与 SameSite 的切入点==

传统 CSRF 攻击的核心在于浏览器的**环境凭证自动附带机制（Ambient Authority）**：当受害者在第三方恶意网页 `attacker.com` 触发对目标站点 `bank.com` 的请求（如表单提交、图片加载）时，浏览器会无条件自动带上受害者在 `bank.com` 下的登录 Cookie。

`SameSite` 的设计理念是**将 Cookie 与发起请求的上下文站点绑定**。当浏览器发现请求来源于其他站点（跨站）时，会根据 `SameSite` 策略主动拦截并剥离该 Cookie，服务端因接收不到会话凭证而拒绝执行未授权操作

例：
```
Set-Cookie: session_token=abc123xyz; Path=/; Secure; HttpOnly; SameSite=Lax
```






2. ==“同站”（Site）与“同源”（Origin）的界定==

理解 `SameSite` 的前提是区分 **Site** 与 **Origin**：

- **Origin（同源）：** 要求 **协议（Scheme）+ 域名（Host）+ 端口（Port）** 三者完全一致。
    
- **Site（同站）：** 基于公共后缀列表（Public Suffix List），由 **有效顶级域名（eTLD）+ 二级域名（+1）** 决定。现代浏览器已全面启用 **Schemeful Same-Site**，即同时校验协议与 eTLD+1。



| 源 A                                                    | 源 B                                                    | 是否同源 (Same-Origin) | 是否同站 (Same-Site) |
| ------------------------------------------------------ | ------------------------------------------------------ | ------------------ | ---------------- |
| `[https://a.example.com](https://a.example.com)`       | `[https://b.example.com](https://b.example.com)`       | ❌ 不同源              | **同站**           |
| `[https://example.com:8080](https://example.com:8080)` | `[https://example.com:9000](https://example.com:9000)` | ❌ 不同源              | **同站**           |
| `[http://example.com](http://example.com)`             | `[https://example.com](https://example.com)`           | ❌ 不同源              | ❌ **跨站**（协议不一致）  |
| `[https://bank.com](https://bank.com)`                 | `[https://evil.com](https://evil.com)`                 | ❌ 不同源              | ❌ **跨站**         |






3. ==SameSite 的三种策略详解==

==`SameSite` 属性共有三种可选值：`Strict`、`Lax` 和 `None`。==


1. `SameSite=Strict`（完全禁止跨站携带）

- **行为：** 无论是任何跨站请求，哪怕是用户在外部网页上点击普通超链接（`<a>`）跳转到目标网站，浏览器也**绝对不会**附带该 Cookie。
    
- **安全性：** 最高，完全杜绝所有外部发起的 CSRF。
    
- **副作用：** 显著影响用户体验。例如用户从邮件或搜索引擎点击已登录网站的链接进入页面时，初次加载将处于“未登录”状态，必须在站内二次跳转或刷新后才能读取到会话。


2. `SameSite=Lax`（宽松模式，现代浏览器默认）

- **行为：** 阻止大多数具有修改性质或子资源的跨站请求发送 Cookie，但在满足以下**两个必要条件**时仍允许携带：
    
    1. **顶层导航（Top-level Navigation）：** 请求会改变浏览器地址栏 URL（如 `<a>` 链接跳转、`window.location.href` 重定向）。
        
    2. **安全只读的 HTTP 方法（Safe Method）：** 必须是 `GET`、`HEAD` 等只读请求，跨站的 `POST`、`PUT`、`DELETE` 绝不携带。
        
- **安全性：** 极佳地平衡了安全性与可用性，覆盖绝大多数基于跨站表单提交与子资源注入的 CSRF 攻击。


3. `SameSite=None`（放行跨站，无防御能力）

- **行为：** 在所有同站与跨站请求中均正常携带 Cookie。
    
- **约束条件：** 现代浏览器强制要求设置 `SameSite=None` 时必须同时声明 `Secure` 属性（即仅限 HTTPS），否则该 Cookie 会被浏览器直接丢弃。通常用于第三方内嵌服务或 SDK（如第三方支付、嵌入式聊天插件）







4. ==不同跨站场景下的 Cookie 发送矩阵==

|**跨站触发场景**|**常见 HTML / API 示例**|**SameSite=Strict**|**SameSite=Lax**|**SameSite=None**|
|---|---|---|---|---|
|**超链接跳转**|`<a href="[https://site.com/home](https://site.com/home)">`|❌ 拦截|**发送**|**发送**|
|**预加载链接**|`<link rel="prerender" href="...">`|❌ 拦截|**发送**|**发送**|
|**跨站 GET 表单**|`<form method="GET" action="...">`|❌ 拦截|**发送**|**发送**|
|**跨站 POST 表单**|`<form method="POST" action="...">`|❌ 拦截|❌ **拦截**|**发送**|
|**嵌入式图片 / 脚本**|`<img src="...">` / `<script src="...">`|❌ 拦截|❌ **拦截**|**发送**|
|**内嵌页面**|`<iframe src="...">`|❌ 拦截|❌ **拦截**|**发送**|
|**异步请求**|`fetch()` / `XMLHttpRequest`|❌ 拦截|❌ **拦截**|**发送**|






6. ==使用 SameSite 防御 CSRF 的局限与注意事项==

虽然 `SameSite=Lax` 是防御 CSRF 的坚实基础，但不能将其视为唯一的银弹：

1. **滥用 GET 请求导致状态变更：** 如果接口未严格遵守 HTTP 规范，使用 `GET` 请求处理敏感业务（如 `GET /user/delete?id=1`），攻击者只需诱导用户点击普通链接，`SameSite=Lax` 就会在顶层导航中带上 Cookie，导致防御彻底失效。

2. **同站多租户与子域名接管风险：** `SameSite` 的判定单位是 **eTLD+1**。如果攻击者通过漏洞控制了同一主域名下的子域（如 `attacker.example.com`），从该子域向 `api.example.com` 发起的请求仍属于 **同站请求（Same-Site）**，浏览器会全量携带 Cookie。

3. **Lax + POST 临时宽限机制历史遗留：** 早期 Chromium 内核对未设置 SameSite 的新 Cookie 曾有 “2 分钟内允许跨站 POST 发送” 的过渡窗口（Lax-allowing-unsafe），生产环境必须**显式在后端设置 `SameSite=Lax` 或 `Strict`**，切勿依赖浏览器的隐式默认行为。

4. **纵深防御建议：** 在设置 `SameSite=Lax/Strict` 的同时，关键业务应配合以下措施：
    
    - **CSRF Token**（双重提交 Cookie 或服务器验证令牌）；
        
    - **Sec-Fetch-* 元数据头校验**（通过 `Sec-Fetch-Site: cross-site` 直接在网关层拦截可疑跨站请求）；
        
    - **严格区分 HTTP 动词**，对状态变更操作仅开放 `POST`、`PUT`、`DELETE`





`SameSite` 的目标:
让浏览器在跨站请求时，有选择地不发送Cookie，从而减少CSRF风险。

## 在服务器测设置CSRF_Token校验机制防御CSRF攻击
CSRF Token（跨站请求伪造令牌）是目前业界应用最广泛、最彻底的服务器端 CSRF 防御机制，其==核心思想是：**破坏请求的“不可知性”与“凭证隐式自动提交”特征，强制客户端在发起敏感写操作时显式提交一个攻击者无法预测、无法读取的临时机密值**==



1. ==核心防护原理==

浏览器向跨域站点发起请求时，会自动携带目标站点的 Cookie；但受限于浏览器的**同源策略（Same-Origin Policy, SOP）**，第三方恶意网站（如 `attacker.com`）**无法通过 JavaScript 读取目标网站（如 `bank.com`）的 DOM 结构、响应内容或只读 Cookie**

2. ==三种主流的 CSRF Token 实现架构==

根据服务器状态管理与前后端架构差异，CSRF Token 在工程上主要有三种实现形式：

1. 同步器令牌模式（Synchronizer Token Pattern, STP）

- **适用场景**：传统的服务端渲染架构（JSP、Thymeleaf、Django Template、PHP 等）。
    
- **工作机制**：
    
    1. 用户认证通过后，服务器在会话（Session / Redis）中存储一个高强度的伪随机数 `csrf_token`。
        
    2. 当服务端渲染表单页面时，将该 Token 注入到表单的隐藏字段中：


例：
![](Pasted%20image%2020260902182305.png)
	3. 用户提交表单时，服务器拦截器从请求体中提取 `_csrf`，与当前 Session 中存储的 `csrf_token` 进行恒定时间比较（Constant-time comparison）。

- **优缺点**：安全性最高、防伪造最彻底；但在无状态微服务集群或纯静态 SPA 前后端分离架构下，会增加 Session 存储与多节点同步的开销。




2. 双重 Cookie 提交模式（Double Submit Cookie）

- **适用场景**：前后端分离架构、单页面应用（SPA）、无状态 RESTful API（无服务器 Session）。
    
- **工作机制**：
    
    1. 服务器生成一个随机 Token，通过 `Set-Cookie` 写入客户端（此 Cookie 不能设置 `HttpOnly`，以便前端脚本能够读取）。
        
    2. 前端框架（如 Axios、Fetch）在发送状态变更请求（POST/PUT/DELETE）时，读取该 Cookie 值，并将其注入到自定义 HTTP 请求头中（如 `X-CSRF-Token` 或 `X-XSRF-Token`）。
        
    3. 服务端中间件提取请求头中的 `X-CSRF-Token` 与 Cookie 中的对应值进行比对，一致则放行。

- **优缺点**：服务器完全无状态，不需要集中式存储；但对子域劫持存在脆弱点（如果同根域下的子域遭受 XSS，攻击者可通过设置上级域 Cookie 覆写受害者的 CSRF Cookie）。



3. 基于 HMAC 的无状态加密令牌（Encrypted Token Pattern）

- **适用场景**：既需要无状态架构，又需要防御子域 Cookie 污染的系统。
    
- **工作机制**：
    
    1. 服务器不存储 Token，而是利用服务端密钥将 `用户ID + 时间戳 + 随机数` 进行哈希计算：
        
        $$\text{Token} = \text{Payload} + \text{HMAC}_{\text{Secret}}(\text{Payload})$$
        
    2. 客户端提交时带上该签名 Token。
        
    3. 服务器收到后，使用同一密钥重新验签，并核对 Payload 中的时间戳是否过期、用户 ID 是否与当前认证会话一致。

- **优缺点**：完全免除 Session 存储负担，防篡改性强；但需要消耗一定的 CPU 算力进行哈希验签。







CSRFToken机制的核心原理：
服务器生成一个一次性随机标识，验证请求来自合法用户


CSRF Token机制流程：
1. 用户访问页面一服务器生成Token并下发。
2. 页面中的表单或JS请求中携带该Token。
3. 用户提交请求时，浏览器带上Token与Cookie。
4. 服务器校验。
