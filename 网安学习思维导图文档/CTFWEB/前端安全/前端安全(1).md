# 同源策略攻防

## 补：同源策略机制简介
==同源策略（Same-Origin Policy, SOP）==是浏览器最核心的安全机制，用于限制一个源的文档或脚本与另一个源的资源进行交互==

它可以隔离潜在的恶意文件，防止黑客窃取敏感数据


==什么是“同源”？==

如果两个 URL 的 **协议 (Protocol)**、**域名 (Domain)** 和 **端口 (Port)** 完全相同，它们就属于“同源”。

- 公式：`协议 + 域名 + 端口` 必须完全一致。 [[1](https://zhuanlan.zhihu.com/p/348948397)]

- 示例：若目标网址是 `http://example.com`：
    - `http://example.com` -> **同源**（路径不同不影响）
    - `https://example.com` -> **不同源**（协议不同，一个是 http，一个是 https）
    - `http://example.com` -> **不同源**（域名不同）
    - `http://example.com` -> **不同源**（端口不同）


==限制的内容==

同源策略主要限制以下三种行为：

- **DOM 读取限制**：不同源的 JS 脚本无法读取或操作对方的 DOM（如页面元素、表单数据）。
- **Cookie、LocalStorage 和 IndexDB**：不同源之间无法读取彼此的本地存储和 Cookie 数据。
- **AJAX 请求限制**：通过 XMLHttpRequest 或 Fetch 发起的跨域请求会被浏览器拦截响应



==允许的跨域嵌入==

浏览器允许某些标签跨域加载资源（因为它们只加载不读取敏感内容）：

- `<img>` 标签加载图片
- `<link>` 标签加载 CSS 样式表
- `<script>` 标签加载 JavaScript 脚本

## 补：同源策略中的“源”介绍
同源策略中的“源”（Origin）是==由**协议（Protocol）**、**域名（Host/Domain）**和**端口（Port）**三者共同组成的==

==“源”的三要素详解==

以 URL `http://example.com` 为例： [[1](https://portswigger.net/web-security/cors/same-origin-policy)]

- **协议（Protocol / Scheme）**：如 `http`、`https`、`ftp` 等。
    - `http://example.com` 与 `https://example.com` 不同源（协议不同）。 [[1](https://dev.to/burakboduroglu/understanding-cors-and-same-origin-policy-in-web-security-54hm), [2](https://portswigger.net/web-security/cors/same-origin-policy)]

- **域名（Host / Domain）**：如 `example.com`、`api.example.com` 等。
    - 主域名与子域名不同源，例如 `example.com` 与 `store.example.com` 不同源。 [[1](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy), [2](https://dev.to/burakboduroglu/understanding-cors-and-same-origin-policy-in-web-security-54hm), [3](https://portswigger.net/web-security/cors/same-origin-policy)]

- **端口（Port）**：如 `80`、`443`、`8080` 等。
    - 常见协议有默认端口（如 `http` 默认 `80`，`https` 默认 `443`）。
    - `http://example.com`（默认端口 80）与 `http://example.com:8080` 不同源（显式指定了 8080 端口



 “源”是Web安全中一个核心的权限边界。它定义了哪个网页有权与哪
个资源进行交互。一个“源”由三个部分组成，缺一不可：
1. 协议(Protocol):`http://,https://,ftp://`等
2. 主机(Host):域名`(www.example.com)`或IP 地址`(192.168.1.1)`
3. 端口(Port):80(HTTP默认),443(HTTPS默认),8080等

因此我们得出，组成一个源的唯一标准：源=协议+主机+端口
例:`https://www.example.com:443/path/page.html`



## 补：同源与不同源判定
两个 URL 是否同源，取决于它们是否同时满足以下 ==**三个核心要素**。只要有一个要素不同，即为“不同源”（跨源）==

- **协议（Protocol）**：如 `http` 与 `https`。

- **域名/主机（Host/Domain）**：如 `example.com` 与 `://example.com`。

- **端口（Port）**：如 `:80` 与 `:8080`（若未指明则使用协议的默认端口）




## 补：同源策略限制行为简介
如果页面与目标资源非同源，浏览器主要限制以下三种行为

1. **Cookie、LocalStorage 和 IndexDB 无法读取**
    - 不同源的网页之间，无法通过前端脚本读取彼此在客户端存储的私密数据、浏览器缓存或本地数据库（如 `localStorage.getItem()` 拿不到跨源数据）。 [[1](https://www.ruanyifeng.com/blog/2016/04/same-origin-policy.html)]

2. **DOM 无法获得**
    - 如果通过 `iframe` 嵌入了不同源的页面，父页面和子页面无法通过 JS 获取对方的 DOM 对象。例如，你在 A 网站里用 `iframe` 打开 B 网站，A 网站的脚本不能读取 B 网站页面里的任何内容。 [[1](https://www.ruanyifeng.com/blog/2016/04/same-origin-policy.html), [2](https://www.cnblogs.com/lmg-jie/p/10756450.html)]

3. **AJAX 请求不能读取响应**
    - 虽然浏览器允许通过 `XMLHttpRequest` 或 `fetch` 发送跨源请求，但**同源策略主要禁止的是读取响应的内容**。如果服务器没有显式允许跨域，浏览器会拦截并报错，阻止脚本获取返回的数据


==常见的可嵌入例外==

虽然有限制，但浏览器==允许嵌入或提交部分跨源资源以保证网页的正常运行==：

- 允许引入外部的静态资源，如 `<script>`、`<link rel="stylesheet">`、`<img>` 等。
- 允许表单提交（Form Submit）和页面跳转（Redirect）





同源策略主要限制以下行为
1. DOM访问:
	例子：A.com的iframe无法读取B.com iframe内的输入框内容
2. Ajax请求:
	例子：A.com的JS无法直接向B.com/api/transfer发送请求获取数据
3. Cookie/IndexedDB/Web Storage访问



## 补：同源策略非限制行为简介
浏览器的同源策略并非绝对禁止所有跨域交互，而是通过“==允许嵌入与写入、限制直接读取==”来平衡安全与功能。


1. ==跨域资源嵌入 (Cross-origin embedding)==

- 浏览器允许通过特定的 HTML 标签加载并展示/执行外部来源的静态资源与脚本。 [[1](https://zhuanlan.zhihu.com/p/104984869), [2](https://developer.mozilla.org/zh-CN/docs/Web/Security/Defenses/Same-origin_policy), [3](https://tsejx.github.io/javascript-guidebook/computer-networks/web-security/same-origin-policy/)]

- **常见标签与行为**：
    - `<script src="...">`：加载并执行跨域的 JavaScript 脚本。
    - `<img src="...">`：加载并显示跨域图片（虽然能获取宽高，但无法直接读取图片像素细节）。
    - `<link rel="stylesheet" href="...">`：引入跨域样式表。
    - `<video>` / `<audio>`：加载并播放跨域音视频多媒体资源。
    - `<iframe>` / `<frame>`：嵌入其他源的网页页面。
    - `@font-face`：引入跨域字体文件



2. ==跨域写操作 (Cross-origin writes)==

- 浏览器通常允许用户通过页面交互向其他源提交数据或跳转，因为这属于“向外部发送请求”而非“窃取外部数据”。 [[1](https://developer.mozilla.org/zh-CN/docs/Web/Security/Defenses/Same-origin_policy), [2](https://tsejx.github.io/javascript-guidebook/computer-networks/web-security/same-origin-policy/)]

- **常见行为**：
    - **表单提交**（`<form action="..." method="POST">`）：可以向不同源的服务器提交数据。
    - **超链接跳转**（`<a href="...">`）：点击后导航到另一个源。
    - **页面重定向**：服务器触发的重定向跳转


3. ==其他天然无限制的行为==

- **表单发送与 GET/POST 跳转**：不通过 JavaScript 读取返回内容时，纯粹的提交和导航行为不受阻拦。
- **服务器端之间的数据请求**：同源策略是**浏览器**的安全机制，服务器与服务器之间的 HTTP 请求和通信（如后端发起 API 调用）完全不受同源策略限制




同源策略不会管制嵌入资源（Embed），例如：
`<link>、<img>、<script>、<video>、<audio>、<iframe>`等等

资源都可以被跨域加载，但是加载后的资源操作还是会受到限制。

## 补：SOP与客户端存储关系
**SOP（同源策略，Same-Origin Policy）是浏览器最核心的安全模型，它==直接决定了客户端存储（如 Cookie、LocalStorage、SessionStorage 和 IndexedDB）的访问权限与隔离边界==。** 简单来说，SOP 规定了一个网站存储的数据，默认情况下绝不允许另一个不同源的网站去读取或修改


==核心隔离规则对照==

| 存储类型               | SOP 隔离依据（同源定义）                           | 跨域/跨源行为特性                                              |
| ------------------ | ---------------------------------------- | ------------------------------------------------------ |
| **Cookie**         | 域名（Domain）+ 路径（Path）  <br>_(不严格遵循端口和协议)_ | 允许子域名间共享（需配置 `Domain`）；  <br>支持通过 `SameSite` 属性控制跨站携带。 |
| **LocalStorage**   | **协议 + 域名 + 端口** _(严格同源)_                | 永久存储。不同源绝对无法通过脚本直接访问。                                  |
| **SessionStorage** | **协议 + 域名 + 端口** _(严格同源)_ + **标签页（Tab）** | 临时存储。除了严格同源外，还必须在同一个标签页（或源自同页面的派生页）中才能共享。              |
| **IndexedDB**      | **协议 + 域名 + 端口** _(严格同源)_                | 结构化大容量数据库。不同源的代码无法打开、读取或写入彼此的数据库                       |



==各类存储在 SOP 下的具体表现==

1. ==Cookie：特例独行的“弱同源”==

Cookie 的隔离机制诞生早于标准的 SOP，因此它的规则相对宽松，**不检查协议和端口**：

- **跨域读取：** 如果你在 `http://example.com:8080` 写入了一个 Cookie，默认情况下 `https://example.com:9000` 也可以读取它（忽略了协议和端口）。
- **子域共享：** 通过将 Cookie 的 `Domain` 属性设置为 `.example.com`，可以实现 `://example.com` 和 `://example.com` 之间的免密登录或数据共享。
- **跨站防御：** 为了防止第三方利用 Cookie 进行 CSRF（跨站请求伪造）攻击，现代浏览器引入了 `SameSite` 属性（`Strict` / `Lax` / `None`），严格限制了跨站请求时 Cookie 的自动携带。

2. ==LocalStorage 与 SessionStorage：严格的 Web Storage 隔离==

这两者严格遵循 SOP（协议+域名+端口）：

- **跨源完全隔离：** `http://example.com` 绝对无法读取 `https://example.com`（协议不同）或 `http://example.com:8080`（端口不同）的 LocalStorage。
- **SessionStorage 的双重限制：** 它不仅受 SOP 限制，还受**窗口上下文（Window Context）** 限制。即使同源，在两个独立打开的标签页中，SessionStorage 也是互不干扰的。

3. ==IndexedDB：安全的本地数据库==

作为浏览器端的“正规”数据库，IndexedDB 同样受到严格的 SOP 保护：

- 每个源都有自己独立的数据库命名空间。
- 即使在同一个浏览器里，网页 A 也无法探测到网页 B 是否创建了某个特定名称的 IndexedDB 数据库，更无法进行读写


常见痛点：如何在 SOP 限制下实现跨源数据共享？

虽然 SOP 保护了数据安全，但有时企业在不同业务域名间（如 `company-auth.com` 和 `company-app.com`）确实需要共享数据（例如 Token）。常用的绕过或合规解决方案包括：

- **使用 `iframe` + `postMessage`（推荐）：**  
    在一个域名的网页中嵌入另一个域名的隐藏 `iframe`，利用 HTML5 的 `window.postMessage` API 进行跨源安全通信，由 `iframe` 内部的脚本去操作它自己同源的 LocalStorage。

- **利用 CAS / SSO 单点登录：**  
    不直接在客户端共享存储，而是通过认证中心服务器重定向、携带 Ticket/Token 的方式，在各自的域名下独立存储





`Cookie`:
SOP对于Cookie的限制是脚本无法读取或修改不同源的Cookie。但是浏
览器在发起HTTP请求的时候会自动携带符合路径和域名要求的Cookie，
无论是否同源

`Web Storage`:
LocalStorage，SessionStorage完全受到sop的管辖每个源都有自己完全
独立的存储空间，JavaScript绝对无法访问不同源的存储数据

`IndexedDB`:
同样受SOP严格保护。每个源都有自己的数据库

## 补：CORS工作流程简介
CORS（跨源资源共享，Cross-Origin Resource Sharing）的工作流程由浏览器自动完成，==主要分为**简单请求**和**预检请求（复杂请求）** 两种处理方式==


1. ==简单请求工作流程==

当请求满足特定条件（如请求方法为 ==`GET`、`HEAD`、`POST`==，且头部字段仅限安全字段）时，浏览器会直接发送请求。 [[1](https://docs.cloud.google.com/storage/docs/cross-origin?hl=zh-cn)]

- **发送请求**：
    - 浏览器自动在请求中添加 `Origin` 头部，记录当前源信息（如 `Origin: https://example.com`）。

- **服务器响应**：
    - 服务器收到请求后，检查 `Origin` 是否在允许的列表中。
    - 若允许，服务器在响应头中包含 `Access-Control-Allow-Origin: https://example.com`（或 `*`）。 [[1](https://learn.microsoft.com/zh-cn/azure/frontdoor/cross-origin-resource-sharing)]

- **浏览器校验**：
    - 浏览器收到响应，检查 `Access-Control-Allow-Origin` 是否与当前源匹配。
    - 匹配则将数据放行给 JavaScript；不匹配则拦截响应并抛出跨域错误




2. ==预检请求（复杂请求）工作流程==

当请求使用非简单方法（如 ==`PUT`、`DELETE`==）或包含自定义头部、`Content-Type` 为 `application/json` 时，浏览器会先发送一次“预检”请求。 [[1](https://docs.cloud.google.com/storage/docs/cross-origin?hl=zh-cn), [2](https://learn.microsoft.com/zh-cn/azure/frontdoor/cross-origin-resource-sharing)]

- **发送预检请求（OPTIONS）**：
    - 浏览器会先向服务器发送一个 `OPTIONS` 方法的请求（探针请求），询问服务器是否允许跨域。
    - 携带关键头部：
        - `Access-Control-Request-Method`：告知服务器后续真实请求将使用的方法。
        - `Access-Control-Request-Headers`：告知服务器后续真实请求将包含的自定义头部。 [[1](https://learn.microsoft.com/zh-cn/azure/frontdoor/cross-origin-resource-sharing)]

- **服务器响应预检**：
    - 服务器检查并确认允许该跨域行为后，返回 `200 OK` 或 `204 No Content` 状态码，并在响应头中说明支持的权限：
        - `Access-Control-Allow-Origin`：允许的源。
        - `Access-Control-Allow-Methods`：允许的方法。
        - `Access-Control-Allow-Headers`：允许的头部。
        - `Access-Control-Max-Age`：预检结果的缓存时间（秒）。

- **发送真实请求**：
    - 预检成功后，浏览器向服务器发送实际的 `PUT` 或 `DELETE` 等主请求。 [[1](https://docs.cloud.google.com/storage/docs/cross-origin?hl=zh-cn)]

- **服务器响应真实数据**：
    - 服务器返回实际业务数据，浏览器校验响应头后将数据交给前端 JS



CORS是一套允许服务器通过响应头的方式声明哪些外部源有权访问其资源的机制，服务器可以声明允许哪些外部源访问资源。

简单请求：直接发送
非简单请求：浏览器先发送预检请求



简单请求的条件：
1、请求方法只限：`GETPOSTHEAD`
2、头部:仅限简单头部(`Accept,Accept-Language,Content-
Language`等)
3.`Content-Type: text/plain, multipart/form-data`,
`application/x-www-form-urlencoded`

不满足简单请求条件的情况下，浏览器需要先发送OPTIONS请求进
行确认是否可以请求

### 关键CORS头部字段介绍
CORS（跨域资源共享）==通过一组 HTTP 头部字段来告诉浏览器是否允许跨域访问==

==请求头部字段（浏览器发送）==

- **Origin**：指示请求来自哪个源（协议 + 域名 + 端口）。
- **Access-Control-Request-Method**：在预检请求中使用，告知服务器后续实际请求将使用哪种 HTTP 方法。
- **Access-Control-Request-Headers**：在预检请求中使用，告知服务器后续实际请求将携带哪些自定义头部字段



==响应头部字段（服务器返回）==

- **Access-Control-Allow-Origin**：指定允许访问该资源的域，可设为具体域名或 `*`（表示所有域）。
- **Access-Control-Allow-Methods**：指定服务器允许的 HTTP 请求方法（如 GET、POST、PUT 等）。
- **Access-Control-Allow-Headers**：指定服务器允许请求携带的自定义头部字段。
- **Access-Control-Allow-Credentials**：布尔值，指示是否允许客户端发送 Cookie 等凭证信息。
- **Access-Control-Max-Age**：指定预检请求的缓存时间（秒），在此期间不用重复发送预检请求。
- **Access-Control-Expose-Headers**：指定浏览器可以访问的响应头列表（默认只能访问基础响应头）



**以下是由浏览器添加的CORS相关头**：
Origin：表明请求来自哪个源
Access-Control-Request-Method：预检请求中声明实际使用的方
法
Access-Control-Request-Headers:预检请求中声明实际使用的自
定义头

**由服务器设置的CORS相关头**：
`Access-Control-Allow-Origin`：允许访问的源（*或具体域名）
`Access-Control-Allow-Methods`:允许的HTTP方法
`Access-Control-Allow-Headers`:允许的自定义头
`Access-Control-Allow-Credentials`:是否允许发送Cookie
`Access-Control-Max-Age`:预检请求缓存时间
