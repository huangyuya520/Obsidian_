
# JSONP介绍

## 补：跨域与数据交互相关的历史简介
==**跨域（Cross-Origin）与数据交互的历史**伴随着 Web 技术的演进，它见证了互联网从“静态文档浏览”走向“动态富应用”的整个过程。==

为了保障安全，浏览器引入了**同源策略（Same-Origin Policy）**，但由于业务发展对跨源数据交互的迫切需求，开发者们在不同历史阶段发明了各种“破局”方案


 1. ==早期阶段（1995 - 2005年）：静态同源与早期的“跨域绕过”==

1995年，网景公司（Netscape）在 JavaScript 中引入了**同源策略（SOP）**。该策略规定：如果两个 URL 的**协议（Protocol）、域名（Host）和端口（Port）** 有任何一个不同，就被视为不同源，浏览器会限制它们之间的脚本交互。

这一时期的 Web 以静态页面为主，页面跳转依靠超链接（`<a>` 标签）或表单提交（`<form>`）。

1. `<form>` 表单的特殊性

- **现象**：`<form>` 表单提交可以向不同源的服务器发送数据（例如 A 网站的表单可以提交到 B 网站）。

- **代价**：表单提交会导致**整个页面刷新**，无法在不刷新页面的情况下获取并处理返回的数据。

2. iframe 与 `document.domain`

随着页面开始使用 `<iframe>` 嵌套不同子域的内容，跨域需求首次出现。

- **方案**：对于主域名相同但子域名不同的场景（如 `://example.com` 和 `://example.com`），开发者通过手动将两边的 `document.domain` 设置为 `example.com` 来实现有条件的跨域通信。



2. ==动态 Web 崛起阶段（2005 - 2010年）：JSONP 与各类黑客式黑魔法==

2005年，**AJAX**（Asynchronous JavaScript and XML）概念被提出，Web 进入 2.0 时代。由于 AJAX 核心的 `XMLHttpRequest` 受到严格的同源策略限制，无法直接请求外域接口，开发者们开始寻找各种替代方案。

1. JSONP（JSON with Padding）的诞生

开发者发现，浏览器虽然限制了脚本跨域读取数据，但允许通过 `<script>`、`<img>`、`<link>` 等标签**跨域加载静态资源**。

- **原理**：利用 `<script>` 标签的 `src` 属性请求跨域接口，服务器不再返回纯 JSON，而是返回一个 JS 函数调用（例如 `callback({data: 1})`）。

- **优缺点**：
    - **优点**：简单好用，兼容性极好（甚至支持 IE6）。
    - **缺点**：**只支持 GET 请求**；存在严重的 XSS 安全隐患（如果信任了恶意的第三方接口）。

2. 各种页面间跨域黑魔法

在两个不同源的 `<iframe>` 或窗口之间，开发者利用浏览器的特性发明了许多“钻空子”的技术：

- **Window.name**：`window.name` 属性在页面跳转时不会丢失，且容量较大。开发者利用一个隐藏的 iframe 先加载跨域页面（将数据存入 `window.name`），再将其跳回同源页面读取数据。

- **URL Hash（锚点变动）**：通过修改 iframe 的 URL 后面 `#` 后面的参数来传递数据，并通过定时器监听 `location.hash` 的变化。




3. ==标准化与现代阶段（2010年至今）：官方标准的全面普及==

随着 Web 应用越来越复杂，“黑魔法”不仅难以维护，还带来了巨大的安全隐患。W3C 和各大浏览器厂商开始推动跨域数据交互的标准化。

1. CORS（跨源资源共享）的推出

为了从根本上解决 AJAX 无法跨域的问题，W3C 推出了 **CORS（Cross-Origin Resource Sharing）** 标准。

- **机制**：通过一套新增的 **HTTP 响应头**（如 `Access-Control-Allow-Origin`）来告诉浏览器：服务器允许哪些外域访问本资源。

- **预检请求**：对于一些可能修改服务器数据的请求（如 POST、PUT、DELETE 或者是自定义 Header），浏览器会先发送一个 **OPTIONS 请求** 进行合规性检查。

- **意义**：这是目前最标准、最安全的跨域解决方案，将跨域的控制权彻底交给了后端服务器。

2. HTML5 PostMessage

为了解决动态页面/窗口之间的安全通信问题，HTML5 引入了 `window.postMessage` API。

- **意义**：允许来自不同源 bran 的脚本采用异步方式进行有限的通信，可以安全地实现跨域窗口、跨域 iframe 之间的数据传递。

3. WebSocket 协议

2011年，IETF 资助了 WebSocket 协议（RFC 6455）。

- **特性**：WebSocket 在建立连接时使用 HTTP，之后则转化为全双工的 TCP 通道。**WebSocket 协议本身不受同源策略的限制**，它自带 Origin 校验机制，由服务器决定是否接受该跨域连接。

4. 工程化时代的代理（Proxy）

随着前端步入模块化和工程化（Webpack, Vite, Node.js 中间件），本地开发环境的跨域问题变得非常普遍。

- **方案**：**反向代理（Reverse Proxy）**。由于**服务器与服务器之间没有同源策略限制**，开发环境通常通过 Node.js 代理服务器（如 `http-proxy-middleware`）或生产环境通过 Nginx，将前端的跨域请求拦截并转发给真实的后端，从而在浏览器端“伪装”成同源请求。

## JSONP工作原理与流程简介
JSONP（JSON with Padding）==是一种利用 `<script>` 标签不受同源策略限制的特性，来实现跨域数据传输的前端技术==。==其核心机制可概括为：**前端预先定义回调函数，后端返回一段调用该函数的 JavaScript 脚本并传入 JSON 数据作为参数**==



==**核心原理**==

浏览器的同源策略（Same-Origin Policy）会限制 `XMLHttpRequest` 和 `Fetch` 的跨域网络请求，但对 HTML 中加载外部资源的标签（如 `<script>`、`<img>`、`<link>`）不做跨域阻拦。

JSONP 正是借用了 `<script>` 标签的 `src` 属性：

- 浏览器向跨域地址请求一个 JS 脚本。
    
- 服务端不直接返回纯 JSON 格式文本（如 `{"id": 1}`），而是返回一段 **可执行的 JavaScript 代码**，将 JSON 包装在指定的函数调用中（如 `callbackName({"id": 1})`）。
    
- 浏览器加载完毕后立即在当前作用域执行该脚本，从而触发前端预先写好的函数，并接收到传入的数据。




==**标准执行流程**==

1. **定义全局回调**：客户端在全局（如 `window`）挂载一个用于接收处理数据的回调函数。
    
2. **动态创建标签**：客户端通过 JavaScript 动态创建 `<script>` 标签，将其 `src` 指向跨域接口，并通过 URL Query 参数告知服务端回调名称（常见如 `?callback=handleResponse`）。
    
3. **挂载发送请求**：将 `<script>` 插入页面 DOM（通常是 `document.body` 或 `document.head`），触发浏览器的跨域 GET 请求。
    
4. **服务端包装数据**：服务端解析请求中的回调名称参数，拼接出一段 JS 调用代码（设置响应类型为 `application/javascript`），将 JSON 数据放入参数中返回。
    
5. **执行代码并消费数据**：脚本加载完毕后，浏览器自动解析并执行返回的内容，调用客户端预设的回调函数，数据作为参数传入业务逻辑。
    
6. **清理 DOM**：回调执行完毕或超时后，客户端主动从 DOM 中移除刚才创建的 `<script>` 节点并释放全局函数，避免 DOM 冗余和内存泄漏

==**局限性与现代替代方案**==

|**维度**|**JSONP**|**CORS（现代标准）**|
|---|---|---|
|**请求方法**|仅支持 **GET**（依赖 `script.src`）|支持 GET, POST, PUT, DELETE 等全套 HTTP 方法|
|**安全性**|较高风险（容易遭受 XSS 脚本注入，需完全信任服务端）|细粒度权限控制（Origin、Credentials、Headers）|
|**错误捕获**|难以精确捕获 HTTP 状态码（如 404、500）|标准 Promise/Fetch 响应，状态码与异常完整可查|
|**数据形态**|必须由服务端动态拼装 JS 脚本|服务端直接输出纯 JSON / XML / 二进制流|

现代 Web 开发中，随着浏览器标准的演进，JSONP 已基本被标准化的 **CORS（跨源资源共享）** 所取代，仅在维护极少数老旧系统或特定第三方微端 SDK 时偶有使用。

# JSONP的安全风险

## 回调注入(Callback Injection)问题
**JSONP 回调注入（Callback Injection）** 是==指服务端未对客户端传入的回调函数名参数进行严格校验与过滤，直接将其与 JSON 数据拼接并输出，导致攻击者能够注入任意 JavaScript 代码或 HTML 标记，从而引发**反射型跨站脚本攻击（Reflected XSS）**==

==漏洞形成原因==

在标准的 JSONP 架构中，服务端接收客户端的 `callback` 参数并动态拼接返回：

例：
```
HTTP 响应体 = callback_param + "(" + json_data + ");"
```

如果服务端代码直接进行字符串拼接，而未对 `callback_param` 的字符集进行白名单校验：

例：
![](Pasted%20image%2020260902211046.png)




==攻击场景与危害==


1. API 域上的反射型 XSS（危害最大）

当服务端未严格设置 `Content-Type: application/javascript`，或将其误设为 `text/html` 时，攻击者诱导受害者在浏览器中直接访问恶意构造的链接：

**恶意请求：**
例：
![](Pasted%20image%2020260902211202.png)


**服务端输出：**

例：
```
<script>alert(document.cookie)</script>({"userId":101,"username":"Alice"});
```

**结果：** 浏览器将响应直接解析为 HTML 页面，在 `vulnerable-api.com` 域名上下文中执行恶意脚本，造成 Cookie 窃取、Session 劫持或 CSRF Token 泄露





2. MIME 嗅探与代码执行（MIME-Sniffing）

即使服务端将 `Content-Type` 设为了 `text/plain` 或省略了该响应头，如果在响应中未配置 `X-Content-Type-Options: nosniff`，部分老旧浏览器（或特定浏览器环境）会尝试嗅探内容格式。当响应内容以 HTML 标签开头时，浏览器会自动降级为 HTML 解析，导致注入的脚本执行。






3. 破坏调用链与逻辑劫持

当受害者站点通过 `<script src="...">` 引入该 JSONP 接口时，攻击者可通过参数注入中断原有逻辑，甚至执行任意脚本：


**恶意请求：**
例：
```
GET /api/user?callback=alert(1);// HTTP/1.1
```


**服务端输出：**
例：
```
alert(1);//({"userId":101,"username":"Alice"});
```
- **结果：** 原始的合法回调函数被短路，浏览器直接执行 `alert(1)`，原本的 JSON 数据被 `//` 注释忽略





==防御与修复方案==

1. 严格的字符白名单校验（核心手段）

合法的 JavaScript 函数名（标识符）通常仅包含字母、数字、下划线及命名空间访问符（如 `.`）。服务端必须在拼接前对参数进行正则白名单限制，拒绝不合规的输入


2. 正确设置响应头（防御深度）

确保返回严格的 JavaScript 媒体类型，并强制禁止浏览器的 MIME 嗅探行为：

- **Content-Type**：统一设置为 `Content-Type: application/javascript; charset=utf-8`。
    
- **安全头**：增加 `X-Content-Type-Options: nosniff`，防止浏览器绕过 MIME 类型将其当作 HTML 执行



3. 字符转义过滤

如果业务架构无法使用严格白名单，必须对危险字符进行实体编码或过滤：

- 过滤或转义 `<`、`>`、`"`、`'`、`\`、`;`、`(`、`)` 以及换行符（`\r`、`\n`）。
    
- 禁止注入单行注释符 `//` 与多行注释符 `/*`。



4. 彻底替代为 CORS

JSONP 属于过渡期的跨域临时方案，无法支持非 GET 请求，且天生缺乏现代浏览器的细粒度安全防护机制。生产环境应全面转向 **CORS（跨源资源共享）**，直接通过 `fetch` 或 `XMLHttpRequest` 交互，从根源上消除动态脚本拼接带来的注入隐患












在服务端未验证callback名称时，容易出现攻击者通过callback参数
注入代码的情况：

`https://api.com/data?callback=alert(1)`

这种情况发生在服务端没有验证callback参数的情况，攻击者可以执行任意JS代码。











## JSONP接口数据泄露问题
**JSONP 接口数据泄露（业界常称“JSONP 劫持”或 JSONP Hijacking）** 是一种==类似于 CSRF 的客户端信息窃取漏洞==。==攻击者利用浏览器对 `<script>` 标签不受同源策略（SOP）限制且会自动附带目标站点凭证（Cookie）的机制，诱导已登录受害者访问恶意网页，从而在恶意站点的上下文中直接读取并盗取该接口返回的敏感数据==



==漏洞产生机制==

JSONP 的数据泄露通常由以下三个机制的叠加导致：

1. **同源策略放行脚本加载与执行**：浏览器允许网页通过 `<script src="...">` 加载任意域名的脚本，并且该脚本执行的上下文环境是**当前的引入页面**，而不是脚本来源域。
    
2. **凭证自动携带（Ambient Authority）**：当浏览器发起跨域脚本请求时，默认会为请求目标域附带当前用户保存在浏览器中的 Cookie 等认证凭据。
    
3. **服务端缺乏来源校验**：服务端仅根据请求中的 Cookie 判定用户身份，未对请求的来源域（`Referer` / `Origin`）进行有效校验，直接返回包含用户隐私信息的 JavaScript 回调代码。

==泄露风险与常见资产影响==

- **用户 PII（个人身份信息）泄露**：真实姓名、手机号、家庭住址、身份证号、收货地址等。
    
- **财务与资产信息暴露**：账户余额、积分点数、历史消费订单、绑定的银行卡尾号等。
    
- **权限与令牌泄露**：若接口返回 CSRF Token、内部 API Token 或用户密钥，攻击者可借此突破防护，发动后续组合攻击（如利用窃取的 Token 执行越权操作）。





==常见防御绕过（渗透中需要规避的误区）==

部分开发者尝试通过简单的规则来过滤来源，但往往因为正则或逻辑漏洞被绕过：

|**错误防御方式**|**潜在绕过手法**|
|---|---|
|**子串匹配**（如判断 `referer.indexOf("target.com") > -1`）|攻击域名构造为 `evil-target.com` 或 `[evil.com/target.com/](https://evil.com/target.com/)`|
|**空 Referer 放行**（允许未携带 Referer 的请求通过）|攻击者在页面加入 `<meta name="referrer" content="no-referrer">` 强制隐匿 Referer|
|**不严谨的正则匹配**（如 `/https?:\/\/.*target\.com/` 遗漏转义点）|攻击域名构造为 `targetxcom.com` 或 `target.com.attacker.com`|



==防御与整改方案==

1. 废弃 JSONP，全面迁移至 CORS（推荐）

JSONP 天生不具备现代浏览器的跨域细粒度访问控制。将接口重构为标准 RESTful API，利用 CORS 实现受控跨域：

- 设置白名单：`Access-Control-Allow-Origin: [https://trust-domain.com](https://trust-domain.com)`（**切忌使用 `*` 通配符**）。
    
- 限制凭据携带：仅对必须跨域携带 Cookie 的受信任源配置 `Access-Control-Allow-Credentials: true`。
    


2. 严格的 Referer / Origin 白名单核验

若受限于老旧系统必须保留 JSONP，服务端必须对 HTTP 请求头的 `Referer` 进行严格白名单匹配：

采用严谨的 URL 解析器或经过锚定字符严格测试的正则表达式



3. 引入一次性或会话级防 CSRF Token

在 JSONP 请求的 URL 参数中增加动态随机 Token（如 `?callback=cb&token=random_token`）。由于攻击者位于第三方域，无法预先得知用户当前的防伪 Token，因此无法构造出合法的 `<script>` 请求。



4. 配置 Cookie 的 SameSite 属性

将敏感凭据 Cookie 的 `SameSite` 属性设置为 `Lax` 或 `Strict`。现代浏览器在检测到由第三方域发起的子资源脚本请求（如 `<script src="...">`）时，将**不会随同发送带有 `SameSite=Lax` 或 `Strict` 标记的 Cookie**，从而在底层切断身份传递链











当提供JSONP功能的API返回敏感数据时，就会导致敏感数据泄漏：

`https://api.com/account/profile`

如果这样的jsonp接口返回了登录用户的个人信息，就会导致攻击
者可以在另一个站点获取已登录用户的个人信息。






## xss攻击与JSON Hijacking（JSON 劫持）攻击问题
在基于 JSONP 的架构中，XSS（跨站脚本攻击）与 JSON Hijacking（JSON 劫持）是威胁最大的两类安全漏洞。==两者的核心危害方向截然不同：**XSS 破坏的是执行环境的完整性（在受害者浏览器中执行恶意代码），而 JSON Hijacking 破坏的是私密数据的机密性（跨域窃取受害者的敏感凭据与数据）**==


1. ==JSONP 中的 XSS 攻击==
JSONP 本质是动态加载并执行一段 JavaScript 脚本。如果接口缺乏输入输出规范，攻击者即可将其变为脚本注入通道
---

1. 回调函数名注入（反射型 XSS）
服务端直接拼接客户端传入的 `callback` 参数，未做严格的字符白名单过滤

**注入 payload**：

2. ==JSON Hijacking 攻击==
“JSON 劫持”在历史上主要经历了两类形态：早期的**原型覆盖劫持（Classic JSON Hijacking）**与现代主流的**JSONP 回调劫持（JSONP Hijacking）**
---


1. 经典 JSON 劫持（原型覆写与 Setter 劫持）
2006 年前后出现的一种针对纯 JSON 数组 `[...]` 的攻击方式：

- **背景**：在早期的 ECMAScript 规范与老旧浏览器（如 Firefox 2.0、IE8 之前）中，允许通过 `Object.prototype.__defineSetter__` 或 `Array.prototype` 重写内置原型对象的构造或赋值逻辑。
    
- **攻击方式**：
    
    1. 接口返回根节点为数组的纯 JSON（例如：`[{"secret": "user_balance_1000"}]`）。
        
    2. 攻击者页面先重写数组原型的 setter 方法：


例：
![](Pasted%20image%2020260902220002.png)

	3. 恶意页面使用 `<script src="[https://target.com/api/array_data](https://target.com/api/array_data)">` 加载该接口。由于浏览器将顶级数组解析为合法语句，实例化数组时触发恶意 setter，隐私数据被截获。

**现状**：现代浏览器均已禁止在顶级脚本中将 `{}`（对象字面量）或直接数组以不受控的方式解析为可劫持对象，纯 JSON 必须通过 XHR/Fetch 访问，此特定手法已被浏览器引擎底层修补




2. ==现代 JSONP 回调劫持==

当前真实网络威胁中的 JSON 劫持特指 **JSONP 数据越权读取**：

- **攻击机理**：
    
    1. 目标接口设计为 JSONP 模式，并包含敏感用户数据（如手机号、身份凭证、CSRF Token）。
        
    2. 接口仅依赖 Cookie 认证身份，未对请求的发起来源（`Referer` / `Origin`）做校验。
        
    3. 攻击者在其恶意站点 `evil.com` 上提前声明全局同名回调函数，并挂载 `<script src="[https://target.com/api/info?callback=mySpy](https://target.com/api/info?callback=mySpy)">`。
        
    4. 受害者登录 `target.com` 后访问 `evil.com`，浏览器执行脚本请求并自动附带 `target.com` 的 Cookie。
        
    5. 响应脚本在 `evil.com` 页面上下文执行，`mySpy(sensitiveData)` 被调用，数据直接泄露给恶意脚本






3. ==核心区别与特征对比==

|**维度**|**JSONP XSS (回调注入)**|**JSON Hijacking (JSONP 劫持)**|
|---|---|---|
|**威胁本质**|破坏代码**执行完整性**（Code Injection）|破坏数据**保密性**（Information Disclosure）|
|**利用漏洞点**|服务端对 `callback` 参数缺乏格式校验|服务端缺乏源校验（跨站请求未校验 Referer/Token）|
|**受害目标**|运行注入脚本的客户端环境 / API 所属域|已登录目标站点的合法受害者个人隐私|
|**攻击产物**|盗取 Cookie、篡改界面、蠕虫传播|窃取身份信息（PII）、资产数据、跨站伪造凭证|
|**防护重点**|严格限制回调参数的字符集与类型|严格鉴权与来源校验（Referer、SameSite、Token）|





# JSONP防御与替代方案

## 校验callback参数(仅允许安全字符回调)策略防御JSONP漏洞
校验 callback 参数（白名单安全字符过滤）是==防御基于 JSONP 的反射型 XSS（Reflected Cross-Site Scripting）与脚本注入攻击最基础且关键的服务器端防线==

JSONP（JSON with Padding）本质上是将数据包装在客户端指定的 JavaScript 函数调用中返回，格式为 `callback_name(json_data)`。若服务端未对 `callback_name` 进行严格校验，攻击者便可通过篡改参数注入恶意代码


1. ==威胁场景：缺乏校验的风险==

当服务端直接将客户端传入的 `callback` 参数拼接至响应体时，攻击者可构造以下攻击载荷：

- **直接闭合与执行代码**：
    
    - 请求：`?callback=alert(document.domain);//`
        
    - 响应：`alert(document.domain);//({"user":"Alice"})`
        
- **HTML/标签注入（若 Content-Type 设置不当为 text/html）**：
    
    - 请求：`?callback=<script>alert(1)</script>`
        
    - 响应：`<script>alert(1)</script>({"user":"Alice"})`
        
- **换行符/响应拆分（CRLF Injection）**： 通过注入 `\r\n` 篡改 HTTP 响应头或注入任意响应体




2. ==字符校验策略与实现规范==
校验 callback 参数的核心是：==**严格限制输入仅能由合法的 JavaScript 标识符组成**，阻断括号、引号、分号、HTML 标签及控制字符。==

正则表达式规范

JavaScript 函数名通常支持字母、数字、下划线、美元符号，且常包含用于命名空间调用的点号（`.`，例如 `jQuery360_123.callbacks` 或 `App.Users.cb`）

**基础单标识符白名单**（最严格，不允许命名空间）：
例：
```
^[a-zA-Z_$][a-zA-Z0-9_$]{0,64}$
```


**支持对象属性调用的安全正则**（兼容常见前端框架）：
例：
```
^[a-zA-Z_$][a-zA-Z0-9_$]*(\.[a-zA-Z_$][a-zA-Z0-9_$]*)*$
```


实施细节要求

1. **长度硬性限制**：设置合理长度上限（如 32 到 64 字符），防止过长参数导致的 ReDoS（正则拒绝服务）或内存消耗。
    
2. **严防特殊标点**：绝对禁止以下字符出现在 callback 中：
    
    - 括号与标点：`(` `)` `[` `]` `{` `}` `;` `,` `=`
        
    - 标签与引号：`<` `>` `'` `"`
        
    - 控制字符：`\r` `\n` `\0`
        
3. **校验失败处理**：一旦匹配失败，直接返回 HTTP 400 Bad Request，或强制回退为固定默认函数名（如 `jsonpCallback(...)`），严禁原样输出非法参数

---

3. ==配套防御措施（防御深度）==

仅过滤 callback 字符不足以完全防御 JSONP 相关的所有安全隐患，必须协同配置以下策略：

- **强制声明 MIME 类型**：明确指定 `Content-Type: application/javascript; charset=utf-8`，避免浏览器将其作为纯文本或 HTML 解析。
    
- **禁用 MIME 嗅探**：添加响应头 `X-Content-Type-Options: nosniff`，阻止低版本或兼容模式浏览器在解析失败时自动将其转换为 HTML 渲染。
    
- **数据内容转义（Unicode Escaping）**：对输出的 JSON 数据中的 `U+2028`（行分隔符）和 `U+2029`（段落分隔符）进行转义。在旧规范中，这两个字符是合法的 JSON 字符，但会被 JavaScript 解析器视作换行，导致语法解析中断。
    
- **防劫持校验（Referer / Token）**：callback 校验只能防御 XSS，无法阻止第三方网站通过 `<script src=".../user">` 窃取用户敏感信息（JSONP 劫持）。涉及私密数据时，必须校验 `Referer` 白名单或加入一次性防劫持 Token



## 验证来源(Referer/Origin)策略防御JSONP漏洞
验证来源（Referer 与 Origin）是==防御 **JSONP 劫持（JSONP Hijacking）** 的核心服务端防线，旨在阻止恶意第三方网站利用受害者的登录态跨域加载敏感数据==

对 callback 参数的过滤只能解决反射型 XSS 问题，无法防御数据窃取；如果攻击者在恶意站点通过 `<script src="[https://example.com/api/userinfo?callback=steal](https://example.com/api/userinfo?callback=steal)">` 引用接口，浏览器会自动携带受害者的认证凭证（如 Cookie），恶意站点即可定义 `steal(data)` 捕获并外发用户的隐私信息



1. ==Referer 与 Origin 在 JSONP 中的差异==

|**请求头**|**产生场景与特点**|**在 JSONP 防御中的适用性**|
|---|---|---|
|**Referer**|浏览器加载 `<script>`、`<img>`、页面跳转时自动携带，包含发起请求的页面完整或部分 URL。|**主要依据**。绝大多数浏览器在执行脚本标签跨域请求时会默认携带 Referer。|
|**Origin**|通常仅在跨域 POST/PUT/DELETE 请求、CORS 预检（OPTIONS）或跨域 Fetch/XHR 请求中强制发送。|**辅助依据**。标准的 GET `<script>` 请求通常**不包含** Origin 头，不能单独依赖。|



2. ==常见的校验疏漏与绕过手法（反模式）==

由于许多开发人员使用弱正则或简单的字符串匹配函数，攻击者常利用以下方式绕过来源检测：

- **包含关系匹配（`Contains` / `IndexOf`）**
    
    - _错误逻辑_：`referer.contains("example.com")`
        
    - _绕过 Payload_：`[https://evil-example.com](https://evil-example.com)` 或 `[https://attacker.com/page?x=example.com](https://attacker.com/page?x=example.com)`
        
- **前缀匹配（Prefix Match）**
    
    - _错误逻辑_：`referer.startsWith("[https://example.com](https://example.com)")`
        
    - _绕过 Payload_：`[https://example.com.attacker.com](https://example.com.attacker.com)`
        
- **正则未转义点号（Regex Unescaped Dot）**
    
    - _错误逻辑_：`/^https:\/\/[www.example.com/](https://www.example.com/)`（`.` 匹配任意字符）
        
    - _绕过 Payload_：`[https://wwwaexample.com](https://wwwaexample.com)`
        
- **放行空 Referer（Bypass on Empty Referer）**
    
    - _错误逻辑_：`if (referer == null || referer.isEmpty()) return true;`
        
    - _绕过手法_：攻击者在恶意页面配置 `<meta name="referrer" content="no-referrer">`，或使用 `iframe` 的 `srcdoc` / `data:` URI，强制浏览器在发送请求时不携带 Referer 头。
        
- **协议混淆**
    
    - _错误逻辑_：仅校验域名，未校验协议。
        
    - _风险_：在内网或受劫持的 HTTP 环境下，攻击者通过伪造的 `http://` 页面绕过面向 `https://` 的策略




3. ==来源校验的最佳实践与实现==

核心校验规则

1. **结构化解析**：禁止使用粗暴的正则全文匹配，必须使用官方提供的 URL 解析器（如 Node.js 的 `new URL()`、Java 的 `java.net.URI`）提取 `protocol` 和 `hostname`。
    
2. **严格白名单对比**：将解析出的完整域名与受信域名列表进行强全量比对，或仅放行格式极其严格的多级子域名。
    
3. **涉及敏感数据时坚决拒绝空 Referer**：任何承载用户身份标识、个人资产或隐私信息的 JSONP 接口，一旦 Referer 为空，一律返回 HTTP 403



4. ==Referer 策略的局限性与纵深防御==

单一依赖 Referer 校验存在生态缺陷：合法第三方合作伙伴调用时白名单维护成本高，且随着浏览器日益收紧的 Privacy/Referrer-Policy（如截断至 Origin 或直接剔除），合法的跨站调用可能误报失败。必须配合以下底层加固措施：

- **Cookie 设置 `SameSite=Lax` 或 `SameSite=Strict`**： 现代浏览器对于 `SameSite=Lax` 的 Cookie，在跨站加载资源（如 `<script src="...">`）时**默认不发送 Cookie**。这从底层阻断了未授权的身份冒用，是防止 JSONP 劫持最彻底的浏览器机制之一。
    
- **增加随机校验凭证（Anti-CSRF Token）**： 在 JSONP 请求的 URL 参数中强制要求携带一次性或基于 Session 的动态 Token（如 `?callback=cb&token=xyz123`）。第三方页面因同源策略无法预先读取受害者在目标站点的 Token，调用将直接失效



## 禁止敏感接口使用JSONP策略防御JSONP漏洞
**禁止敏感接口使用 JSONP** ==是一种从架构源头收缩攻击面（Attack Surface Reduction）的“本质安全”防御策略==

与其在代码层面对 `callback` 参数进行正则清洗、对 `Referer` 来源进行严苛校验（这两者极易因配置疏漏、正则缺陷、浏览器策略变动或子域名劫持而失效），**直接从设计层面规定“涉及身份认证与私密数据的接口一律不得提供 JSONP 能力”**，是消除 JSONP 劫持（JSONP Hijacking）与跨站脚本包含（XSSI）最彻底、容错率最高的方式

1. ==为什么对敏感接口必须“直接禁用”而非“打补丁”==

在实际攻防演练与生产事故中，许多针对敏感接口的防御方案最终被攻破，核心原因在于 JSONP 架构本身的固有缺陷与高价值资产的不兼容性：

- **信任边界过于脆弱**：JSONP 依赖 `<script>` 标签发起请求，浏览器在加载外部脚本时天然会附带当前站点的 Cookie/登录态。只要接口支持 JSONP，攻击者就能通过跨站脚本引用诱发凭据传输。
    
- **来源校验存在单点崩溃风险**：即使配置了严格的 Referer 校验，一旦企业存在某个被接管的子域名（Subdomain Takeover）、开放重定向（Open Redirect）漏洞，或者第三方合作伙伴页面被攻破，攻击者即可利用合法信任源绕过检查，直接把私密数据批量拖走。
    
- **防御成本与资产价值倒挂**：公共数据（如天气预报、汇率查询）即使校验被绕过也无实质危害；而对于资产、隐私类数据，一旦防御链中出现微小疏漏（如正则未转义点号），损失往往是灾难性的



2. ==敏感接口与数据的界定标准==

在企业 API 治理中，凡符合以下任一特征的接口，均必须列入 **JSONP 绝对禁用清单**：

|**接口分类**|**具体敏感字段 / 场景**|**滥用危害**|
|---|---|---|
|**身份与凭据接口**|Session ID、Token、CSRF Token、SSO 票据、权限列表、用户登录状态|导致全量账号被盗、权限冒用、Session 固定攻击|
|**个人身份信息 (PII)**|真实姓名、身份证号、手机号、家庭住址、邮箱、通讯录|个人隐私泄露、撞库、电信诈骗情报收集|
|**金融与资产数据**|银行卡号、账户余额、积分点数、消费记录、订单收货信息|经济损失风险、商业交易机密泄露|
|**写操作与状态变更**|修改密码、绑定手机、转账、点赞/关注、提交表单|CSRF 攻击变种（利用 GET 产生副作用破坏系统状态）|

>**判定原则**：只要接口响应的数据内容**因请求者身份的不同而发生变化（具备上下文个性化/私密性）**，该接口就严禁支持 JSONP。只有全网公开、任何匿名访客访问内容均完全一致的数据，才
>允许开放跨域只读服务



3. ==企业级落地与治理策略（例）==

禁止敏感接口开放 JSONP 是一项系统工程，需要从开发规范、网关控制和发布流水线实现多层治理：


网关与反向代理集中拦截

在 API 网关（如 Kong、APISIX、Envoy）或 Nginx 层面实施规则控制：

- **阻断参数**：针对用户中台、订单、支付等敏感路径（如 `/api/v1/user/*`、`/api/account/*`），一旦请求 Query 中包含 `callback`、`cb`、`jsonp` 等参数，直接剥离参数或返回 `HTTP 400 Bad Request`。
    
- **强制响应类型**：统一敏感路由的输出格式，强制设置 `Content-Type: application/json; charset=utf-8`，彻底阻断返回可执行脚本



框架层与架构解耦（无 Cookie 策略）

若业务中存在历史遗留的、确实需要跨域调用的数据接口：

- **剥离登录凭据**：在网关层对 JSONP 路由强行剥离 `Cookie` 请求头，确保该接口只能以匿名状态运行。
    
- **Token 隔离**：不在 URL 参数中接受身份凭证，避免敏感会话信息暴露于日志和浏览器历史记录中。




CI/CD 代码审计与卡点

- **AST 语法扫描**：在代码扫描流水线（SonarQube、Semgrep 等）中配置规则，扫描针对包含鉴权注解（如 `@RequireAuth`、`@PreAuthorize`）的控制器（Controller）。若该控制器中存在类似 `MappingJackson2JsonView`、`JSONPObject` 或手动拼接 `callback` 的逻辑，直接触发构建失败并告警









## 替换现代方案：CORS策略

JSONP 是在浏览器缺乏跨域机制时代的折中方案，存在无法配置请求类型（仅支持 GET）、缺乏原生凭据精细控制、天然暴露数据接口等架构缺陷。

|**维度**|**JSONP**|**CORS (Cross-Origin Resource Sharing)**|
|---|---|---|
|**HTTP 方法**|仅限 GET|支持 GET、POST、PUT、DELETE 等全部方法|
|**错误处理机制**|难以捕获 HTTP 4xx/5xx 状态码|支持完整的状态码与网络错误捕获|
|**安全控制**|依赖 Referer 与 Callback 过滤，极易受劫持|原生基于 Origin 协议协商，细粒度控制请求头与凭据|
|**XSS / 注入风险**|高（依赖字符串拼接）|极低（纯数据传输，返回 `application/json`）|

现代 Web 应用应直接将接口重构为标准 REST/JSON 接口，配合服务端设置明确的 CORS 头：

例：
![](Pasted%20image%2020260902221934.png)





从架构层面彻底杜绝 JSONP 风险的最佳方式是废弃 `<script>` 注入机制，改用 **CORS + Fetch/XHR**：

1. **响应类型隔离**：CORS 接口直接返回 `Content-Type: application/json`。浏览器遇到非 JS 语法的数据格式不会作为脚本执行，杜绝 XSS。
    
2. **强制标准 Origin 验证**：CORS 规范强制浏览器在跨域请求时发送不可伪造的 `Origin` 请求头，服务端根据 `Origin` 决定是否下发 `Access-Control-Allow-Origin`。
    
3. **支持自定义 Header 拦截**：要求前端在请求头中携带自定义 Header（如 `X-Requested-With: XMLHttpRequest`），跨站普通的 HTML 标签（如 `<script>`、`<img>`）无法添加自定义 Header，杜绝非预期的隐式跨站调用
