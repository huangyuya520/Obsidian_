
# xss防护方法

## 使用HTML实体转义方法防护xss攻击
**HTML 实体转义（HTML Entity Encoding）** 是防御存储型与反射型跨站脚本（XSS）攻击的基础手段。==其核心逻辑是将 HTML 语法中的敏感控制字符替换为对应的实体编码，使浏览器将其解析为**普通文本内容**，而非可执行的 HTML 标签或属性==

1. ==核心转义原理与关键字符==
浏览器在解析 HTML 时，依赖特定字符识别标签结构、属性边界以及脚本指令。如果未对用户输入进行处理，恶意输入（如 `<script>`）将被识别为 DOM 节点并执行。

实体转义通过破坏代码执行的语法结构实现拦截。OWASP 推荐必须进行实体转义的五大核心控制字符如下：

|**原始字符**|**实体名称（Entity Name）**|**实体编号（Entity Number）**|**语法威胁与转义目的**|
|---|---|---|---|
|`&`|`&amp;`|`&#38;`|实体声明前缀；**必须最先转义**，防止二次转义或混淆|
|`<`|`&lt;`|`&#60;`|阻止闭合现有标签或注入新的 HTML 标签（如 `<script>`）|
|`>`|`&gt;`|`&#62;`|阻止闭合标签属性或指令标记|
|`"`|`&quot;`|`&#34;`|阻止跳出双引号包裹的 HTML 属性边界|
|`'`|`&#39;` / `&apos;`|`&#39;`|阻止跳出单引号包裹的 HTML 属性边界|
|`/`|`&#x2F;`|`&#47;`|阻止在闭合标签或特定属性中利用闭合路径闭合上下文|

>**执行顺序：** 转义处理时必须优先将 `&` 替换为 `&amp;`。如果最后转义 `&`，之前生成的 `&lt;` 会错误地二次转义为 `&amp;lt;`，导致页面显示乱码。





HTML实体转义会把一些危险的符号转义为普通文本，使浏览器不
会把它们当作HTML代码来解析，且不影响用户的使用。可以使用语言
自带的转义函数，也可以手动实现这样的操作

3. ==HTML 实体转义的局限性与失效场景==
HTML 实体转义**并非万能防护**。它==仅在 **HTML 标签文本内容（HTML Body）** 和 **普通 HTML 属性值** 场景下有效==。在其他上下文中，由于解析引擎不同或存在二次解码，转义策略会彻底失效。



- 场景一：直接放入 `<script>` 标签内（JavaScript 语境）

例：
![](Pasted%20image%2020260902105131.png)
- **失效原因**：`<script>` 标签内部的内容由 JavaScript 解释器解析，而非 HTML 解析器。JavaScript 解析器不会把 `&quot;` 当作引号实体解码，而是直接抛出语法错误或在无引号的数值注入处直接执行代码。







- 场景二：内联事件处理器（二次解码陷阱）

例：
```
<button onclick="display('<?php echo htmlspecialchars($input, ENT_QUOTES); ?>')">Click</button>
```

**失效原因**：浏览器处理内联事件（如 `onclick`、`onload`、`onerror`）时遵循两阶段解析：

1. **HTML 解析器**首先执行，将 `&quot;` 解码回真实的引号 `"`。
    
2. **JavaScript 解析器**接管并执行解码后的代码，导致逃逸出字符串边界执行注入代码





- 场景三：URL 伪协议（`href` / `src` 属性）

例：
```
<a href="<?php echo htmlspecialchars($input, ENT_QUOTES); ?>">点击访问</a>
```

**失效原因**：如果攻击者输入 `javascript:alert(1)`，该字符串中不包含 `<`、`>`、`"`、`'` 等特殊字符，实体转义对其无影响。当用户点击链接时，浏览器仍会触发 JavaScript 伪协议执行代码




4. ==综合纵深防御方案==

单一的 HTML 实体转义不足以抵御所有 XSS 攻击，实际工程中应结合以下策略实施纵深防御：

1. **根据上下文执行精准编码**：
    
    - **HTML Body / Attribute**：使用 HTML 实体转义（如 `htmlspecialchars`）。
        
    - **JavaScript 变量**：使用 Unicode/JSON 转义（如 `json_encode` 或 `\uXXXX` 编码）。
        
    - **URL 参数**：使用标准 URL 编码（如 `encodeURIComponent`），并校验协议前缀白名单（禁止非 `http://`、`https://` 协议）。

2. **现代前端框架内置保护**：
    
    - React（JSX `{value}`）、Vue（模板 `{{value}}`）以及 Angular 默认将变量视为字符串并自动执行上下文编码。避免在未经处理的情况下使用 `dangerouslySetInnerHTML` 或 `v-html`。

3. **富文本输入采用白名单过滤**：
    
    - 针对需要保留部分 HTML 格式的场景（如文章编辑器），不能单纯实体转义，必须使用经受实战检验的 HTML 清洗库（如 **DOMPurify**），通过白名单剔除危险标签和事件属性。

4. **启用内容安全策略（CSP）**：
    
    - 在 HTTP 响应头配置 `Content-Security-Policy`（例如限制 `script-src 'self'`），禁止加载内联脚本和未授权的外部脚本，切断 XSS 载荷的最终执行路径

## 设置`Cookie`的 `HTTP-only`防护xss攻击
**HttpOnly** 是 HTTP 响应头 `Set-Cookie` 中的一个关键安全指令。==它的核心作用是**切断浏览器端 JavaScript 对特定 Cookie 的访问权限**==，是防御因跨站脚本（XSS）漏洞导致会话劫持（Session Hijacking）最关键的纵深防御手段。

需要明确的是：**HttpOnly 无法阻止 XSS 漏洞被触发，但它能阻止攻击者直接窃取敏感凭证（如 Session ID、JWT）**




1. ==核心工作原理==

在 Web 体系中，Cookie 的交互通常存在两条路径：

1. **网络层自动传输（安全路径）：** 浏览器发送 HTTP 请求时，无论是否设置 HttpOnly，都会自动在请求头 `Cookie` 中携带对应域名的 Cookie，供服务端校验身份。
    
2. **DOM 脚本接口（风险路径）：** 浏览器提供 `document.cookie` 接口，允许页面运行的 JavaScript 读写 Cookie


|**场景**|**未设置 HttpOnly**|**设置 HttpOnly**|
|---|---|---|
|**HTTP(S) 请求传输**|浏览器自动附加在请求头中|浏览器自动附加在请求头中|
|**`document.cookie` 读取**|**允许**（攻击脚本可直接读取并外发）|**禁止**（返回空字符串或不包含该 Cookie）|
|**`document.cookie` 覆盖/修改**|允许覆盖已有 Cookie|禁止通过前端脚本覆盖已有 HttpOnly Cookie|



当目标 Cookie（如 `session_id`）设置了 `HttpOnly` 标志后，即便攻击者成功在页面中注入并执行了 `<script>` 恶意代码，当其尝试执行 `var stolen = document.cookie;` 时，也无法获取到带有 HttpOnly 属性的凭证内容

4. ==HttpOnly 的局限性与残留风险==

虽然 HttpOnly 极大降低了凭据被直接盗取的风险，但**不能等同于解决了 XSS**。攻击者在拥有页面 JS 执行权的前提下，仍有以下利用路径：

1. **会话代理操作（XSS 驱动的虚拟 CSRF）：**
    
    - 攻击者不需要读取 Cookie 明文。只要在受害者浏览器中发起 `fetch('/api/account/transfer', {method: 'POST', body: ...})`，浏览器依然会**自动在网络层附带 HttpOnly Cookie**，直接在受害者当前活跃会话下执行非法操作。

2. **内联钓鱼与表单嗅探：**
    
    - 攻击者可利用 DOM 操作注入伪造的“登录过期，请重新输入密码”弹窗，监听键盘输入，直接盗取用户的原始明文账号和密码。

3. **敏感页面内容爬取：**
    
    - 攻击者可读取页面的 DOM 树，获取用户的手机号、身份证号、聊天记录等直接呈现在前端界面的隐私数据，并发送回攻击者服务器。

4. **历史协议攻击（Cross-Site Tracing, XST）：**
    
    - 若 Web 服务器启用了 HTTP `TRACE` 方法，攻击者在旧版客户端环境中曾可通过发送 TRACE 请求迫使服务器反射请求头（包含客户端发送的所有 Cookie）来绕过 HttpOnly。_现代浏览器和主流 Web 服务器默认已彻底禁用或拦截针对 TRACE 的脚本调用_





5. ==Cookie 纵深防御最佳组合==

为保证会话凭证的安全，不应仅依赖单一的 `HttpOnly`，应配合以下安全基线：

- **`HttpOnly` + `Secure` + `SameSite=Lax/Strict`**：
    
    - `HttpOnly` 防护前端脚本读取。
        
    - `Secure` 确保凭据仅通过 TLS/HTTPS 加密信道传输，杜绝中间人嗅探。
        
    - `SameSite` 防御第三方网站发起的跨站伪造请求（CSRF）。

- **采用 Cookie 前缀标准（Cookie Prefixes）**：
    
    - 将关键 Cookie 命名为 `__Host-SessionId`。浏览器规范强制要求带有 `__Host-` 前缀的 Cookie 必须包含 `Secure` 属性、来自安全源、路径为 `/` 且不得被子域名覆盖，有效防御子域名污染与 Cookie 投毒。

- **从根本上消除 XSS**：
    
    - 配置强 **Content-Security-Policy (CSP)** 限制脚本加载源与内联执行；
        
    - 坚持在视图渲染层做**上下文自适应的 HTML 实体转义**与输入净化

## 使用内容安全策略(CSP)防护xss攻击
**内容安全策略（Content Security Policy, CSP）** ==是一种由服务端通过 HTTP 响应头传递给浏览器的声明式安全机制==。它是目前针对跨站脚本（XSS）攻击**最关键的纵深防御底线**。

与“转义”、“过滤”等试图清洗输入的防御机制不同，CSP 的逻辑是：**即便攻击者的恶意代码成功注入到了 HTML 结构中，浏览器也会基于安全策略直接拒绝解析、下载或执行该脚本**



1. ==CSP 防御 XSS 的三大核心拦截机制==

浏览器在解析启用了 CSP 的页面时，会强制施加以下底层约束：

- **默认禁用内联脚本与事件处理器：** 页面中直接书写的 `<script>alert(1)</script>` 以及内联事件（如 `<img onerror="..." />`、`<button onclick="...">`）将被浏览器直接拦截，阻止执行。
    
- **默认禁用动态代码求值：** 阻断类似 `eval()`、`new Function()`、`setTimeout('alert(1)', 100)` 等将字符串当作代码执行的 JavaScript 运行时 API（触发报 `EvalError`）。
    
- **严格限制资源加载来源：** 限制 `<script src="...">`、`fetch()`、`XMLHttpRequest` 的请求目标域，阻止恶意脚本从黑客外部服务器加载第二阶段载荷（Payload），或向不受信服务器外带窃取敏感数据


 




2. ==使用内容安全策略防御 XSS 的关键指令==

| **指令**            | **作用域与安全威胁**                                        | **推荐的安全配置**                                |
| ----------------- | --------------------------------------------------- | ------------------------------------------ |
| ==`script-src`==  | **核心指令**。限定 JavaScript 脚本的加载与执行权限。                  | `'nonce-{RANDOM}' 'strict-dynamic'` 或严格白名单 |
| `object-src`      | 控制 Flash、Java Applet 等插件加载（历史 XSS 高发区）。             | `'none'`（现代 Web 几乎已不需要插件）                  |
| `base-uri`        | 限制 `<base href="...">` 标签，防止攻击者篡改相对路径基础 URL 劫持脚本源。  | `'none'` 或 `'self'`                        |
| `connect-src`     | 限制 `fetch`、`XHR`、`WebSocket` 发送目标，阻止 XSS 执行后外发窃取数据。 | `'self'` 配合业务必须的 API 域名                    |
| ==`default-src`== | 兜底指令。其他未明确声明的 `-src` 指令自动沿用此项配置。                    | `'self'` 或 `'none'`                        |





3. ==从传统“域名白名单”到现代“严格 CSP（Strict CSP）”==

- 早期 CSP 大量采用**域名白名单**机制，例如：

例：
```
Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted-cdn.com;
```

但在工程实践中，域名白名单极易被绕过：

1. **JSONP 接口绕过：** 若白名单域（如 Google、CDN、企业自建服务）中存在任何开放的 JSONP 接口，攻击者可直接构造 `<script src="[https://trusted-cdn.com/api?callback=alert](https://trusted-cdn.com/api?callback=alert)">` 绕过 CSP。
    
2. **Angular / Vue 客户端模板注入：** 若白名单库中包含旧版本的前端框架，攻击者可通过内联 HTML 属性注入表达式，利用框架的解析器执行代码



- 基于 Nonce 的严格 CSP (Strict CSP)（推荐方案）
Google 等安全团队倡导的现代最佳实践是基于密码学随机数的 **Strict CSP（Level 3）**：

例：
![](Pasted%20image%2020260902114253.png)
- **`'nonce-{随机字符串}'`**：服务端每次响应时动态生成一个加密安全的随机 Token，并写入 HTTP 头及合法的 `<script nonce="rAnd0m123">` 标签。攻击者由于无法预测当次请求的 Nonce，注入的 `<script>` 标签因缺少正确的 Nonce 将被浏览器拒绝执行。
    
- **`'strict-dynamic'`**：告知现代浏览器信任已通过 Nonce 验证的脚本动态创建的子脚本（例如模块加载器动态注入的 script），无需手动将每个子依赖域加入白名单。
    
- **回退保护**：当支持 Level 3 的现代浏览器识别到 `'strict-dynamic'` 时，会自动忽略后面的 `https:` 和 `'unsafe-inline'`；而老旧浏览器则能向下兼容
