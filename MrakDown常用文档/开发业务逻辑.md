## 项目策划书 / GDD

一份标准的Web策划案涵盖以下几个核心模块：

1. ==项目概述与目标==
- **项目背景**：为什么要做这个Web项目？解决什么痛点？
- **目标用户**：目标受众是谁（年龄、职业、兴趣、痛点）？
- **核心商业/服务目标**：希望达成什么样的转化（如提升销量、注册量、品牌展示）？

2. ==竞品分析与市场定位==
- **竞品调研**：分析3-5个同类竞品的优劣势。
- **差异化定位**：提炼本项目相较于竞品的独特卖点（USP）。

3. ==需求分析与功能规划==
- **核心功能模块**：例如用户系统、支付系统、后台管理、内容发布等。
- **功能清单（Product Backlog）**：将功能拆分为颗粒度较小的任务，区分**MVP（最小可行性产品）** 和后续迭代功能。
- **非功能性需求**：安全性（防刷、数据加密）、性能指标（首屏加载速度、并发支持）等。

4. ==信息架构与用户体验（UX）==
- **网站地图（Site Map）**：梳理网站的层级结构（首页 → 详情页 → 结算页等）。
- **业务流程图**：梳理核心业务路径，如用户从注册、浏览到下单的完整闭环。
- **原型图草案（Wireframes）**：低保真或高保真原型，明确页面布局和交互逻辑。

5. ==技术方案与规范==
- **技术栈选型**：前端（Vue/React）、后端（Node.js/Python/Java）、数据库（MySQL/MongoDB）等。
- **运行环境**：多端适配（PC端、移动端H5、响应式设计）、浏览器兼容要求。
- **数据接口**：API设计规范及第三方服务集成（如微信支付、地图API、短信接口）。

6. ==项目计划与资源配置==
- **时间节点（Timeline）**：包含UI设计、前端开发、后端开发、测试（QA）及上线时间。
- **人员配置**：项目经理（PM）、UI设计师、前端开发、后端开发、测试人员等。
- **里程碑设定**：分阶段交付的目标（例如Alpha版、Beta版、正式发布）。

7. ==测试、运营与风控==
- **测试计划**：功能测试、兼容性测试、性能压测及安全审计。
- **上线与运营**：SEO（搜索引擎优化）方案、上线后的推广计划。
- **风险预案（风险管理）**：技术延期风险、预算超支风险、服务器宕机备用方案。






## 规范驱动开发(SDD)

主要包含以下典型的自动化开发阶段：

- 规范制定（Specify）：人类与 AI 合作将高层需求扩展为结构化规范（用例、约束、验收标准等），并反复校对确保无歧义。
- 规划设计（Plan）：AI 基于规范输出实现方案（架构、组件、接口契约、技术栈），并接受组织约束（例如必须使用的框架）。
- 分解任务（Tasks）：AI 将计划拆成一系列小且可测试的任务，每个任务有明确的完成标准。
- 实现与测试（Implement & Test）：AI 逐项实现并运行与规范对应的验证（单元/集成/性能测试），只有通过验证才继续下一个任务。
- 部署与交付（Deploy）：AI 可生成并执行部署脚本、CI/CD 配置，甚至在受控环境中自动化部署。






## 系统架构设计文档(SAD)(技术方案方向细化)

1. ==单体架构==

2. ==微服务式架构(容器化架构)==


一份标准的架构设计文档通常包含以下核心结构：

1. ==文档概述与背景==
- **业务背景**：描述项目启动的原因与业务痛点。
- **架构目标**：系统需要满足的核心指标（如高并发、低延迟、高安全性）。
- **项目范围**：明确系统的边界，即系统做什么、不做什么。 

2. ==需求与复杂度分析==
- **功能需求**：系统需提供的核心业务功能模块。
- **非功能性/复杂度分析**：针对性能（TPS/QPS）、可用性、安全性、可扩展性等进行量化分析，并给出技术推导。

3. ==多视图架构设计==
主流架构设计会采用类似“4+1视图模型”或综合多维图表，从不同角度解析系统：
- **逻辑视图**：面向开发人员，展示系统的功能模块划分、领域模型与核心类图。
- **物理/部署视图**：面向运维，展示系统的服务器节点、网络拓扑、云资源及负载均衡配置。
- **进程视图**：面向系统运行时，描述进程间的通信、线程及数据流向。 

4. ==关键技术选型==
- **技术栈**：前后端框架、数据库（SQL/NoSQL）、缓存、消息队列等选型说明及理由。
- **架构模式**：如采用微服务、事件驱动或分层架构。 

5. ==核心模块与数据设计==
- **核心模块划分**：详细拆解各子系统的职责、依赖关系与交互协议。
- **数据模型**：数据存储方案、分库分表策略、E-R图及数据流向说明。

6. ==接口与非功能性设计==
- **接口设计**：内部模块通信协议与外部API规范（如RESTful、gRPC）。
- **容灾与安全**：数据备份、异常恢复策略、权限认证机制与防刷策略。

### API接口文档(后端)

一份标准的 API 接口文档通常包含以下核心部分：

- ==**接口描述**==：简述该接口的功能和业务逻辑（例如：获取用户信息、提交订单等）。

- ==**请求地址（URL）**==：调用接口的目标路径（通常分为生产环境和测试环境地址）。

- ==**请求方法**==：常见的有 `GET`（用于获取数据）和 `POST`（用于提交或修改数据）。

- ==**请求参数**==：调用接口时需要提供的数据字段，包含参数名、数据类型（如字符串、整数）、是否必填及字段说明。

- ==**响应内容（返回结果）**==：接口调用成功后返回的数据结构（通常为 JSON 格式），包含各字段的含义。

- ==**错误代码**==：列出请求失败时返回的状态码及对应的解决方案，方便排查问题（如 `400` 参数错误，`401` 未授权等）。







### 页面结构与组件规划(前端)

1. 信息架构与路由拓扑（Page & Route Map）

- **页面清单与层级**：明确一级菜单、二级子页、以及以抽屉（Drawer）或弹窗（Modal）形式承载的轻量级操作视图。
    
- **权限与路由守卫**：定义各页面对应的 RBAC 权限码，明确未登录跳转、无权限（403）和路径失效（404）的统一承接页。
    
- **URL 参数契约**：规定筛选条件、分页页码或详情 ID 是否同步到 URL Query 中，确保用户刷新页面或分享链接时能准确还原上下文。



2. 页面布局骨架与响应式策略（Layout & Grid）

- **区域划分**：定义全局固定区（顶部导航、侧边菜单）、核心动态工作区（主内容区）以及全局浮层（消息提示、确认框）。
    
- **栅格与断点规则**：说明在常见屏幕尺寸（如 1920px、1440px、1280px 及移动端）下的栏数折叠规则、侧边栏收起阈值以及表格横向滚动策略，防止小屏下布局错位。



3. 组件层级拆解（原子化架构）

行业内通常采用原子设计（Atomic Design）思想对页面自底向上拆解，将视觉元素划分为“原子、分子、有机体、模板、界面”五个层级，以此对齐设计与研发语言：


|拆分层级|工程定位|典型组件示例（以网络设备管理后台为例）|归属与维护策略|
|---|---|---|---|
|**原子（Atoms）**|不可再分的基础 UI 元素|按钮、输入框、开关、在线/离线状态灯|直接映射基础组件库，禁止随意改写样式|
|**分子（Molecules）**|多个原子组合的单一功能单元|带格式校验的 IP/子网掩码输入组、搜索栏|沉淀为项目级公共基础组件|
|**有机体（Organisms）**|相对独立的复杂业务区块|顶部筛选栏、端口状态数据表、拓扑图面板|封装特定领域逻辑，按业务模块复用|
|**模板（Templates）**|页面骨架与区块排布规范|“左树右表”布局模板、主从详情页模板|统一全站视觉节奏，不含具体业务数据|
|**界面（Pages）**|注入真实数据的最终页面|交换机端口配置页、路由策略监控页|负责路由参数解析、API 调度与区块联动|


4. 组件数据契约与前后端边界（Props / Events / API）

这是“前后端功能拆分”最关键的衔接部分，需要针对每个“有机体”和“页面”写明：

- **容器组件与展示组件分离**：明确哪一层负责调用后端接口（通常由页面或顶层有机体发起），底层分子/原子组件只通过输入属性（Props）接收数据、通过事件（Events）向上抛出用户操作，保持纯粹的展示职责。
    
- **状态归属划分**：清晰标注哪些是**局部 UI 状态**（如折叠面板展开与否）、哪些是**全局共享状态**（如当前登录用户信息、主题设置）、哪些是**服务端数据状态**（如设备列表、告警日志）。
    
- **计算与交互职责切分**：明确列表的分页、排序、模糊搜索是由**前端内存完成**还是**后端接口完成**；明确数据拉取时机（初始化加载、点击触发、定时轮询还是 WebSocket 推送）。



5. 交互状态机与异常兜底矩阵（UI State Matrix）

文档绝不能只描述“数据正常返回”的理想状态，每个依赖外部数据的组件都必须补充以下五种状态定义：

- **加载态（Loading）**：首屏使用骨架屏稳定页面结构，局部刷新使用微加载提示，避免整页闪烁。
    
- **空状态（Empty）**：严格区分“从未创建数据（提供引导新建按钮）”与“筛选条件无匹配（提供一键重置按钮）”。
    
- **错误态（Error）**：接口超时或返回 5xx 时，提供可读的错误说明与“点击重试”入口，而非直接暴露原始报错码。
    
- **部分降级态（Partial Failure）**：当一个复合页面包含多个独立接口（如仪表盘同时拉取流量图与日志表）时，单个模块失败只能局部报错，不得阻塞其他模块渲染。
    
- **锁定与防重态（Disabled / Submitting）**：表单提交或指令下发期间自动禁用提交按钮并展示处理中状态，防止网络延迟引发重复提交。




















### 生成数据文件结构设计

1. 业务场景与前后端职责边界

明确文件生成的上下文，防止前后端在边界逻辑上互相推诿：

- **生成触发机制**：区分同步按需生成（前端请求后实时流式返回）、异步任务生成（后端离线组装完成后通知前端下载）以及定时批处理生成。
    
- **职责切分矩阵**：清晰界定前后端在每个环节的责任：
    

|**生命周期阶段**|**后端职责（生产端）**|**前端职责（消费端）**|
|---|---|---|
|**参数协商**|校验导出/生成条件、权限鉴权、评估数据量级|收集筛选条件、传递目标格式与版本号|
|**生成与存储**|数据抽取、脱敏、序列化、压缩、落盘或上传对象存储|轮询任务状态或接收进度推送、展示等待交互|
|**传输与校验**|提供下载通道（流/预签名 URL）、输出文件摘要值|处理分片下载/断点续传、核对完整性校验码|
|**解析与兜底**|记录失败原因、清理过期临时文件|校验 Schema 版本、流式解析、处理空数据与错误提示|



2. 文件全局物理规范

在进入具体字段前，必须先锁定文件层面的底层通信与存储标准：

- **文件命名规范**：采用结构化、无歧义的命名模板，例如 `{业务域}_{数据类型}_{YYYYMMDDHHmmss}_{版本号}_{批次号}.{扩展名}`，同时禁止空格及系统非法字符，保证重试时的幂等性与防覆盖。
    
- **封装格式与编码**：明确是文本类（JSON、CSV、XML、JSONL）还是二进制类（Protobuf、Parquet、自定义二进制帧）；必须锁定字符集（默认 UTF-8，若面向 Excel 导出需写明是否携带 UTF-8 BOM）、行尾换行符（统一 `LF` 还是 `CRLF`）以及二进制文件的字节序（大端序 Big-Endian 或小端序 Little-Endian）。
    
- **压缩与加密包装**：约定压缩算法（Gzip、Zip、Zstd）、分卷策略、传输/静态加密方式（如 AES-256-GCM），以及文件级校验码算法（SHA-256 或 CRC32）。



3. 文件逻辑分层与字段定义（核心章节）

无论采用文本还是二进制格式，在数据通信场景下，建议统一按**三段式结构**进行文档建模：

1. **文件头（Header / Metadata）**：存放协议版本（`schema_version`）、生成时间戳、数据来源标识、编码方式、总记录数（`record_count`）及加密标志。
    
2. **数据体（Body / Payload）**：核心业务数据集合，需说明数组嵌套层级、排序规则、主键唯一性以及多模块间的引用关系。
    
3. **文件尾（Footer / Trailer）**：存放汇总统计信息（如金额总计）、结束标记（EOF 标识）以及覆盖 Header 与 Body 的完整性校验摘要（`checksum`），用于防止文件传输截断。


**字段清单必须使用标准表格固化，示例模板如下：**

|**字段名**|**层级路径**|**物理类型**|**长度/精度**|**必填**|**默认值**|**取值约束与业务说明**|
|---|---|---|---|---|---|---|
|`schema_version`|`header.schema_version`|`string`|最大 16 字节|是|无|语义化版本号，如 `1.2.0`，用于解析器路由|
|`tx_id`|`body[].tx_id`|`string`|固定 19 位|是|无|分布式长整型 ID，防前端精度丢失强制转字符串|
|`amount`|`body[].amount`|`string`|精确到小数点后 4 位|是|`"0.0000"`|定点数金额字符串，禁止使用二进制浮点数|
|`event_time`|`body[].event_time`|`int64`|13 位|是|无|UTC 毫秒级时间戳，时区偏移统一由前端转换|
|`status`|`body[].status`|`uint8`|0 至 3|是|`0`|枚举：`0`-待处理，`1`-成功，`2`-失败，`3`-已撤销|
|`checksum`|`footer.checksum`|`string`|64 位十六进制|是|无|`body` 原始字节流的 SHA-256 摘要值|




4. 数据通信流程与异常容错规范

- **大小阈值与分片策略**：规定单文件体积或行数上限（例如单文件不超过 50 MB 或 10 万行）；超限时说明分卷规则以及汇总索引文件（如 `manifest.json`）的结构。
    
- **异步状态同步契约**：若文件耗时较长需异步生成，文档需附带任务状态机（`PENDING` → `GENERATING` → `READY` / `FAILED`）及状态查询接口的返回结构。
    
- **异常与空数据兜底**：明确当查询结果为空时，是生成“仅含表头/空数组的有效文件”，还是直接中止生成并返回特定业务错误码；当单条记录存在脏数据时，是跳过并输出错误清单文件，还是整包失败回滚。




5. 版本演进与兼容性策略

- **向后兼容原则**：约定消费端遇到未定义的扩展字段时应**静默忽略**而非抛出异常，允许生产端平滑新增可选字段。
    
- **破坏性变更规则**：明确字段删减、类型变更或语义重构必须升级主版本号（Major Version），并约定旧版本结构的并行兼容窗口期。





6. 标准数据样例（不可省略）

文档末尾必须提供可直接用于自动化测试与 Mock 联调的真实样例，且至少覆盖三类：

- **标准全量样例**：包含所有核心字段及嵌套结构的完整合法文件。
    
- **边界条件样例**：包含空集合、超长字符串、特殊转义字符（引号、逗号、换行符、Emoji）及 `null` 值。
    
- **异常/失败回执样例**：生成失败或校验不通过时的错误描述结构。










### 开发里程碑与任务拆解

#### 让 UI 与 UX 设计更符合大众使用习惯
1. 顺应心智模型（雅各布定律）

用户绝大多数时间都在使用其他成熟软件，因此他们对界面位置存在强烈的“肌肉记忆”。

- **布局惯例**：品牌标识置左上、主导航置左侧或顶部、关闭按钮置弹窗右上角、全局搜索置顶栏。
    
- **操作习惯**：确认按钮与取消按钮的位置全站统一；高危操作（删除、重置、重启）统一使用警示红色。将创新精力集中在业务流提效上，而非强行改变用户的通用操作预期。



2. 降低决策负担（希克定律与渐进式披露）

选项越多，用户的决策耗时呈对数级增长。

- **控制单屏焦点**：核心操作区的主按钮每屏不超过 1 个，同级导航或操作菜单尽量控制在 5 到 7 项以内。
    
- **渐进式披露（Progressive Disclosure）**：遵循二八原则，首屏只暴露 80% 用户最常用的核心字段；低频高级配置（如网络参数中的高级 QoS 或自定义报文超时）收纳入“高级选项”折叠面板或次级抽屉中。
    
- **符合视觉浏览动线**：列表与表格型页面契合 **F 型动线**（核心标识放最左列，操作列放最右且固定）；概览与看板页契合 **Z 型动线**（左上放关键 KPI，右下放行动入口）。




3. 强化空间关联与操作效率（完形心理学与菲茨定律）

- **亲密性分组**：逻辑相关的组件在视觉上紧密排布，无关模块用留白或分割线明确区隔。例如，表单的标签应紧贴其对应的输入框，而不是等距居中导致归属模糊。
    
- **合理的热区与距离**：高频点击控件（如提交按钮、复选框连同文字标签）应扩大可点击热区；破坏性操作按钮（如“删除配置”）应与高频确认按钮保持物理距离，降低误触概率。




4. 建立可预期反馈与防错机制（尼尔森可用性原则）

- **响应时间分层反馈**：小于 0.1 秒的交互让用户感知为瞬时响应；超过 1 秒必须展示明确加载进度；超过 10 秒的异步长任务（如批量配置下发）应转为后台任务队列，允许用户切走处理其他工作并通过消息中心接收完成通知。
    
- **防错优于纠错**：能用选择器、单选框或格式化输入组件限制输入范围的，就不要提供自由文本框；校验提示采用失焦即时内联提示，并在出错字段旁直接说明“如何修改”，而不是只弹出冰冷的“参数非法”。
    
- **提供安全退出与无障碍冗余**：轻度操作优先提供“撤销（Undo）”而非频繁弹窗打断；高危不可逆操作则要求输入目标名称进行二次确认。此外，严禁仅靠颜色区分状态（需照顾色弱群体），例如设备状态指示应同时结合“颜色 + 图标 + 文字”（如绿色圆点配“运行中”、红色三角配“链路中断”）。







#### 编写文档时的核心注意事项

结合数据通信的严谨性与前后端工程落地的常见痛点，编写时需重点把控以下八项原则：


==数据通信与底层解析视角==

1. **彻底消除数据类型二义性与精度丢失** 切忌在文档中只写“数字”“时间”等模糊词。前端 JavaScript 的 `Number` 类型采用 IEEE 754 双精度浮点数，最大安全整数仅为 $2^{53}-1$（即 9007199254740991）。后端的 `int64`（如雪花算法 ID）以及高精度金融金额（`Decimal`），在 JSON 或文本数据文件中**必须强制约定以字符串形式序列化**。
    
2. **时间与时区标准绝对唯一** 严禁使用 `2026/11/27 10:00` 这类缺失时区的本地化字符串。数据文件内统一采用带时区的 ISO 8601（如 `2026-11-27T15:00:00Z`）或明确注明单位的 UTC 毫秒时间戳，把本地时区格式化完全留给前端展示层。
    
3. **显式锁定编码、转义与字节序**
    
    - CSV 类文件必须注明遵循 RFC 4180 转义规范（字段含逗号、换行或双引号时如何包裹与转义），否则极易在前端解析时发生错列。
        
    - 涉及网络协议包或高性能二进制数据文件时，必须标明**字节序（通常网络传输统一采用大端序）**、结构体字节对齐方式以及变长字段的长度前缀类型，防止跨架构设备解析出乱码。
        
4. **防“半截文件”的完整性设计** 在不可靠网络或进程异常退出场景下，文件可能只写入了一半。除了依赖传输层的 HTTP `Content-Length`，文件自身结构设计最好包含头部预期条数与尾部哈希校验，要求消费端“先校验、后入库/渲染”。

---

==前后端协同与工程安全视角==

1. **严守数据与视图解耦** 生成的数据文件只应承载客观结构化数据与状态枚举，不要在文件中硬编码前端 UI 逻辑（如颜色十六进制值、HTML 拼接标签、写死的提示文案）。这样一份数据文件才能同时被 Web 端、移动端和第三方数据接口复用。
    
2. **提前划定前端内存与性能红线** 浏览器单标签页内存有限，一次性 `JSON.parse()` 解析几十兆的巨型 JSON 文件极易引发页面卡死或内存溢出。设计文档应在前期就评估数据量级：大数据量场景应优先选用按行流式解析友好的 **JSONL（JSON Lines）** 或 CSV 格式，或约定后端按页拆分。
    
3. **内嵌安全与脱敏规则**
    
    - **敏感数据脱敏**：在字段表中直接标明手机号、证件号、令牌等字段的脱敏掩码规则或禁止落盘要求。
        
    - **防范公式注入（CSV Injection）**：若生成的文件供用户在表格软件中打开，文档需规定对以 `=`、`+`、`-`、`@` 开头的文本单元格做前置转义处理，防止恶意公式执行。
        
4. **推行“契约即代码”（Schema-First）** 纯 Word/Markdown 文档极易在迭代中与真实代码脱节。建议在设计阶段同步沉淀机器可读的契约文件（如 **JSON Schema**、**Protobuf `.proto`** 或 **Avro Schema**），前后端直接基于同一份 Schema 自动生成类型定义与校验器，把人工对文档的成本降到最低。







## 迭代实施(编码阶段)

进行敏捷开发，将大项目的技术功能部分拆解为一个个小功能模块进行开发

- **任务拆解（Backlog Refinement）(BR)**：把需求拆解成一个个具体的开发任务（Ticket）



> **测试驱动开发(TDD)**：遵循经典的 **“红—绿—重构”** 循环：1. 编写失败测试（红 - Red）2. 编
> 写功能代码（绿 - Green）3. 代码重构（重构 - Refactor）


- **并行编码 (Developers)(Dev)：** 前端开发（写界面和交互）与后端开发（写逻辑和处理数据）对照 API 文档同时开工

- **CI/CD 管道建设 (DevOps/Architect) (D/A)：** 搭建自动化构建和部署流水线。代码一提交，系统自动进行语法检查和编译

- **每日例会讨论：** 团队/个人花时间进行功能颗粒度对其，暴露存在的问题







## 项目测试

**核心任务：找 Bug，确保软件稳定、安全**

- **单元测试 (Developers)：** 开发自己写代码测试自己写的函数是否正确。

- **功能与集成测试 (QA)：** 测试人员根据《测试用例》，全方位轰炸系统，找出界面错位、逻辑漏洞等 Bug，并提交给开发修复。

- **性能与压力测试 (QA/Architect)：** 模拟几万、几十万人同时涌入系统，看系统会不会崩溃，找出性能瓶颈并优化。

- **UAT 测试（用户验收测试）(PM/Client)：** 让真实用户或业务方在模拟环境中提前试用，确认开发出来的东西确实是他们想要的。

- **产出物：** 测试报告、Bug 修复清单、可发布版本
