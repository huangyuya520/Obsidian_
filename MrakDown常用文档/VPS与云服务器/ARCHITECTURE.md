# 二级代理部署 Skill 架构记录

## 目的

`chained-vps-proxy-deployment/SKILL.md` 将二级代理部署抽象为可复用技能：一个或多个 Relay 节点负责中转，一个 Egress 节点负责最终出口，并覆盖代理协议、透明转发、IPv4/IPv6、云端端口映射、防火墙、分层验收和回滚。

## 固化的架构决策

- 使用 `Relay`、`Egress`、`Management plane` 和 `Data plane` 描述角色，不绑定国家、供应商、固定端口或固定服务名。
- 先从目标环境发现服务、配置、监听、路由、防火墙后端和云端映射，再选择协议终止、透明转发或混合方案。
- 先审计、再备份、后变更；既有 Egress 配置默认不覆盖，优先新增兼容入站或限制来源。
- 不接受安装脚本的清空/关闭防火墙选项；云安全组、NAT、主机防火墙和服务监听按层验证。
- IPv4 与 IPv6 的 DNS、云端规则、监听、防火墙、路由和外部可达性分别验证；IPv6 URI 地址使用方括号。
- 透明转发与协议终止属于不同架构。迁移时旧 NAT、旧入口、旧客户端配置和旧文档必须与新架构同步标记状态。
- 端口迁移遵循“先新后旧”：新映射/规则/监听先准备，完成外部与端到端验收后再删除旧路径。
- 服务端已完成 Relay→Egress 链路时，客户端不额外启用前置代理；Mux、UDP/QUIC 等增强项由兼容性和实测决定。
- 交付文档区分“已验证”“静态确认”和“尚未验证”，不把配置存在误写成公网或端到端成功。

## 源记录抽象出的关键坑点

1. 公网端口、云端映射、宿主机/容器目标和实际监听可能不一致；不能只改客户端端口。
2. 管理 API 具有版本差异，返回 `404` 或字段不符时不能猜接口；应检查实际版本、前端调用、日志和权威配置来源。
3. IPv4 与 IPv6 防火墙规则相互独立；通配 IPv6 监听是否接受 IPv4 还受系统双栈策略、映射和防火墙影响。
4. 透明中继切换为协议终止后，原客户端参数通常不再适用，必须根据新入口重新生成公开参数和客户端配置。
5. 同一 Relay 上的直连、管理、备用和二级代理入口必须分别标注出口、地址族、转发模式和生命周期，不能混称为同一节点。

## 脱敏边界

本 Skill 包不保存真实 IP、SSH 密码、UUID、代理/Reality 私钥、公钥、Short ID、面板凭据、完整 VMess/VLESS 链接或数据库内容。运行时使用变量和安全凭据输入；普通变更记录仅保留脱敏摘要、参数类型和验证结论。

## 2026-09-05 动态化优化

本次优化移除了地域、实例端口、固定服务组合和特定历史拓扑的直接依赖，改用角色占位符、能力发现、地址族矩阵、事实/决策分离和条件化命令。后续新增案例仅在明确标注为“非默认示例”时写入具体协议或端口。
