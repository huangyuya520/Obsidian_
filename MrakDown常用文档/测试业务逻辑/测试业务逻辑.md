
# 测试准备阶段


![](Pasted%20image%2020261020111200.png)


## 1. 需求分析与评审阶段
此阶段的核心是建立对业务逻辑的统一认知，提前挖掘需求漏洞，防止“设计即缺陷”。

- **业务逻辑与核心活动：**
    
    - 精读产品需求文档（PRD）、业务原型图、交互说明书及接口架构设计方案。
        
    - 梳理业务实体、主干业务流、分支流、边界场景与异常容错逻辑。
        
    - 参与由产品经理主持的需求评审会，针对需求模糊、逻辑自相矛盾、缺失边界条件、缺少逆向流程或不可测的内容提出质疑并推动澄清。

- **准入与准出：**
    
    - _准入条件：_ 产品经理输出正式版本的 PRD 及原型。
        
    - _准出条件：_ 所有需求疑问项均达成闭环一致，PRD 完成定稿基线化。

- **核心产出内容：**
    
    1. **==《需求疑问清单 / 澄清记录表》==**：记录需求评审中提出的问题、产品/架构回复及变更决议。
        
    2. **==《业务流程图 / 业务梳理思维导图（XMind）》==**：梳理后的业务主体脉络与功能结构拆解图。
        
    3. **《需求跟踪矩阵（RTM，初稿）》**：建立业务需求编号与后续用例的映射索引雏形，确保需求无死角覆盖











1. 产品需求文档、产品原型图、接口说明文档以及设计说明文档等应齐全
==---重点：需求文档分析==

了解熟悉业务，分析需求测试点

（1）确认功能(业务功能，辅助功能，数据约束，易用性需求，编辑约束，参数需求，权限需求，性能约束）

（2）场景分析（考虑场景调用者和系统内部各个场景之间联系）

（3）挖掘隐性需求（常用业务流程以及各分支）








## 2. 测试计划与方案设计阶段
明确本次迭代或项目的测试范围、测试深度、策略方案与排期，进行资源协同与风险前置。

- **业务逻辑与核心活动：**
    
    - 依据需求变更规模、工期限制以及系统架构风险，确定测试维度（功能测试、接口测试、性能测试、兼容性、安全性等）。
        
    - 制定测试策略，如核心业务依赖哪些第三方接口、哪些模块通过自动化回归、哪些环节需进行压测。
        
    - 估算测试工时，进行 WBS（工作分解结构）排期，协调测试环境资源与多端配合计划。
        
    - 识别项目风险（如第三方接口延期交付、联调环境不稳定）并制定降级备选方案。

- **准入与准出：**
    
    - _准入条件：_ PRD 基线化，研发排期已初步锁定。
        
    - _准出条件：_ 测试计划经研发主管、产品经理、项目经理共同评审通过。

- **核心产出内容：**
    
    1. **==《软件测试计划（Test Plan）》==**：包含测试背景、测试范围、测试环境诉求、进度排期、资源分配、人员职责、风险评估与应对措施。
        
    2. **==《测试策略/方案设计文档》==**（大型项目特有）：针对性能、安全、接口自动化等专项测试的落地策略与工具选型





### 《软件测试计划》编写内容


1. 编写目的

此文档根据项目需求文档，制定测试策略、评估测试风险，确定所需的资源，并对测试的工作量进行估计，进行人员和进度安排，并且列出测试项目的可交付元素。

2. 参考文档

详细设计文档，设计原型

3. 测试概要

（1）测试目标

通过测试，达到以下目标：

**==测试已实现的产品是否达到设计的要求，包括：各个功能点是否以实现，业务流程是否正确。；==**

==**产品规定的操作和系统运行稳定；**==

**==Bug数和缺陷率控制在可接收的范围之内，遗留BUG一般不超过所有BUG的10%==**

（2）测试范围

列出测试最终需要交付的功能模块列表

（3）测试人力资源
（4）测试环境：服务器环境，终端环境，网络环境
（5）bug管理工具

==一、 按功能与业务需求划分（功能测试）==

- **基本功能测试**：验证软件的所有业务逻辑、界面交互、输入输出是否符合需求规格说明书。

- **边界值与等价类测试**：针对输入框、数字、日期等做极限值、空值、超长字符串、非法字符等异常输入测试。

- **流程与业务链路测试**：测试单据流转、主干业务流程（如电商下单、支付、退款闭环）以及多角色协同流程。

- **数据与数据库测试**：验证数据的增删改查（CRUD）、数据一致性、事务处理以及缓存同步是否准确


==二、 按非功能属性划分（质量特性测试）==

- **性能测试**：
    - **负载/压力测试**：评估系统在高并发、大流量下的响应时间、吞吐量和资源占用率（CPU、内存、网络）。
    - **稳定性/可靠性测试**：长时间连续运行下，系统是否存在内存泄漏、句柄未释放或崩溃问题。 [[1](https://zhuanlan.zhihu.com/p/680724235), [2](https://zhuanlan.zhihu.com/p/482983707)]

- **安全性测试**：检测系统漏洞，如 SQL 注入、XSS 跨站脚本、越权访问、敏感数据明文传输、认证与权限绕过等。 [[1](https://zhuanlan.zhihu.com/p/680724235)]

- **兼容性测试**：
    - **平台与设备**：不同操作系统（Windows、macOS、Linux、iOS、Android）、不同浏览器（Chrome、Safari、Edge等）。
    - **分辨率与机型**：各种屏幕尺寸、移动端主流机型适配。 [[1](https://zhuanlan.zhihu.com/p/680724235)]

- **易用性与界面（UI）测试**：检查文字拼写、排版对齐、按钮反馈、色彩规范以及是否符合用户操作习惯（UI/UX）。 [[1](https://zhuanlan.zhihu.com/p/482983707), [2](https://zhuanlan.zhihu.com/p/680724235)]

- **安装、卸载与升级测试**：验证全新安装、覆盖安装、卸载残留以及历史版本平滑升级的能力



==三、 按软件开发阶段划分（测试进阶范围）==

- **单元测试（Unit Testing）**：由开发人员或白盒测试员针对代码中最小的模块（如函数、类）进行隔离测试。 [[1](https://ww2.mathworks.cn/discovery/software-testing.html), [2](https://www.cnblogs.com/R-bear/p/17786698.html)]

- **集成测试（Integration Testing）**：验证各模块之间的接口、数据传递及协同工作是否正常。 [[1](https://www.cnblogs.com/R-bear/p/17786698.html), [2](https://ww2.mathworks.cn/discovery/software-testing.html)]

- **系统测试（System Testing）**：将软硬件作为一个整体，全面验证系统是否满足客户需求规格。 [[1](https://ww2.mathworks.cn/discovery/software-testing.html), [2](https://www.cnblogs.com/R-bear/p/17786698.html)]

- **验收测试（Acceptance Testing / UAT）**：在交付前由用户、业务方或产品经理从业务角度进行的最终确认测试（包含 Alpha/Beta 测试）。 [[1](https://www.cnblogs.com/R-bear/p/17786698.html), [2](https://zhuanlan.zhihu.com/p/680724235)]

- **冒烟测试（Smoke Testing）**：版本提测后对核心主干功能进行快速验证，确认主流程可用才进入全面测试。 [[1](https://blog.csdn.net/qq_48811377/article/details/139774584), [2](https://zhuanlan.zhihu.com/p/482983707)]

- **回归测试（Regression Testing）**：在代码修改、修复 Bug 或迭代新版本后，重新测试受影响的模块及周边功能，确保未引入新问题




4. 测试规范

开始测试标准：代码编译通过，软件可以争取安装运行，实现功能与产品设计出人，冒烟测试通过

中断测试标准：安装无法正确完成，程序代码编译不通过，系统服务异常，发现阻塞功能的bug


5. bug规范

致命，严重，一般，建议


6. 测试策略

冒烟测试：依据开发提测时间变动

第一轮功能测试：执行测试用例，包括边界值测试，兼容性测试，易用性测试，用户界面测试，安全性测试

第二轮功能测试：bug复测及功能验证

回归测试：全面回归测试

性能测试：需确认具体性能测试方案和工具

发布测试

测试报告总结


7. 测试风险

测试本身（测试时间/测试技术/开发进度延误/难以修复缺陷/其它原因）



8. 测试输出文档

==测试计划==
==测试用例==
==测试bug单==
==测试报告==








## 3. 测试用例设计与评审阶段
将业务逻辑转化为可落地执行的验证细则，建立测试执行的基准标准。

- **业务逻辑与核心活动：**
    
    - 运用黑盒测试设计方法（等价类划分、边界值分析、判定表、因果图、状态迁移法、场景法、错误推测法）编写具体用例。
        
    - 设计冒烟测试用例集（BVT，Build Verification Testing），提炼核心业务主通路。
        
    - 组织测试内部互审，以及三方用例评审（产品、开发、测试），校对测试点是否充分、业务规则理解是否出现偏差。

- **准入与准出：**
    
    - _准入条件：_ PRD 定稿，测试方案确认。
        
    - _准出条件：_ 三方评审意见全部修正完毕，测试用例集入库基线化。

- **核心产出内容：**
    
    1. ==《软件测试用例集（Test Cases）》==：包含用例编号、模块、前置条件、测试数据、操作步骤、预期结果、用例等级（P0-P3）。
        
    2. ==《冒烟测试用例集（Smoke Test Suite）》==：针对系统核心闭环流程提取的 P0 级别极简用例集。
        
    3. **《完善版需求跟踪矩阵（RTM）》**：补充“需求项 - 测试用例”的双向追溯关系







### 《软件测试用例集》编写内容
测试需求分析和业务流程分析

1. 设计方法：

等价类划分法（将测试的范围划分成几个互不相交的子集）

边界值分析法（选出的测试用例，应选取正好等于、刚刚大于、刚刚小于边界的值）

错误推测法（在测试程序时，人们可以根据经验或直觉推测程序中可能存在的各种错误）

判定表法（适合于逻辑判断复杂的场景，通过穷举条件获得结果，对结果再进行优化合并，会得到一个判断清晰的策略）

正交实验法（在各因素互相独立的情况下，设计出一种特殊的表格，找出能以少数替代全面的测试用例）

还有其它场景法和状态迁移法等

2. 测试用例八要素：用例编号，测试项目，测试标题，重要级别，预置条件，测试输入，操作步骤，预期输出

（1） 用例编号（规则：由字符和数字组成的字符串，具有唯一性，易识别性）

（2） 测试项目（对应测试用例编号中的测试子项名 系统测试

（3） 测试标题（体现测试出发点关注点以及测试用例期盼的测试结果）

（4） 重要级别、优先级别（重要级别一般分为高中低 ）

（5） 预置条件：测试用例在执行时需要满足一些前提条件，环境的设置

（6） 测试输入（测试执行中需要加工的外部信息，避免用描述性语言，要具体，根据测试用例具体情况，有手工输入，文件，数据库记录）

（7） 操作步骤：执行当前用例需要经过的操作步骤，需要明确的给出每一个步骤的描述

（8） 预期输出：需要判断测试对象是否正常工作



# 测试执行阶段

## 1. 测试环境与测试数据准备阶段

在代码提测前构建起稳定、可运行的隔离验证空间，避免因数据或环境阻塞测试进度。

- **业务逻辑与核心活动：**
    
    - 协同运维/基础架构部署被测版本所需的服务端节点、中间件（Redis、MQ 等）及数据库。
        
    - 针对复杂上下游链路配置 Mock 桩服务，屏蔽第三方不可控因素。
        
    - 构造满足业务测试需要的基准数据（如特定会员等级账号、特定状态订单、余额账户、测试卡号等）。

- **准入与准出：**
    
    - _准入条件：_ 研发联调进入尾声，测试用例设计基本完工。
        
    - _准出条件：_ 测试环境联通性验证通过，基础测试数据与配置项生效可用。

- **核心产出内容：**
    
    1. **==《测试环境拓扑与配置说明文档》==**：记录环境域名、服务版本、中间件地址、白名单及 Mock 配置规则。
        
    2. ==**《测试数据池 / 账号清单》**==：分类整理的测试账号底表、初始数据集、数据初始化执行脚本






### 《测试环境拓扑与配置说明文档》编写内容


1. 测试环境搭建

==测试环境：硬件环境，软件环境==
==硬件环境：测试必须的服务器，客户端，网络连接设备，以及打印机/扫描仪等辅助硬件设备构成的环境==
==软件环境：被测软件运行的操作系统，数据库以及其它应用软件构成的环境==
==搭建测试环境的准备工作：==
==安装工具：虚拟机==
==虚拟机优点：运行在主机上==








## 2. 冒烟测试与提测准入阶段
对开发提测包进行质量第一关卡拦截，防止质量过差的代码浪费测试团队的正式人力。

- **业务逻辑与核心活动：**
    
    - 研发完成代码联调与单元测试，在测试平台发起提测工单。
        
    - 测试人员严格执行《冒烟测试用例集》，通常耗时 30-60 分钟。
        
    - 若主流程受阻、阻断性 Bug 超过阈值，直接触发提测驳回机制，退回开发返工。

- **准入与准出：**
    
    - _准入条件：_ 研发提交提测申请，附带自测报告与部署构建物。
        
    - _准出条件：_ 冒烟用例 100% 通过，主业务逻辑畅通无阻。

- **核心产出内容：**
    
    1. **==《提测准入审核记录 / 冒烟测试结果》==**：明确标注“准入通过”或“打回并记录驳回原因”。






### 《冒烟测试结果》编写内容

执行测试用例

根据测试用例优先级来执行测试用例

-----测试关注点

1. 根据UI效果图进行UI测试

（1）、观察APP的用户界面(如菜单、对话框、窗口和其它可规控件)是否符合UI稿

（2）、不同的连接页面之间导航链接是否有效，是否跳转是否正确

（3）、旋转手机，确保程序不退出，页面排版无异常

（5）、输入框说明文字的内容与产品需求一致

（6）、某页无数据时、断网时、有网但接口异常时的状态页是否和UI一致

2. 功能测试时主要依据编写的功能测试用例进行软件功能的测试

3. 涉及的测试主要包括基本功能测试，逻辑测试，安装、卸载、运行测试，中断测试，异常处理（包括网络突然断开或者网速过慢、机器内存不足等异常情况的处理）测试

（1）、App安装完成后是否能正常启动，且打开速度控制在预期时间内

（2）、切换后台再切换前台的操作对当前状态如登陆、当前页、数据刷新的影响

（3）、强制杀掉APP进程再启动对当前状态如登陆、当前页、数据刷新的影响

（4）、登陆验证/免密登陆时的手势密码和指纹是否正常符合产品需求

（5）、对于有数据交换的页面，每个页面都必需要进行前后台切换、锁屏解锁的测试，这种页面最容易出现崩溃

（6）、同一用户在多个终端先后登陆时，APP是否有正常符合产品需求的处理

（7）、App使用过程中有电话进来的中断测试，与文件下载、音乐播放、等应用的交叉情况测试

（8）、很多应用会支持缓存数据，测试在断网启动或从有网到无网时是否可以浏览缓存数据

（9）、软件在不同操作系统及版本（Android、iOS、）下安装是否正常

（10）、软件安装后的是否能够正常运行，安装后的文件夹及文件是否写到了指定的目录里，安装后没有生成多余的目录结构和文件

（11）、软件安装过程是否可以取消

（12）、软件安装过程中意外情况的处理是否符合需求（如死机，重启，断电）

（13）、安装空间不足时是否有相应提示

（14）、对于需要通过网络验证之类的安装，在断网情况下尝试一下

（15）、重复安装应该有提示iOS没有提示

（16）、升级安装时，版本更新链接有效，比如后台设置的版本白名单

（17）、使用各种方式卸载程序，如直接删除安装文件夹卸载是否有提示信息、长按图标卸载、手机设置里卸载、第三方应用卸载iOS卸载没有提示，Android安装时会闪退（偶现）

（18）、测试卸载后文件是否全部删除所有的安装文件夹

（19）、卸载过程中出现的意外情况的测试（如死机、断电、重启）

（20）、卸载是否支持取消功能，单击取消后软件卸载的情况


4. 兼容性及适配测试

硬件的适配：不同手机厂商、硬件性能，不同屏幕大小的适配；

如：

厂商：苹果，型号：苹果XSmax,手机版本：iOS11，屏幕：6.0英寸，分辨率：2688x1224像素

（2） iOS版本的兼容：IOS 6版本以上；Andriod 5版本以上等

（3） 不同分辨率屏幕的适配：移动设备的分辨率多种多样，如果app没有做比较合适的处理就可能会显示不好，甚至影响功能的操作。

（4） 兼容性测试必须在一定数量的真机上进行，由于真机类型过多，尤其Android在做兼容性测试时，可以选取典型的几种运用较多的真机，进行兼容性测试

（6）在各种系统、系统版本的不同手机上测试登陆，卸载，注册，登陆，修改密码等功能

5. 安全性测试

- 软件权限

（3）限制/允许使用手机读取用户数据，手机信息、联系人信息等

（3）对密码长度和复杂度的安全要求

（4）当将密码或其他的敏感数据输人到应用程序时, 其不会被储存在设备中, 同时密码也不会被解码

（5）当应用程序处理明细或其它的敏感数据时，不以明文形式将数据写到其他单独的文件或者临时文件中

## 1. 验收测试与上线准备阶段

站在终端用户或真实业务方角度评估系统可用性，确保系统符合商业预期并保障安全发布。

- **业务逻辑与核心活动：**
    
    - 测试团队提供支持，协助产品经理、业务方或客户代表进行用户验收测试（UAT）。
        
    - 配合运维编写上线配置步骤，整理 SQL 变更脚本、系统配置项与灰度放量规则。
        
    - 组织上线演练，准备上线回归核对表（Checklist）。

- **准入与准出：**
    
    - _准入条件：_ 系统测试完成准出，无阻断性缺陷。
        
    - _准出条件：_ UAT 验收签字确认，发布审查委员会审批通过。
        
- **核心产出内容：**
    
    1. **《UAT 验收记录与业务签字确认单》**：业务方确认功能符合交付预期的正式记录。
        
    2. **《上线发布执行 Checklist》**：包含上线顺序依赖、配置项检查点、生产冒烟验证核心用例。
        
    3. ==**《应急回滚方案与预案说明》**==：遭遇严重生产事故时的容灾回退指导






**==线上测试注意事项==**

1. 如果没有白名单，这个时候是不能随便操作做数据的，测试人员能做的也就是点点，保证按钮、界面正常。如果是业务人员做好数据，测试人员要验证数据的准确性和界面显示无误。

2. 如果有白名单，也不能随便操作数据，但是可以在容许的情况下，回归一遍线上测试，保证线上测试无误。
